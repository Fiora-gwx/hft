# Agent Note: M1.5 扩大测量范围,M3 末加一次满订阅探针并用它定主机档位

Status: proposed

## Problem

M1.5 延迟探针只有单 venue BBO、无深度、简化 sequencer,看不到 IRQ 核上的软中断队头阻塞、多 socket 行情线程的轮询节拍与 BBO 批对回报的阻塞,而 c16 与 c32 的差别恰恰取决于这几项;规格却让 M1.5 承担选档([W5 评审](../../../../design/_work/review-2026-10-03-M0d-W5延迟与整体.md) N-P1-1、N-P1-6)。AZ 探测排在 M7 之前,而 M1.5 已要求开在 Binance 所在 AZ([W4 评审](../../../../design/_work/review-2026-10-03-M0d-W4运行与交付.md) P1-8)。

## Proposal

用户决定按推荐执行([round8-decisions](../../../../design/_work/round8-decisions.md) R8-11;规范见 [round8e 简报](../../../../design/_work/round8e-spec-brief.md) E3)。里程碑归 [11 实施路线图](../../../../design/11-实施路线图.md),线程计划归 [hft-core](../../../../apps/hft-core/README.md#线程计划),租用实例的用法归 [development 参考机](../../../../docs/development.md#参考机),调优核对归 [host-tuning](../../../../docs/runbooks/host-tuning.md)。

1. **AZ 探测前移到 M1.5 之前**([az-probe](../../../../docs/runbooks/az-probe.md)),租用实例开在选定 AZ;同一报告给出第二 AZ 与是否需要第三 AZ 看门狗。
2. **M1.5 增测**(结论写 Agent Note):"压舱"深度连接(全量订阅、只读不解码)下的 `nic_to_kernel`;IRQ 核空闲 vs 保持唤醒 A/B;`calib_err_ns`;`net_poll_empty`;每包软中断成本;CNTVCT 频率;HW RX 时间戳与 PTP;ENA 队列数与 RSS。M1.5 不再选档。
3. **M3 末满订阅探针**:按需租 `c8g.4xlarge`,按 c16 线程计划、6 个产品线满订阅(BBO、成交、标记价、资金费,另加压舱深度),打开 raw journal 与 persist,测试网探针单。据此选定主机类(默认 c32;c16 只在达标且启用 `epoll_pwait(0)` 时保留),并决定是否启用 IRQ 拆分([irq-split-reserve](2026-10-03-irq-split-reserve.md))。

## Alternatives considered

**在 M1.5 定档。** 测量对象与最终负载差太远,定出来的档位要么过大要么在 M7 才发现不够。

**等到 M7 在升级主机上定档。** 档位错了要重开实例、重建 ENI 与 EIP、重跑 AMI 验证,且 M7 的 ⑩ 窗口推迟;M3 末探针只多租几小时 c8g.4xlarge(几十美元量级)。

**直接上 c32 不测。** 费用约为 c16 的两倍,且 IRQ 拆分是否需要仍无依据。

## Acceptance criteria

- M1.5 结论 Note 含上列每项的数值(或"不可用"与原因)。
- M3 末探针报告:BBO 的 `nic_to_kernel` 在批量推送窗口内外的 p99、各热线程的轮询节拍、c16 计划下的核与内存余量;结论(档位、是否启用 ENI-B2)写进 ops-log 与 architecture-v2/11。
- az-probe 报告在 M1.5 开机前完成。

## Risks

- 测试网探针单的回执路径与正式端点不同,订单类分段只作近似;最终仍以 ⑩ 为准。
- 租用实例的开关机依赖负责人的时间;忘记关机产生持续费用(ops-log 记录开关时刻)。

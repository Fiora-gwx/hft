# Agent Note: M2 收窄为 M2-lite

Status: implemented

## Problem

审计发现 M2 的规格增长与实现进度相抵,净进度约为零;M2 设计对首个 CEX-CEX 策略范围过大。以 `current_milestone = "M2"` 本地运行 `cargo xtask test-trace`,未实现的 M2 用例有 306 条,其中多数属于现金归因、Model 检查点、逐字节恢复核验与运维流程,与"两所对冲的资金主路径"无关。

## Decision

负责人 2026-10-14 采用 M2-lite,规格冻结(新增用例须负责人批准)。退出条件与推迟清单归 [11 §3.3](../../../../design/11-实施路线图.md);本 Note 只记依据与计数。

- **留在 M2**:每个 venue 单账户、两个 venue;OMS 状态机、热账本、风控(限额、Kill、CloseOnly)、执行层对冲(含 `HEDGE_LIMIT` 与滑点定价 SEQ-171/172/173)、只追加 journal、replayer 只做 verify、DST 不变量冒烟、解耦验收(SDK-001–010、REG-011)。
- **`M9`(上线后)**:现金归因(PERP_CASH、外来现金、凭据、ReconcileBatch、AUTO_EXTERNAL/ADL 合成、资金费自动校正、AdoptExchange/WriteOffResidual)、引擎内 Sim 账户、advisor/Advice/Model 检查点/`InjectWarmup`/hft-py、冷 JournalLedger、逐字节恢复核验(关键帧 Verify/Mirror/Recompute、RecoverMismatch、state_hash 二分)、同一 venue 多账户。`M9` 由 test-trace 解析为大于 M8,`check_tests.py` 的里程碑集合同一提交加入。
- **移到上线前的后续里程碑**(不在负责人推迟清单里、上线前仍需要):主循环让位、BBO 等待与吞吐/零分配基准、L2 深度与订阅、账户配置与下架公告 → M3;MarginStress/L3、自身 ADL/强平成交、无 client id 成交归属 → M4(其验收本就含"单边 +30%");冷启动与崩溃恢复、启动闸门、Drain/升级/ReplaceRefdata、控制命令映射、replayer CLI 细节 → M5(其验收含崩溃恢复与 Drain 演练)。
- `strategies/` 下(latency-probe、registry)的改标按 decoupling-gate 单独提交。
- 只改未实现用例的 `里程碑`;已实现并通过的 M2 测试(含推迟功能的)保持不变。

## Alternatives considered

把所有非 M2-lite 用例都标为 `M9`:会把上线门槛依赖的 MarginStress、崩溃恢复与 Drain 推到上线之后,与"上线门槛不变"矛盾,因此只把负责人列出的功能与多账户标为 `M9`,其余按既有里程碑内容分到 M3–M5。删除推迟功能的用例:会丢失已写定的验收,且违反"删除的编号不复用、保留标题"的规则,不采用。

## Acceptance criteria

本地 `current_milestone = "M2"` 的 `cargo xtask test-trace` 报 unimplemented = 106、extra = 0、inconsistent = 0;`check_tests.py` 无问题。仓库内的 `current_milestone` 仍为 `M1`(test-trace 改为只报告由 CI 负责人另行提交)。

## Risks

M3–M5 的用例数因此增加,后续里程碑需按同一口径再审。`M9` 功能在启用前必须复核其规格与 [docs/changes.md](../../../../docs/changes.md) 中对应的未确认行(批次见 [签字批次 1](../../implemented/process/2026-10-14-signoff-batch-1.md))。

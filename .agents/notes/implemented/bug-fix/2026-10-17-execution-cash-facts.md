# Agent Note: 系统成交使用交易所现金事实

Status: implemented

## Problem

测试网逐笔凭据汇总为已实现 −0.16010941 USDT、手续费 2.25536270 USDT,初始钱包 4988.90231663,最终 REST 4986.48684452。本地均价的分析已实现为 −0.16011000,六位现金投影因此少一个最小单位。协议已读取 rp,但系统 OrderEvent 没有携带它。

## Decision

按负责人默认决定,OrderEvent v4 追加本笔现金覆盖量和金额,保留旧累计字段及偏移。在线 OMS 与冷 JournalLedger 在完整订单身份下将连续逐笔事实转为累计水位,钱包通过既有 apply_settled_fill 使用实际现金,费用独立记一次。本地均价仍用于分析已实现和成本。Binance rp 是本笔交易现金,不能直接写成订单累计金额;协议来源见 [USDⓈ-M user data stream](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/user-data-streams#event-order-update)。

## Alternatives considered

直接覆盖钱包余额会把遗漏成交或费用掩盖为现金修正。用单笔 rp 填累计 cash_sum 会在多笔成交时少算或重复。仅修改 Python 投影会使冷热账本分叉。为此不采用这些方案,也不宣称生产协议已经支持完整外来 PERP_CASH。

## Consequences

首次已知零现金也建立覆盖水位,之后缺事实的新成交、遗漏的成交前缀、混合两种表示和金额溢出均失败。没有保留订单身份的逐笔事实不能推测累计前缀。重复/旧水位不再入账,同一成交键的金融载荷一致性沿用协议保证。槽和墓碑继续持久化现有累计水位,网关重连不丢结算进度。

OrderEvent 体长 136 B,rep 环元素上限 144 B;追加事实使回报元素增加 16 B,Windows dev profile 的私有流基准复测均值置信区间为 [8.8653,9.0138,9.1972] µs,未见该场景退化;真实主机端到端延迟仍需复测。旧累计字段在未启用 PERP_CASH 时保持原先不参与现金结算的语义;只有新逐笔字段或已持久化的覆盖前缀启用可选现金路径。旧 journal 未记录的现金事实不会凭空恢复,历史修正必须从原始成交凭据重新归一化。未开启完整外来现金能力,其来源容量与重叠限制不变。

SEQ-411/412 使用真实 sequencer、OMS、热账本、冷投影和全量/快照回放验证连续分笔、重复、终态查询、缺口拒绝,并以原会话汇总金额构造确定性订单验证严格余额相等;该测试不冒充原会话 247 笔的逐条重放。EVT-205 验证编码兼容及覆盖边界,BIN-101 验证 rp 精度和缺失/零的区别。

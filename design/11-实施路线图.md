# 11 · 交付计划

> 新框架首要服务 CEX-CEX(ccex):按依赖顺序建成、在 CI 与现有服务器上测试。**不设小额实盘阶段,只有模拟盘与正式实盘**(R8-9):现有服务器(`dev2`)只做开发测试、交易所测试网/模拟盘联调与模拟账户长跑,不放正式实盘账户;**延迟的第一份证据来自 M1.5 延迟探针**(按需租用的主机,§3.1);大体没问题后统一升级主机,升级主机同时运行 `prod` 与 `sim` 两个实例,在那里做延迟验收;上线门槛全部满足后,先做零成交冒烟与正式实例 Shadow 3–7 天(不开仓),再让首个策略在**新开的交易所子账户**上开始正式实盘。不接管旧仓位,不与现有系统共用账户。现有 cdex 继续在旧框架运行,迁移到新框架是可选扩展。不设周次,按依赖慢慢做。组件是否在交付范围内,以 `hft/` 各 README frontmatter 的 `scope: core | optional` 为唯一来源(可选组件另有 `status: frozen`)。
>
> 本章是 M1.5 里程碑、M3 末满订阅探针与整体路线图的唯一归属;hft 规格(development、testing、latency-budget、hft-core 线程计划)链接这里。数值(容量、门槛、CI 分钟)不在本章重抄,链接各自的归属。

## 2. 开发与构建环境

- **代码仓库**(R8-12):实现开始(M1)时把 `E:\trading\hft` 复制到本机目录 `E:\hft`(主控选定,在 `E:\trading` 之外;待用户纠正);**免费 GitHub 组织**下的私有仓库 `<org>/hft` 由负责人创建后再推送(`[需授权]`;负责人 = Admin,老板 = Read 角色——个人账户的私有仓库做不到只读协作者),在此之前只做本地 git 提交。不放进 Trading 的仓库,避免误传;Trading 仓库仍在个人账户。规格在 M0-f 与测试规格(M0-g)合并后冻结为设计基线 v1(§3 M0 行)。
- **本地**(R8-12):Windows 本机写代码;本机已有 Rust 工具链,平台无关的 crate 在本机 `cargo test`,Linux 专用部分以 `cargo check --target aarch64-unknown-linux-gnu` 检查;正式构建以 CI 为准;不用 WSL2。
- **CI 是唯一的正式构建环境,只用免费的 GitHub 托管 runner,与旧项目一致**(R8-8):质量门在 `ubuntu-latest`;aarch64 不可变发布归档按 tag 在 `ubuntu-24.04-arm` 产出(也可对 `ci.yml` 全绿的 PR 头直接出开发构建);服务器上跑 ③④ 用的验证包也由 CI 构建(§4.1);不用自托管 runner。工作流清单、构建剖面、超时与缓存,唯一归属 [development.md](../docs/development.md);形态与理由见 [10 §5](10-语言分工与代码组织.md)。
- **CI 分钟**(R8-10、R8-11、R8-12):组织私有仓库每月 2,000 分钟由 hft 独享(与 Trading 互不影响),不加付费资源。分钟分配、额度规则(用量自估与每周对账、Admin 覆盖、过阈值后 PR 只跑哪些作业)、额度耗尽时的应急出包路径与 arm runner 不可用时的交叉编译路径,唯一归属 [development.md](../docs/development.md),本章不重抄。Free 组织的私有仓库没有受保护分支:生产安全以"发布工作流 `preflight` 证实该 SHA 的 `ci.yml` 全绿且 `decoupling-gate` 通过"为准。`ubuntu-24.04-arm` 在个人私有仓库可用已由 Trading 8–9 月 20 次成功运行证实;组织私有仓库上的可用性与计费倍率 M1 第一周核实([待测量 J6](待测量与待决定事项-2026-10-01.md))。
- **服务器不编译**:现有服务器只安装 CI 产出的发布制品与验证包(冷部署、保留一个已验证回滚版本);交易所联调只能在服务器上做(本机连不上交易所)。改动 `venue-*`、`hft-venue`、`hft-net`、`hft-oms` 的版本,在升级主机上发布前先在 dev2 测试网窗口装同一个版本冒烟。仓库与 CI 的唯一归属是 [deploy](../deploy/README.md) 与 [development.md](../docs/development.md)。
- **dev2 上运行什么**(R8-9、R8-10):长期运行 `sim` 实例(只含 Sim 账户、不持任何 key);交易所测试网/模拟盘联调时另起一个 `prod` 角色实例,指向测试网端点(行情也用测试网:`feed_env = "testnet"` 与测试网 refdata)、只持测试网 key、refdata 只含测试网账户,只在联调窗口运行;以最低优先级常态运行 `hft-verify`(③④ 累计);运行机外看门狗 `hft-offbox-watchdog`(dev2 在 apne1-az2,升级主机开在 Binance 所在 AZ,正好用来盯升级主机;若 az-probe 证实两者同 AZ,看门狗改到第三 AZ 的 t4g.nano,§6)。**dev2 不放正式实盘账户**——所以护栏停掉 hft-core 不会留下实盘断腿。
- **dev2 护栏**(现有服务器同时跑 cdex 正式账户;2 vCPU、3.8 GB,swap 已用约 0.8 GB):hft-core 运行在 `hft-core.slice`;批处理(replay-verify、hft-verify、journal-archiver、pipeline、treasury)运行在**根级** `hftbatch.slice`,设 `CPUWeight=idle`(cgroup `cpu.idle`;线程级 SCHED_IDLE 不跨 cgroup 生效,所以不靠单元的调度策略),各批处理单元 `Nice=19`,I/O 用带宽上限,不设 `CPUQuota`。守护脚本读**旧系统所在 `system.slice`** 的压力、`MemAvailable` 与 swap-in 速率,但**只在 hft 自身用量明显**(`hft.slice` 或 `hftbatch.slice` 的 CPU 或内存超过阈值,待标定)时才停 hft,否则只告警;整机 PSI 只告警;停机动作写持久标志 `/var/lib/hft/guard/tripped`,批处理单元的 `ExecCondition=` 先查它,人工清除才解除;护栏停掉 sim 后资源回落且无人手动启停过 sim 时自动重启 `hft-core@sim`(每 UTC 日至多一次);只含 Sim 账户的实例非干净重启后,无 `RecoverMismatch`、无毒丸即自动解除 Recovery(规则归 hft-risk)。dev2 上只对 hft 各 uid 加 IMDS 的 nft 丢弃规则,并运行 `hft-cred-broker`(不影响旧系统)。**cdex 优先。** 数值与停机规则唯一归属 [hft-core](../apps/hft-core/README.md#线程计划),单元、slice 与 IMDS 规则归 [deploy](../deploy/README.md)。
- **dev2 联调窗口**:脚本 `hft-window start|stop`;窗口标志 `/run/hft/window/active` 存在期间,批处理单元的 `ExecCondition=` 一律跳过,测试网 `prod` 实例不受每日定时器影响。不用 `Conflicts=`(它是双向的,每天的 replay-verify 定时器会把测试网实例停掉,门槛 ⑥ 的"连续 3 天"每天被打断),也不用 `systemctl mask`(对装在 `/etc/systemd/system` 的单元无效)。`hft-verify.*` 是否安装由主机清单开关 `verify = true|false` 决定。启停步骤与单元规格只在 [deploy](../deploy/README.md)。
- **dev2 退路**(R8-10、R8-11):另开一台 `c7g.large`(约 $66/月,`[需授权]`)专给 hft 跑验证包与回放,主机类仍按 `dev2` 配置,护栏阈值放宽(那台主机上没有旧系统)。触发条件:**M3 标定演练失败**(批处理满载 10 min,护栏动作或 `system.slice` PSI 上升;`[需授权]`,在生产主机上做)→ 提前启用;运行中护栏一周因 hft 自身用量明显而停机 ≥ 2 次(只告警的触发不计),或旧系统的延迟/成交出现可测劣化 → 启用。规则唯一归属 hft-core 的 dev2 护栏。
- **dev2 容量**(R8-11 按"2 个研究策略 × 2 个池实例 × 32 group"重定):`max_instances`、`max_cells_total`、advisor 预算(`advisor.mem_budget_mib`,各策略以 `Model::mem_bytes` 声明,装配时求和)与 Model 检查点磁盘上限的取值只在 [hft-core 容量表](../apps/hft-core/README.md#线程计划);portfolio-carry 的 sim 实例默认 ≤ 32 group。本章不重抄数值(第四轮评审 W3 P2-65 发现本节旧值已与 hft-core 分叉)。

### 3.1 M1.5 延迟探针

**为什么**:五路评审(V5 P1-1、§3.1、§3.7;V4 P1-4)指出,按原计划全链路延迟的第一份证据要到 M7 才出现——参考机要等统一升级后才有,wire 级 mock 是可选项,组合携带下单太少、测试网 7 天凑不够 p99 的样本量;而决定线程计划、IRQ 布局与主机档位的三个结构性问题(收包模型、sequencer 取批、feed 线程队头阻塞)必须在写 hft-net、hft-venue 与 sequencer 主循环之前定下来。对"延迟优先"的系统来说太晚(R8-10 第 2 条)。第四轮评审(W5 N-P1-1、N-P1-6)又指出 M1.5 的简化切片只有单 venue BBO、无深度、简化 sequencer,看不到 IRQ 核的软中断队头阻塞、多 socket 行情线程的轮询节拍与关键帧停顿,而 `c16` 与 `c32` 之差恰恰取决于这几项——所以 M1.5 扩大测量范围、不再承担选档,选档移到 M3 末满订阅探针(§3.2,R8-11)。

**做什么**:

0. **先做 AZ 探测**(az-probe,< $50,[待测量 B1](待测量与待决定事项-2026-10-01.md)):M1.5 租用实例开在探测选出的 AZ。原写法"AZ 探测在 M7 之前、M1.5 却要求开在 Binance 所在 AZ"自相矛盾(W4 P1-8),已前移。
1. **租用实例**:M1 之后按需按小时租 `c8g.4xlarge`(约 $0.8/h,估算),开在上一步选出的 AZ;`[需授权]` 的 AWS 操作由负责人执行;实例上只放测试网 key,用完即停。租用实例的主机清单只在运行期核对网卡 MAC(MAC 不进发布哈希),不必为它先发正式版。
2. **纵切片**:hft-net(中断驱动收包,ENI-B 的 IRQ 在独占核)+ 一个 venue 的 BBO feed(主网公共行情)+ 简化 sequencer + 一个 gw(测试网下单,下单负载按 `latency-probe` 的 `quote` 模式口径:远离对手价的最小名义 PostOnly,Ack 后撤单)。纵切片需要的 hft-net、该 venue 的 BBO 解码与下单帧在这里先写出最小可用部分,其余在 M2/M3 补全;简化 sequencer 只用于探针。
3. **产出**:`kernel_rx`、`ingest`、`decide`(简化)、`egress` 的直方图,HW 与 SW 时间戳分开统计。**增测**(R8-11):
   - "压舱"深度连接(全量订阅、只读不解码)下的 `nic_to_kernel`,与无压舱对照;
   - IRQ 核空闲(WFI)与保持唤醒的 A/B(保持唤醒只用 hostprobe 规则登记的允许形式:`nohlt` 或列入白名单的 keepawake 线程;SCHED_IDLE 自旋线程会触发 TASK_ON_HOT 硬校验,不用);
   - `calib_err_ns`(ENA PHC 的读取窗口)与 PHC↔TSC 插值的误差分布;
   - `net_poll_empty`(一次空 `recvmsg` 的成本)与每包软中断成本;
   - CNTVCT 频率;
   - HW RX 时间戳与 PTP/PHC(假设 [12 A7](12-风险与未决问题.md),两份调研说法相反);ENA 队列数与 RSS 哈希;
   - **HW RX 时间戳不可用时的替代测法**(也用于 §3.2):同 CPG 放一台回显对端,做 TCP 往返 RTT 的 A/B(IRQ 核空闲 / 保持唤醒 × 有 / 无压舱);只在探针上记 IRQ 核的软中断排队时长;
   - 样本按"突发 / 平静"分层抽样(分层规则归 testing §8.2),`kernel_rx` 报上下界(上界来自 `MarketHdr.rx_empty_gap_ns`)。

   结论写成 Agent Note。
4. **据此决定**:hft-net 的收包细节(`epoll_pwait(0)` 与短读即停的实测收益)、时钟换算口径是否成立、IRQ 核要不要保持唤醒;给出 [latency-budget §3](../docs/latency-budget.md) 的第一版 Graviton 分配(现行数字是中断驱动收包下的分配,[00 §4.1](00-目标与延迟预算.md))。**主机类不在这里选**(§3.2)。
5. **参考机从 M1.5 起**:每个里程碑结束时在同型(`c8g.4xlarge`)按需租用实例上跑 `bench-gate --reference`(相对回归 + 单 crate 上限)。它不是 CI;原计划"参考机要到统一升级后才有、M7 之前没有性能回归门槛"已被取代。

**不覆盖的**:完整线程计划、满订阅与关键帧停顿(→ M3 末探针);prod + sim 同机的干扰与 7 天尾部(→ M7 的门槛 ⑩)。门槛 ⑩ 的证据口径(按事件加权的离线统计 + `rep_to_order`,不再另取测试网行情窗口)见 [00 §4.2](00-目标与延迟预算.md)。

### 3.2 M3 末满订阅探针

**为什么**(第四轮评审 W5 N-P1-1、N-P1-2、N-P1-6,R8-11):`c16` 原计划的 feed-bbo 一个线程要轮询全部 venue 的 12 个 BBO socket,光轮询节拍就吃掉 `kernel_rx` 的预算(现计划改为两条 feed-bbo + 一条 feed-md,初值 4 + 8 个 socket,核号表归 [hft-core 线程计划](../apps/hft-core/README.md#线程计划) 的 `c16` 节;是否闭合仍要本探针实测);全部交易网卡流量(含深度、标记价的整点集中推送)挤在一个 IRQ 核上,BBO 会排在软中断后面;这些只有在完整线程计划、满订阅、打开 raw journal 与 persist 时才看得到。M1.5 看不到,M7 才看到又太晚(那时主机已经买了)。

**做什么**:

1. M3 交易所接入完成后,按需租 `c8g.4xlarge`(与 M1.5 同型、同 AZ;`[需授权]`,负责人执行;只放测试网 key),**按 `c16` 线程计划**用正式版安装:探针清单 `hosts/probe-c16.toml` 随每个正式版发布(MAC 只在运行期核对,租用新实例不必先发版),同时启动 `prod` 与 `sim` 两个实例;测试网 key 白名单加入探针的 EIP、用完撤销。装机步骤与清单归 [deploy](../deploy/README.md)。
2. 6 个产品线(三所 × 现货/永续)**满订阅** core 行情(BBO、逐笔成交、标记价、资金费),另加"压舱"深度连接;打开 raw journal 与 persist;`latency-probe` 的 `quote` 模式在测试网账户上下探针单(产生 `tick_to_trade` 与 `rep_to_order`),按"突发 / 平静"分层抽样(testing §8.2)。运行时长覆盖至少一个资金费结算整点(标记价与资金费集中推送的突发窗口)。
3. **另租几小时 `c8g.8xlarge`**(`[需授权]`),以 `c32` 探针清单(文件名归 deploy)按 `c32` 线程计划跑同样的负载一次,并在其上做 ENI-B2 拆分的 A/B(启用 / 不启用 ENI-B2 与核 28)。
4. 产出:各分段直方图(按事件加权的 `kernel_rx`/`ingest`/`feed_host`,`kernel_rx` 报上下界 + 探针的订单类分段);突发窗口内 BBO 的 `nic_to_kernel` p99(HW RX 戳不可用时用 §3.1 的替代测法);feed-bbo 的轮询节拍(启用 `epoll_pwait(0)` 前后);关键帧一次写完的停顿与关键帧后 1 ms 内的 `decide` p99;persist 滞后;内存与大页实际占用;`sim` 在非隔离核上的尾随滞后与同机干扰(核对项见 [hft-core](../apps/hft-core/README.md))。结论写 Agent Note,ADR 见 `architecture/2026-10-03-m3-end-probe.md`。

**据此决定**:

- **主机类**:`c16` 只在本探针达标(各分段不劣于硬线,`kernel_rx` 在 `c16` 上有可写的预算)且启用 `epoll_pwait(0)` 时保留为候选;否则 `c32`(默认)。宁可上更大档位,不砍首批 venue。首批下单产品线数(决定 `c16` 是否可行):策略研究后定(R8-12);在此之前 `c32` 默认、`c16` 条件候选的写法不变。`c16` 的 `kernel_rx` 预算在这里写进 [latency-budget §3](../docs/latency-budget.md)(c32 用 §3 的数字),`c16`/`c32` 的线程计划改动只改 [hft-core 线程计划](../apps/hft-core/README.md#线程计划)。
- **IRQ 拆分**:突发窗口内 BBO 的 `nic_to_kernel` p99 显著上升(阈值由本探针的 Agent Note 定;HW RX 戳不可用时,"回显对端 RTT 的 A/B"或"软中断排队时长"二者之一显著上升即算;`c8g.8xlarge` 上的 ENI-B2 A/B 是直接证据)→ 启用 `c32` 预留的第二块交易网卡 ENI-B2 与第二 IRQ 核(核 28):延迟敏感流(BBO、下单、用户流)留在 ENI-B(IRQ 核 1),批量流(深度、成交、标记价、REST)走 ENI-B2(IRQ 核 28);ENI-B2 只有行情与 REST,不进任何 key 白名单。线程计划与清单 `[eni_b2]` 的唯一归属是 [hft-core 线程计划](../apps/hft-core/README.md#线程计划) 与 [deploy](../deploy/README.md)。
- **硬线**:`rep_to_order` 的硬线(现为 35 / 110 µs)可按本探针重定([00 §4.2](00-目标与延迟预算.md))。

**成本**:`c8g.4xlarge` 与 `c8g.8xlarge` 各按小时租几小时,量级几十美元(§8)。

### 4.1 累计门槛 ③④ 在服务器上跑(R8-10)

- **服务器仍不编译**:CI 在 `ubuntu-24.04-arm` 上构建验证包 `hft-verify-<ver>-aarch64.tar.zst`(+ `.sha256`,Release 资产):每个 core 解码器目标一个 libFuzzer 二进制(固定 nightly + ASan)、`hft-dst`(`ci` 剖面的 DST 运行器)、`hft-verify` 驱动与初始语料;构建时为每个目标组求 `path_digest`(相关源路径的哈希)写进 `VERIFY.json`。何时出包、对哪些提交可以出包,唯一归属 [development.md 验证包工作流](../docs/development.md)。
- **运行**:`releasectl install-verify <ver>` 装到 `/opt/hft/verify/<ver>/`(不影响生产版本激活);`hft-verify.service`(oneshot)+ 定时器,用户 `hft-verify`,根级 `hftbatch.slice`(`CPUWeight=idle`)、`Nice=19`,OOM 时最先被杀;只装在主机清单 `verify = true` 的主机上;`ExecCondition=` 查护栏标志 `/var/lib/hft/guard/tripped`、窗口标志 `/run/hft/window/active` 与 `hft-core@prod` 联调实例;`hft-replay-verify` 运行时 archiver 与 pipeline 暂停(全部主机类,规则归 hft-core,实现在 deploy 主表)。状态在 `/var/lib/hft/verify/`,不联网;S3 备份由 journal-archiver 的 `files` source 上传;崩溃输入最小化后由人带回仓库做回归金样。单元参数唯一归属 [deploy](../deploy/README.md)。
- **在哪台服务器**:dev2 常态运行(护栏内、最低优先级,CPU 份额按 `hftbatch.slice` 的 `CPUWeight=idle` 让给旧系统,吞吐待 M3–M6 实测,[待测量 J7](待测量与待决定事项-2026-10-01.md));升级主机只在 M7 期间、门槛 ⑩ 的 7 天测量窗口之外运行;正式实盘开始后升级主机不再运行,后续版本的累计在 dev2 上继续。
- **计量与账本**(R8-11):③ 按子进程 CPU 时间计、单输入超时按 harness 内的线程 CPU 时间判定;受限主机上的 OOM/超时先记"疑似",由 CI 以默认限额对最小化输入复现,复现才按失败清零;`hft-dst` 与 fuzz 子进程的 SIGABRT/SIGSEGV 一律算失败。只有失败清零;漏跑不清零;运行记录与账本丢失时用 `hft-verify ledger rebuild` 重建。跨版本只累计 `path_digest` 与候选版本相同的运行(`hft-verify ledger show --candidate <ver>`)。**候选版本补跑**:开正式实盘所用的版本,其验证包本身必须按 testing 的补跑量再跑一次、零失败(计入累计)。账本规则唯一归属 testing §6.1,阈值在 testing §8,`hft-verify` 规格在 [tools](../tools/README.md),部署在 [deploy](../deploy/README.md)。
- 取代关系:原计划"③④ 按 CI 每夜累计、账本存 CI artifact、丢失按 artifact 历史重建、dev2 不跑 fuzz/DST"已被取代——按 Trading 仓库 8–9 月的实际用量推算,免费 CI 要 4–8 个月才攒得够。

## 5. 上线步骤(新子账户)

唯一归属 [runbooks/launch.md](../docs/runbooks/launch.md)。要点:

1. 开通新子账户:交易 key 无提现权限 + IP 白名单(升级主机的 prod 出口 EIP);登记交易所账户 UID——hft-core 启动对**每把**交易 key(Ed25519 会话 key 与 HMAC REST key 分别)查 UID,kill-switch 自检与 reconciler 启动同样查,不等于 `venue_uid` → 退出 2 + P0;核验账户配置(持仓模式、保证金模式、现货账户关闭借币——OKX `enableSpotBorrow = false`、Bitget 现货杠杆关闭——与 `VenueCaps` 要求一致)。
2. 在交易所设定永续杠杆(不超过 `RiskParams.max_perp_leverage_x100`,超过即 `ACCOUNT_CFG` 不符、禁开);hft-risk 从 `AccountConfigReport` 读实际杠杆。
3. 运营在 `RiskParams` 设定正式实盘的风险上限;**初始上限与"第一次放宽"的条件是上线签字记录里的必填数值**(不是门槛)。
4. 同参数先在 sim 实例的模拟账户上运行,报告无未解释异常。
5. **M7 → M8 切换**:清掉 hugetlbfs 上的测试网热段;journal-archiver 的 source 前缀在 M7 是 `hft-testnet`,S3 对象键带主机段(`<prefix>/<host>/<instance>/…`,dev2 与升级主机的同名实例不再撞键),消费者凭证同时覆盖 `hft/` 与 `hft-testnet/` 前缀;切换前先用 `journal-archiver check` 确认测试网小时全部提交、同前缀下没有 quarantine,再搬目录;正式主机启用 IMDS 锁定(只有 root 能访问实例元数据,冷进程用 `hft-cred-broker` 发放的短期凭证,preflight 检查"非 root 访问 IMDS 被拒")。同一步还要处理:kill-switch 先停、以正式配置重启(它只在启动时读目标表与 key);pipeline 中 prod 实例的配置与状态归档后重新生成;残留的停机标记归档;`verify` 开关只改 `host-local.toml` 的清单选择(同一发布内两份清单,不另发补丁版)。步骤与核对项唯一归属 launch D-23。
6. **零成交冒烟(D-smoke)**:用 Admin 专用的控制命令 `SmokeOrder{account, venue, inst, side, ttl_ms}`(需确认;OMS 以 `OrderFlags::SMOKE` 建槽,只能是 PostOnly、离对手价 ≥ `smoke_far_bp`、最小名义,`ttl_ms` 到期由 OMS 自动撤单;Shadow/CloseOnly 下允许,走完整风控链,不计入任何策略),对每个(正式账户, venue)各挂撤一次;因为单在 OMS 槽里,交易所死手的刷新覆盖该 inst,所以死手的刷新与到期、kill-switch 对正式端点撤单、reconciler 连续两轮 `Ignore`、每把 key 的 UID 与 `ACCOUNT_CFG` 都能验证。原写法"网页手工挂单"测不到死手(OMS 不知道那张单)且会触发 `Recon`,已被取代(W4 P1-9)。不开仓,也不是一个实盘阶段;每月正式账户冒烟同样用它。正式账户的 kill 演练以 [incident-response](../docs/runbooks/incident-response.md) 为准(只在维护窗口、CloseOnly 下做零成交撤单冒烟,不 SIGSTOP 有仓位的 hft-core)。
7. **正式实例 Shadow 3–7 天(D-shadow)**:正式 `prod` 实例全部策略实例 `RunMode = Shadow`(决策照算、订单不发),打通真实保证金、资金费流水、用户流、对账与告警;与同参数的 sim 实例逐决策比对(`replayer compare --a <prod journal> --b <sim journal> --map <prod 账户>=<sim 账户> --out <dir>`),差异需解释。期间若做"决策不变的修复"(§4 ⑦),⑦ 不重新计时,D-shadow 重计 3 天。
8. 切 Live(前提含升级主机上满规模 ⑦ 复跑 ≥ 7 天,§4);正式实盘开始后同参数模拟账户继续并行校准。
9. 回退 = `Drain`:撤挂单、等全部链接与 IOC 终态、两腿对平后停。

ccex 用新子账户直接上线,不涉及接管旧仓位;"现货腿采纳入账"与迁移手册只在 cdex 迁移时需要。现有系统(cdex 旧框架、collector)不受影响。零成交冒烟与 Shadow 补上的是"正式端点上的撤单、死手、真实保证金、资金费流水、用户流在切 Live 前一次都没用过"这一缺口;真实撮合、成交与费用仍在切 Live 当日才第一次出现,由保守的初始 `RiskParams` 兜底([12 §3.1](12-风险与未决问题.md))。

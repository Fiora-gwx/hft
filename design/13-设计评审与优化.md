## 1. 结论

**方向可行,主干不改**:单热进程 + 单写者 sequencer + journal 即真相 + 冷进程只读尾部 + 控制环,Rust + Python,阶段一内核 TCP 不做 bypass,链上 chain-first + 多 builder——这些决定的证据链完整(research/01–06),与 LMAX / hftbacktest / Aeron 的公开形态一致,两人 + AI 能写得出来。

**但有 4 处会在实现时直接出错的工程问题(§2 的 P0),以及收益排序上的一个战略偏差(§4)**:我们现在的现金流(C/D 类)瓶颈是"机会数量与链上腿被抢跑",不是主机内微秒;9/29 复盘里正式账户资金利用率只有 15–20%,原因是没信号/没成交。微秒级栈的直接受益者(A/B 类)在 OKX/Bybit 迁东京后能否有边尚未证实(假设 A3)。所以**架构照做,投入顺序要改**:链上执行轨道与 AZ 搬迁前移,A 类先影子跑出 LeadLag 证据再加码。

## 2. 必须修正的问题

| # | 级别 | 问题 | 为什么会出错 | 修正 | 落点 |
|---|---|---|---|---|---|
| R1 | P0 | "每 tick 预加密到用户缓冲、触发时只剩一次 write"(03 §6 `prepare()`、05 §4.2) | TLS 1.3 每条记录用递增序号做 nonce;预先加密而不发送的记录无法丢弃——丢了连接就解密失败,发了就是多余的单。rustls unbuffered 的 `encrypt` 同样推进序号。**投机式预加密在 TLS 上不可能** | 预热只做到**明文帧模板填好 + WS 掩码**;加密代码路径用一个**独立的 scratch AES-GCM 上下文**每 tick 空跑一次保持 I-cache/分支预测热;真触发时对真实连接加密 ~300 B(≈ 0.1–0.2 µs)再 `write`。预算不变 | 03 §6、05 §4.2;note `no-speculative-tls-encryption` |
| R2 | P0 | 热 journal 放在普通文件 mmap 上(08 §2 "hugetlbfs 或普通 mmap") | 文件型 `MAP_SHARED` 页被内核回写后会重新写保护,下一次写触发 `page_mkwrite` 缺页;遇到 stable-pages 还要**等 I/O 完成**(ms 级)。这正是 sequencer 的 p99.9 杀手,且与"热路径零 fsync"无关——不 fsync 也会发生 | **热 journal 一律放 RAM**(hugetlbfs 或 tmpfs(`/dev/shm`)上的**具名文件**(不用匿名 memfd:它随进程退出释放,崩溃即丢),启动预触摸);由 housekeeping 核上的 **persist 线程**顺序复制到 NVMe/EBS 文件并 `fdatasync`,落后几毫秒。进程崩溃不丢(RAM 段仍在),整机掉电丢复制滞后的几毫秒到几百毫秒——与原设计同级 | 08 §1–2、§6;note `hot-journal-in-ram` |
| R3 | P0 | venue 线程同时做行情与下单(01 §3.2) | 队头阻塞:Gate 行情突发时 venue-gate 线程正在解密/解析一批帧,出环里的 Gate 订单要等这一批处理完——A 类的触发恰恰发生在行情突发时。p99 会被"对端所的行情量"决定 | **下单连接独占 gw 线程**(每个会下单的 venue 一个 `gw-<venue>` 线程,行情在 `feed-<venue>` 线程);48 核够用(6 所 × 2 + seq + 余量 ≈ 16 核)。只看行情不下单的 venue 保持单线程。gw 线程只轮询出环 + 下单连接回报,循环极短 | 01 §3.2–3.3、03 §3.2;note `dedicated-gateway-threads` |
| R4 | P0 | 定点数"i64 + 编译期 scale"(10 §4、07 §3) | 单一全局 scale 覆盖不了我们的品种:BTC 数量步长 1e-8、PEPE/SHIB 类数量 1e11–1e12、BSC 代币价格可到 1e-10。i64 固定 1e-8 数量上限 9.2e10 会溢出;固定 1e-9 价格对 1e-10 代币只剩个位精度;名义 = px × qty 直接 i64 相乘必溢出 | **按资产(SymbolGroup)定指数**:同一资产在所有 venue 用同一 `px_exp/qty_exp`(跨所比较零换算),写在 refdata 里;交易所的 tick/lot 是该指数下的整数步长;名义与 PnL 用 **i128** 或 USDT 1e-6 的 i64;链上 wei 用 U256,进入 sequencer 时按资产指数换算一次 | 07 §3、10 §4;note `per-asset-fixed-point` |
| R5 | P1 | 事件头定义两处不一致:01 §5 `EventHeader` 32 B(含 seq/kind/venue/inst/三个时间戳)vs 08 §2 `RecordHeader` 24 B(len/kind/flags/seq/tsc) | 实现时一定会分叉成两套编码,回放与 Parquet 映射出错 | 统一为 **journal 记录头 24 B(`len,kind,flags,seq,tsc`)+ 事件体**;领域时间戳(`ex_ts, ex_send, hw_rx, rx_tsc`)在事件体里,`proc_tsc` = 记录头 `tsc`。唯一定义放 `hft/docs/subsystems/event-model.md` | 01 §5、08 §2;note `single-event-header` |
| R6 | P1 | 段头只记 `config_hashes[]` | 回放时需要的是配置**内容**;只有哈希就依赖外部文件还在、没被改——违背"状态 = f(日志)" | 启动与每次变更把 refdata/参数/风控参数的**完整 blob** 作为 `ConfigBlob` 事件写进 journal;段首快照也带当前 blob。journal 自足 | 08 §2、§5;note `self-contained-journal` |
| R7 | P1 | systemd `WatchdogSec` 心跳"来自 sequencer 主循环"(09 §4.2) | `sd_notify` 是 `sendmsg` 系统调用,违反热路径规则 | sequencer 只递增一个缓存行上的心跳计数;housekeeping 线程每 1 s 检查计数前进才 `sd_notify` | 09 §4.2 |
| R8 | P1 | Binance 合约"每连接 ≤ 10 个流 → 2–3 条连接赛马"(04 §5) | 官方文档是**每连接最多 1024 个流**;10 是**每连接每秒入向消息数**。另:2026 起 fstream 分 `/public`(高频:bookTicker/depth)、`/market`(markPrice/aggTrade 等)、`/private` 三条路由,不带路由的连接只收 `/public` | 行情双连接是为了冗余与赛马,不是流数限制;按路由拆连接:`/public` 主备 + `/market` 一条 | 04 §5 |
| R9 | P1 | 第一阶段 bsc-geth 与 hft-core 同机(01 §7、02 §2.2) | c7i.metal-24xl **没有实例存储 NVMe**,BSC 节点要 io2(贵)或 gp3(慢);且 geth 的 GC、压缩与内存带宽会污染同一颗 CPU 的 L3(8488C 单路 105 MB L3 共享),拖 hft-core 的 p99 | BSC 节点从第一天起放**同 CPG 的 i7ie/i4i**(本地 NVMe),与 hft-core 走 CPG 内网;若必须同机,用 Intel RDT/CAT(resctrl)给热核划 L3 份额(阶段 0 验证 metal 上可用) | 01 §7、02 §2.3;note `separate-chain-node-host` |
| R10 | P2 | 所有策略都在 sequencer 线程里,包括每分钟的 ClosePolicy(分位数)、LeadLag 互相关、20 档 VWAP | 这些计算量大、周期性,会在 A 类触发的同一时刻占住 sequencer | 增加 **warm-compute 车道**:慢计算放在非热核的 advisor 线程,输出作为 `Advice{kind,…}` 事件进入 sequencer 的输入环并被 journal 记录(回放时从日志读,仍然确定);sequencer 里只留 O(1) 的比较与状态迁移;A 类用"预计算触发价"(每次 slow 所报价变化时算出 fast 所需要到达的价位,tick 到来时只做一次整数比较) | 01 §3.3、07 §2;note `warm-compute-lane` |

## 4. 收益排序与路线图调整

测得的收益大小(00、02、03、research/01/05):

| 杠杆 | 可省 / 可得 | 依赖重写吗 |
|---|---|---|
| 搬到交易所所在 AZ/spine | 0.5–1.5 ms RTT | **不依赖**——现有系统就能搬 |
| 链上腿:自建节点 + 块流 + 多 builder 直投 + 生命周期状态机 | 包含 1.3 s → 0.5 s,抢跑率 80% → 目标 < 30% | **不依赖 hft-core**——chain-core 是外部 venue |
| 双腿间隔(LegLink) | 数百 ms → µs | 依赖 hft-core |
| 主机内 µs 栈 | 50–150 µs 尾部 | 依赖 hft-core |

修订(已写回 [11](11-实施路线图.md)):

1. **阶段 0 顺手把现有系统搬到胜出 AZ**(探测完成后第 2 周),不等新栈——第一笔、最便宜的 0.5–1 ms。
2. **链上轨道从第 3 周并行启动**(第二名工程师):bsc 节点、块流、多 builder 直投、tx 生命周期、nonce 分配器先做成 chain-core,**第一个客户是现有 Python cdex**(通过本机 Unix socket 的临时接口提交 swap、拿回 TxLifecycle)——链上抢跑问题最早得到改善,假设 A4/A5(包含率、builder 自营抢跑)最早得到数据;第 12 周后再切到 hft-core 的外部 venue 协议。
3. **阶段一范围收窄**:Binance 合约 + Gate,策略 C(Carry)实盘、A(CrossTaker)**只影子**(积累 LeadLag 证据);回放只做验证模式;hftbacktest fork(假设模式)移到阶段二。阶段一从 6 周延到 8 周(第 3–10 周)——原排期对两个人偏紧。
4. **A/B 类加码(m8azn bake-off、Onload、更多 venue 的 µs 优化)以 LeadLag 实测为触发条件**,不按日历推进。

## 5. 组件化决定

判断标准(与 DSH 的"要有当前所有者与需求"一致):**有独立的不变量要测、有 ≥ 2 个使用方、或需要单独的延迟基准**,才成为 crate;只是装配、线程布局、配置解析的,留在 app 里。

| 层级 | 组件(crate / 进程) | 为什么独立 | 不做成组件的 |
|---|---|---|---|
| 纯基础 | `hft-types`(定点、ID、枚举)、`hft-event`(事件与命令定义、schema 导出)、`hft-refdata`、`hft-book`、`hft-amm`、`hft-ledger` | 无 I/O,实盘/回放/mock/PyO3 共用;各自有属性测试与基准 | 单独的 `clock`、`ring`、`control` crate(并入 `hft-rt` 与 `hft-event`,体量太小) |
| 运行时 | `hft-rt`(环、TSC、绑核、大页、自旋)、`hft-journal`、`hft-net`、`hft-venue`(venue 运行时) | 热路径原语,需要独立微基准与 `unsafe` 审计 | 每个 app 自己的线程装配 |
| 交易所协议 | `venue-binance`、`venue-gate`、`venue-okx`、`venue-bybit`、`venue-bitget`、`venue-kucoin`、`venue-hyperliquid` | 纯协议,金样 + fuzz;按阶段逐个建 | 通用 "exchange SDK" 层(不做) |
| 决策 | `hft-oms`、`hft-risk`、`hft-strat-lib`、`hft-strategies`、`hft-sequencer` | 各自的状态机与属性测试;sequencer 是唯一装配点 | 策略插件动态加载(不做,编译期 enum) |
| 链上 | `hft-chain-evm`(L0 镜像、revm、bundle、nonce、builders、生命周期)、`hft-chain-solana`(阶段三) | 外部 venue;块级 | 独立的 "mev-sdk" |
| 控制/观测/工具 | `hft-ctl`(ctl-gateway + 客户端协议)、`hft-telemetry`、`hft-sim`(阶段二)、`hft-py`、`hft-testkit` | 冷路径复用、测试基建 | tracing 框架进热路径(不做) |
| 进程 | `hft-core`、`chain-core`、`journal-archiver`、`watchtower`、`reconciler`、`kill-switch`、`replayer`、`mock-exchange` | 每个都有独立的故障域或部署节奏 | 单独的 metrics-exporter / risk-monitor 进程(合并进 watchtower) |
| Python | `pipeline`(名单/池子/成本线/参数)、`ops_bot`、`research`、`treasury` | 慢路径、老板工作流 | Python 出现在任何事件级路径 |

## 8. 这次评审没有改的判断(并说明为什么)

- **不引入 C++、不做 DPDK/AF_XDP/Onload-on-ENA**:证据未变(03 §4)。

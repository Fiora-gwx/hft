# 03 · 网络与传输层

> **实现以 [`hft/`](../README.md) 规格为准,本章是设计证据;冲突处以 hft 为准。** socket 选项、收包循环与连接管理归 [hft-net](../crates/hft-net/README.md) 与 [hft-venue](../crates/hft-venue/README.md),运行期调优归 [deploy](../deploy/README.md),热路径规则归 [hot-path-rules](../docs/hot-path-rules.md)。2026-10-03(M0-d)起收包只用中断驱动一种模型(§3.1);同日 M0-e 起,承载 ≥ 3 个 socket 的行情线程每圈可 `epoll_pwait(0)`、TCP 短读即停,`c32` 预留第二 IRQ 核与第二块交易网卡 ENI-B2(§3.1、§3.2)。
>
> 依据:[research/01 网络/内核绕过/TLS](research/01-network-kernel-bypass-tls.md)、[research/05](research/05-hardware-hosting-os-tuning.md)。本章决定"字节如何进出机器":内核栈还是绕过、哪种轮询模式、TLS/WS/JSON 怎么处理、连接怎么管。

## 1. 预算的真相

Deltix/EPAM 在 AWS 东京对 Binance BTCUSDT 行情的 pcap 实测(2023):交易所事件时间 → 我们网卡 **p50 3.97 ms、p90 5.3 ms、p99 13.1 ms**。主机内核路径 50–100 µs 只占 2–3%。所以顺序是:

| 优先级 | 杠杆 | 可省 | 章节 |
|---|---|---|---|
| 1 | AZ / spine 放置 | 0.5–1.5 ms RTT(东京跨 AZ 1.54–1.87 ms,全球最慢 Region 之一) | [02](02-硬件与托管方案.md) |
| 2 | 独占物理核 + 内核调优 + 忙等 | 50–150 µs 尾部 | 02 §4、本章 §3 |
| 3 | 交易所侧专线 / 二进制协议 / WS 下单 | 交易所内部排队(ms 级,不可控部分最大) | [research/02](research/02-exchange-connectivity.md)、04、05 |
| 4 | 内核绕过(Onload/XLIO,仅裸金属) | ≈ 5 µs/单程 + 抖动降 6 倍 | 本章 §5 |

**AWS 上的地板是 fabric,不是软件**:同 AZ + CPG 的 m8a.metal 内核 UDP RTT p50 20.7 µs / p99 24.1 µs,DPDK 路径反而 25.6 / 28.2,AF_XDP 零拷贝 32 / 37;AWS 自己的结论是"虚拟化 ENA 上每跳 ≈ 23 µs 由 NIC/hypervisor 决定"。这就是基准形态**不做任何 bypass** 的定量依据。

## 2. 分段成本(调优后的内核栈,metal)

| 段 | 中断驱动 | 忙轮询 | 可选:裸金属 + Onload |
|---|---|---|---|
| NIC DMA → socket 队列 | 5–15 µs | **1–3 µs** | ≈ 1 µs |
| `read()` 返回 + 拷贝 | 0.5–2 µs | 0.5–1 µs | ≈ 0.3 µs |
| TLS 记录解密(2 KB) | 0.26 µs(x86 aws-lc-rs 7.95 GB/s)+ 0.1–0.3 µs 固定 | 同 | 同 |
| WS 解帧 + JSON | bookTicker 300 B ≈ 0.2–0.5 µs;depth 2 KB ≈ 1.5–3 µs(sonic-rs) | 同 | 同 |
| 环 + sequencer 取出 | 0.1–0.3 µs | 同 | 同 |
| 簿 + 策略 + 风控 + OMS | 1–5 µs | 同 | 同 |
| 模板填充 + TLS 加密 + `write()` → NIC | 3–6 µs(LLQ) | 2–4 µs | 0.5–1 µs |
| **主机内合计(HW RX → 线上)** | 15–35 µs | **8–20 µs** | **5–10 µs** |
| C-state 退出 / 调度迁移 / tick | 10–200 µs 尾部 | 0(idle=poll + 隔离核 + 忙等) | 0 |

基准形态选的是**中断驱动**一列(§3.1),目标:主机内 tick-to-trade **p50 ≤ 22 µs、p99 ≤ 75 µs**(p99.9 只记录),其中 `kernel_rx` p50 ≤ 8 µs、p99 ≤ 20 µs(`c32`;`c16` 待 M3 末探针);硬线(验收下限)p50 ≤ 30 / p99 ≤ 100 µs,落在目标与硬线之间需 Admin 签字(在统一升级后的主机上验收,prod 与 sim 同机;分配待 M1.5 与 M3 末探针实测,唯一归属 [latency-budget §3](../docs/latency-budget.md),重定经过见 [00 §4.1、§4.2](00-目标与延迟预算.md))。原目标 p50 ≤ 20 / p99 ≤ 60 / p99.9 ≤ 200 µs 是按上表"忙轮询"一列与 c7i.metal 估的,已被取代。可选:裸金属 + Onload(触发条件见 §5):p50 ≤ 8 µs、p99 ≤ 25 µs。

## 3. 基准形态:内核 TCP + 中断驱动收包,无运行时的自旋线程

### 3.1 轮询模式(按核数选择)

基准形态只用第一行;其余各行是调研证据或日后 A/B 的候选。

| 模式 | 做法 | 效果(公开数据) | 何时用 |
|---|---|---|---|
| **中断驱动 + 热线程自旋读(默认,唯一)** | ENI-B 全部队列的 IRQ/NAPI 在一个**专用 IRQ 核**(升级主机类的核 1,不放线程)完成;热线程绑隔离核,只做非阻塞 `recvmsg` 循环,不做 NAPI 轮询;承载 ≥ 3 个 socket 的 `Spin` 行情线程每圈可调用一次 `epoll_pwait(epfd, …, timeout = 0)`,只对就绪的 socket 调 `recvmsg`;TCP 短读即停;`net.core.busy_poll = 0`、`busy_read = 0`,ENI-B 的 `napi_defer_hard_irqs = 0`、`gro_flush_timeout = 0`,`adaptive-rx off rx-usecs 0`;conn-builder 建连时显式 `SO_BUSY_POLL = 0`;hostprobe 硬校验 | 中断路径 NIC → socket 5–15 µs(§2,metal 数字;Graviton 待 M1.5);`kernel_rx` 分配 p50 ≤ 8 / p99 ≤ 20 µs(`c32`) | 所有升级主机类(dev2 只有一块网卡,同样不开 busy poll) |
| 专核 busy poll(已否决) | 热线程 `SO_BUSY_POLL` + `SO_PREFER_BUSY_POLL` + `SO_BUSY_POLL_BUDGET`;`napi_defer_hard_irqs=2`、`gro_flush_timeout=200µs` 让 IRQ 在轮询期间保持屏蔽 | LWN:中断 p99 21.1 µs → 独立核轮询 14.0 µs | 不用:热线程会替同一队列上全部 socket(含同机 sim)做 NAPI 轮询;一时没人轮询时包最多等 200 µs;与 IRQ 在专用核的规格互相矛盾([00 §4.1](00-目标与延迟预算.md)) |
| threaded NAPI busy poll | `echo 2 > /sys/class/net/<eni>/threaded`(6.17+),NAPI 内核线程钉核 | p99 13.0 µs,比用户态自旋再低 1–1.5 µs | 内核 ≥ 6.17 后 A/B(需要专门的 NAPI 核) |
| epoll + IRQ suspend | `EPIOCSPARAMS{prefer_busy_poll, budget, usecs}`(6.9)+ per-NAPI `irq-suspend-timeout=20ms`(6.13) | memcached:基线 p99 416 µs @26% CPU → 141 µs @32% CPU(全自旋 133 µs @100%) | 核不够时的省电折中(冷进程、探针机) |

收包不按连接导核:ENI-B 的全部 IRQ 都在 IRQ 核,热线程在哪个核都一样读 socket。原设计"每条交易所连接经 RSS 源端口预计算或 ntuple 落到它的 feed/gw 线程所在核的队列,IRQ 钉同核或相邻核"已被 hft 取代;RSS 源端口预计算与 ntuple 降为可选 A/B(ENA 上 `ntuple-filters: off [fixed]` 的情况打镜像时验证)。sim 实例用独立的 ENI-C,IRQ 钉在 sim 的核上,所以 prod 的 IRQ 核也不处理 sim 的行情包。

**IRQ 单核的队头阻塞与拆分预留**(第四轮评审 W5 N-P1-1,R8-11):全部交易网卡流量在一个 IRQ 核上串行做软中断;Binance 深度(`@depth@100ms`)与标记价(`@markPrice@1s`)按固定节拍集中推送,BBO 包若与深度包落在同一队列就排在整批深度包后面(每包软中断成本按 1–2 µs 估,300 个合约的深度突发约 0.3–0.6 ms,待核实)。处置分三层:(1)首次上线的 core 行情不含全量增量深度(§3.5),突发只剩标记价、成交与资金费;(2)M1.5 用"压舱"深度连接做 IRQ 核空闲 vs 保持唤醒的 A/B,M3 末探针在满订阅下看突发窗口里 BBO 的 `nic_to_kernel`;(3)`c32` 线程计划**预留**核 28 作第二 IRQ 核、第二块交易网卡 ENI-B2(默认不启用),探针显示突发窗口内 BBO 的 `nic_to_kernel` p99 显著上升时启用:BBO、下单、用户流留在 ENI-B(IRQ 核 1),深度、成交、标记价、REST 走 ENI-B2(IRQ 核 28)。IRQ 核本身的卫生:加入 `rcu_nocbs`;hostprobe 检查 NVMe 等 managed IRQ 的 effective_affinity 不落在 IRQ 专用核;TASK_ON_HOT 检查覆盖 IRQ 核([02 §4](02-硬件与托管方案.md))。

**多 socket 行情线程的轮询节拍**(W5 N-P1-2,R8-11):`kernel_rx` 包含应用轮询节拍的等待。固定顺序对每个 socket 调一次 `recvmsg`,空闲一圈的成本随 socket 数线性增长——`c16` 原计划一个 feed-bbo 线程承载 12 个 BBO socket(现计划拆为两条,初值 4 + 8 个,[02 §2.2](02-硬件与托管方案.md)),一圈约 12–24 µs,平均多等 6 µs、最坏约 24 µs,`kernel_rx` 预算放不下。所以 T7 改为:承载 ≥ 3 个 socket 的 `Spin` 行情线程每圈可调用一次 `epoll_pwait(timeout = 0)`(约 0.5 µs,不阻塞、不唤醒任何线程),只对就绪的 socket 读;系统调用白名单同步。另外 BBO 路由每连接每次 poll 至多 `feed.bbo_frames_per_poll`(默认 8)帧,连接之间按帧轮转,另一个 venue 突发时 BBO 不再最多等 64 帧(约 96 µs);非 BBO 路由仍用 `feed.frames_per_poll`。规则归 [hot-path-rules](../docs/hot-path-rules.md) 与 [hft-venue](../crates/hft-venue/README.md)。

### 3.2 线程与 socket
- feed 线程 / gw 线程各是一个 OS 线程(下单连接独占 gw 线程,避免行情突发时订单排队,见 [13 R3](13-设计评审与优化.md));升级主机上 BBO 路由(`feed-bbo:<venue>`,BBO 主/备赛马)与深度/成交/标记价路由(`feed-md:<venue>`,单路)分属不同线程;gw 拥有下单主/备、用户流与 REST 连接;REST 快照(core 只有 BBO 补帧)连接归 warm 任务 `snap-fetch`,不在 feed 线程上;账户查询(保证金与配置的 REST 响应,最大约 50 KiB、解码 ≤ 120 µs)的解码移到 warm 任务 `acct-fetch`,结果经 `acct-<venue>` 环交回 gw(hft-venue 内部字节环,gw 再推入 `rep-<venue>`),解码不在 gw 线程上(W5 P2-2:解码期间新到的对冲单会被挡住,而 MarginNow 恰在保证金告急时触发)。固定顺序轮询,socket ≥ 3 的 `Spin` 行情线程每圈先 `epoll_pwait(0)` 只读就绪的 socket(§3.1);WS 只用 `tungstenite` 的帧头解析(其同步消息 API 每条消息分配,不用),payload 是接收缓冲的切片,`WouldBlock` 或短读即换下一条;**没有 tokio、mio、阻塞或带超时的 epoll 在热路径**(`timeout = 0` 的 `epoll_pwait` 是唯一例外;tokio 只在冷进程与启动期)。gw 的用户流连接每圈都 poll(Binance USDⓈ-M 的成交只从用户流来),每解出一帧回报就把出环排空一次,对冲单不排在整批回报之后。
- socket 选项:`TCP_NODELAY`;显式 `SO_BUSY_POLL = 0`;`TCP_QUICKACK` 默认不设(T11:有数据的读之后补设要多一次 `setsockopt`,≈ 0.2–0.5 µs,只有按角色 A/B 证明有收益才打开,原设计"每次读后都设"已被取代);`SO_TIMESTAMPING`(RX_HARDWARE\|RX_SOFTWARE\|RAW_HARDWARE;TX 软件时间戳是可选扩展,默认关,触发条件:升级主机直方图显示内核 TX 段值得单独测——打开时再加 TX_SCHED\|TX_SOFTWARE\|OPT_ID\|OPT_TSONLY,经 `MSG_ERRQUEUE` 由 warm 线程收;ENA 没有 TX 硬件戳);`SO_BINDTODEVICE`(prod 为 ENI-B,sim 为 ENI-C);connect 前 `bind` 预计算的源端口(可选 A/B);`SO_RCVBUF/SNDBUF` 适中(过大增加 worst-case)。
- 收包用 `recvmsg` 带 cmsg 拿时间戳;**短读即停**:TCP 非阻塞读返回的字节数小于缓冲即认为队列已空,先解帧,不再补一次空 `recvmsg`(原写法"循环读到 EAGAIN"每个数据事件多一次 0.8–2 µs 的空读,约占 `ingest` p50 预算的 25%,W5 P2-1);缓冲区固定、复用、大页;TLS 用 rustls **unbuffered API**(`UnbufferedConnectionCommon`)直接在我们的缓冲上解密,不经内部 `Vec`。
- 发送:整帧一次 `writev`;触发前该帧的明文模板已填好、WS 掩码已完成;**TLS 加密只在真正发送时对真实连接做一次**(TLS 1.3 记录序号即 nonce,预加密的记录无法丢弃),加密代码路径由 scratch 上下文每 tick 空跑保持热(可选扩展,默认关;[13 R1](13-设计评审与优化.md))。

### 3.3 TLS
- `rustls 0.23` + `aws-lc-rs`;x86 上 2 KB 记录 ≈ 0.26 µs,不是瓶颈;三大库差距 ≤ 20%。
- **握手比收发贵得多**(2026-10-01 在东京生产机实测:各所 TLS 握手 3–12 ms(不含 TCP 建连),加 WS 升级与登录约 10–30 ms;早前笔记里的 60–150 ms 未能复现,见 [现状测量](现状测量与升级分析-2026-10-01.md) §3.2):N+1 热备已完成 TLS + WS Upgrade(+ 会话登录)的连接;主备错峰轮换避开 24 h 强断与 300 连接/5 min 限制;TLS 1.3 会话票据复用;后量子 X25519MLKEM768 默认开(握手更贵,同样由热备掩盖)。
- 不用 kTLS(小报文无收益、失去用户态自旋控制)、不用网卡 TLS 卸载(ENA 无)。

### 3.4 WebSocket 与 JSON
- 关闭 permessage-deflate(所有所);若某所只给压缩流,`yawc` 单独测。
- WS 解帧零拷贝:payload 是接收缓冲的切片;控制帧在 venue 线程内答复。
- JSON:`sonic-rs` + 每消息专用结构体、字段借用、数字保留字符串 → 自写定点解析;先用固定偏移/`memchr` 取分派字段再选结构体。300 B ≈ 0.2–0.5 µs,2 KB ≈ 1.5–3 µs。
- **二进制行情**:首批交易所(Binance、OKX、Bitget)的 core 行情走 JSON;二进制通道都是可选扩展,触发条件是解析成本或时间戳精度成为瓶颈:OKX `/public-sbe` 随 OKX 接入时评估;Binance Spot SBE 是 Binance 现货 JSON 之外的可选通道;Gate spot SBE 随 Gate(optional)接入。各通道的事实:Binance Spot SBE(µs 时间戳、`bestBidAsk` 带 eventTime、diff depth 20 ms vs JSON 100 ms)+ FIX 下单/Drop-Copy;Gate spot SBE;OKX `/public-sbe`(bbo-tbt 登录即可,L2 逐笔需 VIP4);Bybit SBE 仅机构 MMWS;**Bitget 的 SBE 未在官方资料中找到(早前笔记有误,待核实)**;Binance 合约仍是 JSON。NeutK 实测 SBE 到达**不早于** JSON——收益是解析与精度,不是时间。Binance JSON 流加 `timeUnit=MICROSECOND`。

### 3.5 连接管理策略
| 事项 | 策略 |
|---|---|
| 行情 | BBO 路由每所 2 条同订阅连接赛马(`feed.bbo_conns` = 2),**feed-bbo 线程**按 `update_id` 去重先到为准(sequencer 只收去重后的事件);全部 BBO 连接都断过的 inst 经 snap-fetch 做 BBO 补帧(REST)。**首次上线的 core 行情**(R8-11)= BBO、逐笔成交、标记价/指数价、资金费,单路,在 `feed-md` 线程;全量增量深度与 REST 快照重同步是可选扩展(触发条件:某个策略需要全深度);需要深度时优先订阅分档快照流(`RouteKind::DepthTopN`,整替换、无序号链、无 REST 重同步,[04 §5](04-行情接入层.md))。原设计"L2 也双路去重是默认"已被 hft 取代,L2 双路合并降为可选扩展 |
| 下单 | 1 主 + 1 热备(已登录);切换 = 改指针;后台补备用 |
| 轮换 | 主连接在交易所连接寿命上限(如 Binance 24 h)前 `conn.rotate_margin_s`(默认 1 h)于无在途订单的时机切备;新备用连接错开 ≥ 1 h 建立(唯一归属 hft-venue ECF1 段 6) |
| 出口 IP | ENI-B 上多个私有 IP 各配 EIP;每条连接固定源 IP;拉宽按 IP 的连接/消息限速。同机的 `sim` 实例用独立的 ENI-C(私有 IP + EIP),它的交易所行情连接全部从 ENI-C 出,不占 `prod` 的按 IP 限速,收包也不进 ENI-B 的队列(R8-10) |
| 路由 | 公网 IP 直连,不经 NAT GW / TGW / PrivateLink;按 AWS `ip-ranges.json` 核对端点属性:Binance stream/WS-API/FIX/`*-mm`/`api1–api4` 与 Gate、INTX 是直连 EC2;`api.binance.com`、Bybit、Bitget WS、KuCoin WS、Hyperliquid API 走 CloudFront;OKX 全部 Cloudflare——**能选直连端点的一律选直连** |
| 探测 | 每条连接每 5 s 一次 ping/pong,记录 RTT 进直方图;p99 突增 → 切备。**BBO 连接**另每 `bbo_ping_ms`(1 000)发一次 WS ping,保证盘口安静时也有回帧:报价新鲜度按连接健康判定(连接 Live、未在重同步、最近任一帧——数据、pong、心跳——距今 ≤ `conn_liveness_ms` 2 000),不按"该 inst 最后一次变化"([05 §3](05-CEX执行层.md)) |

## 4. 明确不做(基准形态)

| 技术 | 原因(2026-09 证据) |
|---|---|
| DPDK | ENA PMD 路径 RTT 反而比内核高(25.6 vs 20.7 µs);要自写 TCP+TLS+WS;占核;WC 补丁 |
| AF_XDP | 零拷贝需 GitHub 驱动 ≥ 2.13、队列 ≤ 一半、MTU ≤ 3498;仍要用户态 TCP/TLS;AWS 实测 32/37 µs 不如内核 |
| Onload-on-ENA | issue #337(2026-08)栈分配失败;#139 能跑但更慢(42.7 → 47.9 µs,max 137 → 241);需补丁驱动 + 补丁 Onload + 2 ENI + 失去 HW 时间戳 |
| ENA Express / SRD | 仅同 Region 实例间且双端开启;轻载中位数 +数十 µs;AWS 明说 HFT 很少适用 |
| kTLS / NIC TLS 卸载 | 小报文无收益 |
| smoltcp / F-Stack / mTCP 用户态栈 | 客户端 TLS+WS 生产级方案不存在;ARM64 更无 |
| io_uring 运行时 | 少连接单核时延迟高于 epoll(monoio 官方基准);自旋线程更简单更快 |

## 5. 可选:裸金属 + Onload(条件触发)

- 触发:某交易所提供 AWS 之外的接入(FIX 专线、跨连接),或基准形态证明 AWS fabric 抖动主导 p99。
- NIC:**AMD Solarflare X4522 + OpenOnload**(POSIX 透明,rustls/tungstenite 零改动,`EF_POLL_USEC` 自旋,板载 PTP;X4 比 X3/X2 平均延迟低 27%/43%,半程 ≈ 0.6 µs);备选 ConnectX-7/8 + XLIO(支持 Arm)。
- 收益上限(公开数据):Cloudflare 阶梯调优内核 25.7 → Onload 17.7 µs RTT,抖动 σ 8.6 → 1.4 µs;Deltix 撮合引擎 p50 78 → 32 µs、p99 243 → 99 µs。
- **前提**:Onload 无 aarch64 → 启用时需要 x86 剖面(`metal` 主机类);基准形态的发布目标是单一 `aarch64`(`target-cpu=neoverse-v1`),x86 构建、SIMD 路径与 `target-cpu` 只随 `metal` 剖面引入。
- ef_vi/TCPDirect 直通只在 Onload 透明模式仍不够时考虑(需几百行 `unsafe` FFI,收益再 1–2 µs)。

## 6. `net` crate 的接口(供 04/05 使用)

下面是原始设计草图,只说明形状;真实接口(`Conn`、`Connector`、`ConnRole`、`Timestamps`、`TxStamp` 等)以 [hft-net](../crates/hft-net/README.md) 为准,连接池与主备切换在 [hft-venue](../crates/hft-venue/README.md)。

```rust
pub struct Conn { fd, tls: rustls::UnbufferedClientConnection, ws: WsCodec, rx: Ring<u8>, tx: Ring<u8>, ts: Timestamps, id: ConnId }
impl Conn {
    /// 非阻塞:读尽 socket,解密到 rx,返回完整 WS 帧的迭代器(借用 rx),每帧附 hw_rx_ns/rx_tsc
    fn poll_frames(&mut self) -> Frames<'_>;
    /// 对已填好、已掩码的明文 WS 帧做一次 TLS 加密并写出;返回 sent_tsc;不阻塞
    fn send_frame(&mut self, frame: &MaskedFrame) -> Result<u64, SendErr>;
    /// cache warming:用 scratch 密钥上下文加密同长度的假帧到丢弃缓冲,不触碰真实连接的记录序号
    fn warm(&mut self, frame: &MaskedFrame);
}
pub struct ConnPool { primary, standby, warming: Vec<Conn>, rotate_policy }
```

- 所有缓冲预分配于大页;`Conn` 无堆分配;错误聚合为位标志由 venue 线程在轮询末尾一次处理。
- `Timestamps` 记录 HW RX / SW RX / 用户 RX TSC / TX 调度 / TX 软件戳(ENA 无 TX 硬件戳)。

## 7. 验证方法

1. **十点分解**(AWS T1–T10):HW RX → 内核 RX(D2)→ 应用 RX(D3)→ 应用 TX(D4)→ 内核 TX(D5);目标 `kernel_rx`(D2+D3)p50 ≤ 8 µs、p99 ≤ 20 µs(`c32` 的分配,M1.5 与 M3 末探针实测后重定);`sw_rx` 常态记录,D2/D3 分开进生产直方图(不作门槛);`kernel_rx` 等含 PHC 端点的分段按 1 s 一条的 `ClockStatus` 插值换算,误差界 > 1 µs 的样本不进分位数([02 §5](02-硬件与托管方案.md))。门槛 ⑩ 用的 `kernel_rx`/`ingest`/`feed_host` 从 seq journal 对每条行情事件离线计算(按事件加权,[00 §4.2](00-目标与延迟预算.md))。
2. **M1.5 延迟探针**([11 §3.1](11-实施路线图.md)):先做 AZ 探测,再按需按小时租与 Binance 同 AZ 的 `c8g.4xlarge`,跑 hft-net + 一个 venue 的 BBO feed(主网公共行情)+ 简化 sequencer + gw(测试网下单)的纵切片,出 `kernel_rx`/`ingest`/`decide`/`egress` 直方图(HW 与 SW 戳分开);同时测"压舱"深度连接下的 `nic_to_kernel`、IRQ 核空闲 vs 保持唤醒 A/B、`calib_err_ns`、`net_poll_empty`、每包软中断成本、CNTVCT 频率,核实 c8g 的 HW RX 戳、PTP、ENA 队列数与 RSS。
3. **M3 末满订阅探针**([11 §3.2](11-实施路线图.md)):同型实例按 `c16` 线程计划、6 个产品线满订阅、打开 raw journal 与 persist,另租 `c8g.8xlarge` 按 `c32` 计划跑一次并做 ENI-B2 拆分 A/B;看突发窗口里 BBO 的 `nic_to_kernel`(HW RX 戳不可用时用替代测法)与 feed-bbo 的轮询节拍,据此选定主机类并决定是否启用 IRQ 拆分(ENI-B2)。
4. **mock 交易所回环**(可选扩展:wire 级 mock-exchange):同机或同 CPG 另一实例跑 wire 级 mock,测 t0→t4 全链路直方图,每夜跑。
5. **到交易所**:`ss -ti` minrtt、ping/pong RTT 直方图、HW RX − 交易所 `E` 分布(需 PHC)。
6. **每项内核参数 A/B 24 h**,以直方图为唯一裁判;同机 sim 的干扰用"2 小时一块、块内开/关顺序按种子随机、按块配对、bootstrap 置信区间上界判定"加 softnet 计数对比实证(判定唯一归属 testing §8.2)。

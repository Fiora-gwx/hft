# 交易系统重建 · 整体工程架构设计(v2)

> 2026-09-29 起草,2026-10-02 第八轮修订,2026-10-03 按 M0 独立评审做第八轮第二次修订([13 §15](13-设计评审与优化.md)),同日按第二次独立评审做第三次修订([13 §16](13-设计评审与优化.md)),又按五路独立评审做第四次修订(M0-d,[13 §17](13-设计评审与优化.md)),再按第四轮五路评审做第五次修订(M0-e,[13 §18](13-设计评审与优化.md)),最后按第五轮五路评审做第六次修订(M0-f,[13 §19](13-设计评审与优化.md)),再写定各组件的测试规格(M0-g,[13 §20](13-设计评审与优化.md)):两者合并后冻结为**设计基线 v1**,此后只走实现驱动的变更。**实现以 [`hft/`](../README.md) 规格为准**;本目录是设计证据,冲突处以 hft 为准。从零重建的交易系统,首要服务 CEX-CEX(组合携带等)策略,CEX-DEX 与其他延迟敏感策略可接入。目标按优先级:**延迟**(p50 / p99 做到我们能控制的极限)→ **正确性**(不留裸腿、账本与交易所一致、可回放)→ **可扩展**(新增或修改策略不改引擎)。

## 一页结论

1. **钱花在哪**:我们 3–5 ms 的 tick-to-trade 里 90% 以上在交易所内部与东京 AWS 的跨 AZ 网络,主机内核路径只占 2–3%。所以顺序是:**先搬到交易所同 AZ 同 spine 的实例(省 0.5–1.5 ms),再把主机内做到 10–20 µs(省 50–150 µs 尾部),再接交易所专线/二进制协议,最后才是内核绕过(≤ 5 µs/单程,且 AWS 上不可行)。**
2. **形态**:每台机器一个 Rust 热进程,**绑核忙等线程 + 单写者顺序化事件日志 + 确定性状态机**(LMAX / Jane Street / Optiver 的公开形态);行情、回报、命令、定时器全是事件,状态 = f(日志),昨天的日志今天重放必须逐字节一致。慢的一切(落盘、指标、Telegram、Python 研究与选币)是只读日志尾部的冷进程,只能经一条带序号的控制环发命令。
3. **语言**:Rust + Python 两种;C 只以 FFI 形式出现(可选:裸金属 + Onload/ef_vi);不写 C++(没有任何证据显示 C++ 的 WS/TLS/JSON 栈快于 Rust 对应物,而内存安全对管真钱的系统是硬收益)。不采用任何开源交易框架作热路径;借鉴 hftbacktest 的 connector/bot 拓扑,其队列模型只作为模拟撮合的可选项。
4. **硬件**:基准形态是 AWS 东京的调优内核栈,主机类是部署配置(同一份 aarch64 二进制,只换线程计划与调优)。开发测试阶段新框架以 `dev2` 在现有 `c7g.large` 上运行(功能、正确性、交易所测试网/模拟盘联调与模拟账户;**不放正式实盘账户**;与 cdex 正式账户共机,受 CPU/内存护栏约束,cdex 优先,护栏只按资源信号停新框架;无延迟验收);延迟的第一份证据来自 **M1.5 延迟探针**(按需按小时租与 Binance 同 AZ 的 `c8g.4xlarge` 跑纵切片);大体没问题后**统一升级**主机,升级主机同时运行 `prod` 与 `sim` 两个实例(sim 只用非隔离核、独立 slice、独立网卡 ENI-C),档位**默认 `c32`**(`c8g.8xlarge`,32 vCPU/64 GiB),`c16`(首批下单 venue ≤ 4)只在 **M3 末满订阅探针**达标时保留,`c8` 只能承载 prod,档位由该探针选定,宁可上更大档位,不砍首批 venue;落在 AZ 探测(M1.5 之前做)选出的 AZ/CPG,三块 ENI(管理 / 交易 / sim,交易网卡的 IRQ 独占一个核;`c32` 另预留第二块交易网卡 ENI-B2 与第二 IRQ 核,探针显示软中断队头阻塞时启用),完整内核调优,在那里做延迟验收,然后才开始正式实盘。可选:`metal` 主机类 `c7i.metal-24xl`(x86、PTP 硬件时钟、48 独占核,$3.9k/月,RI $2.6k),`m8azn.metal-12xl`(5 GHz)与 `c8g.metal-24xl` 进 bake-off(触发条件见 02)。**colo 只在交易所迁出 AWS 时才做**——colo→AWS 公共端点 RTT 1–2 ms,永远输给同 AZ EC2。
5. **网络栈**:内核 TCP + 中断驱动收包(交易网卡的 IRQ 在一个独占核上完成协议栈处理,`busy_poll`/`busy_read` = 0,socket 显式 `SO_BUSY_POLL = 0`)+ 热线程绑隔离核自旋做非阻塞读(承载 ≥ 3 个 socket 的行情线程每圈可 `epoll_pwait(0)` 只读就绪的 socket,TCP 短读即停),无 tokio 于热路径;BBO 与其他行情分线程,REST(core 只有 BBO 补帧)与账户查询解码在 warm 线程上;首次上线的行情是 BBO、成交、标记价、资金费,全量增量深度是可选扩展(需要深度时用分档快照流);rustls(aws-lc-rs)unbuffered、tungstenite 同步、sonic-rs 专用结构体、i64 定点;N+1 热备连接掩盖握手与登录(实测 TLS 3–12 ms,加 WS 升级与登录 10–30 ms);首批交易所行情走 JSON,二进制通道(OKX SBE、Binance Spot SBE)是可选收益;凡有直连端点一律直连(避开 CloudFront/Cloudflare)。明确不做 DPDK / AF_XDP / Onload-on-ENA / ENA Express / kTLS(2026-09 的实测证据见 03)。
6. **执行**:意图 → 风控(几百 ns)→ OMS 订单槽状态机 → gw 线程填预编码帧模板、加密并 `writev`;策略可以直接下订单,也可以只给**目标仓位**,由执行层切片、协调两腿、对冲与补腿;多腿用 `LegLink` 在同一事件内完成第二腿(双腿间隔从数百 ms 到 ≤ 20 µs),按扣费后的净量对冲、对冲量有上限;开仓前查第二腿(所在 venue 可用、BBO 连接健康、资金够——永续按账户实际杠杆);报价新鲜度按**连接健康**判定(盘口不动不算过期),对冲腿超滑点改价而不判失败;两腿按较粗的 lot 对齐;断腿(Broken)持续 2 分钟自动做一次有界的"平掉多出的一腿",保证金 L3 与带平仓的 kill 也先减断腿组合的永续腿,另一所行情断开时照样先减永续(接受短时现货裸多 + P0),带平仓的 kill 加清仓锁;引擎减仓单的限价与名义按风控上限截取;WS 会话登录一次、不逐单签名;`Unknown` 是显式状态;死手开关 + 独立 kill-switch 进程;账户保证金按**到强平价的距离**分档(25% 禁开 → 15% 通知策略减仓 → 10% 引擎先减永续,待标定;"单边 +30%"压力用例必过),自身强平/ADL 成交入账(用户流断线期间漏掉的 ADL 由对账第二轮自动补入);人工在网页上成交后该 cell 进入 `manual_hold`,连自动补腿也停,不和人抢;资金费差异只告警、账本按交易所流水自动校正,不进启动闸门。老板在 ops_bot 是只读的 Viewer,唯一的写权限是"紧急停止" `/stop`(非 HARD kill:停开仓 + 撤挂单,对冲与平仓继续;确认只认同一人的预览;hft-core 不健康时经 kill-switch 撤单、经 polkit 停 hft-core 并 P0,恢复后自动补发 Kill,停机前另写持久标记,干净重启也不会自动恢复开仓;不能恢复)。
7. **范围**:新框架**首要服务 CEX-CEX**:首批交易所 **Binance、OKX、Bitget**(各接现货 + USDT 本位永续;一个账户在同一交易所只用一个市场,**不做同所现货 × 永续**),首个策略是**组合携带**(永续空 × 现货多,两腿在不同交易所,以老板的 portfolio-arb 为雏形);交易所差异由能力表 `VenueCaps` 表达,策略代码不出现交易所名字。cdex 继续在旧框架运行,迁移不急;**链上全部转为可选**(chain-core free profile、SwapGuard、builder profile、Solana 的设计保留在 06,外部 venue 协议不删,cdex 迁移时启用)。
8. **策略与工程解耦**:一策略一 crate(`strategies/<name>`),只依赖稳定的策略 SDK;策略包 = 快速部分(sequencer 里的纯状态机,无 f64)+ 慢速部分(advisor 线程里的 `Model`,输出不透明 `Advice` 进 journal)+ 参数 schema(配置工具、控制协议、ops_bot 按 schema 通用处理);策略的 Note 码表、报表字段、人工命令(`StrategyCmd`)、冷启动预热数据(`InjectWarmup`,作为 Input 进 journal)都走通用出口,Model 检查点不随改参数与发版失效。**新增或修改策略不改任何引擎 crate**,装配处加一行;由依赖方向检查、doc-check 与"新增第二个测试策略引擎 diff 为零"的 CI 门槛保证。引擎负责全账户硬约束(限额、kill、保证金、裸腿、限速、对账、交易所能力),策略负责进出场与止损。
9. **不做回测,做模拟**:回测一定不准;策略在**模拟账户**上以实时行情 + 模拟撮合运行(代码与实盘相同,回报经同一回报环记入 journal,回放仍确定),可多个模拟账户并行比较参数;正式实盘开始后同参数模拟与实盘并行校准。模拟始终在独立的 sim-only hft-core 实例(不持交易所 key;每个研究中的策略预置 2 个模拟实例):`dev2` 上长期运行,升级后与 `prod` 同机但不占 prod 的热核。pipeline 在实盘账户上也自动下发(中性),人工覆盖项按实例分开,模拟实例上的试验不会流到实盘。确定性回放(`replay verify`)只用于正确性与排障。
10. **数据**:raw journal(原始报文)+ seq journal(归一化事件与决策;链上启用时另有 chain journal);**热段在 RAM(hugetlbfs/tmpfs),独占的 persist 线程持久化到盘**;配置内容以 `ConfigBlob` 进 journal(自足);seq 段按 UTC 整点滚动且**强制带快照**(修正现有 WAL 84% 段被隔离;raw 段不要求自足),段内每 5 分钟在空闲轮一次写完一个关键帧;冷进程转 Parquet/S3,DuckDB/Polars 研究,ClickHouse 备选;PyO3 零拷贝给 Python。可观测:每事件五个时间戳(含 ENA 硬件 RX 戳,另常态记录内核软件戳 `sw_rx`)、每订单八个;冷进程 hdrhistogram;延迟验收的**硬线是验收下限**(主机内 tick-to-trade p50 ≤ 30 µs、p99 ≤ 100 µs,对冲路径"回报 → 下一单" `rep_to_order` p50 ≤ 35 µs、p99 ≤ 110 µs),基准形态(22 / 75、25 / 80 µs)是**目标**,落在两者之间需 Admin 签字,p99.9 只记录;行情类分段从日志按事件加权离线统计,时钟换算每秒校准、逐样本给误差界;p99 预算被突破自动告警并阻断发布。**测量先于优化。**
11. **交付方式**([11 交付计划](11-实施路线图.md)):按依赖的里程碑 M0 规格修订 → M1 地基 → (AZ 探测)→ **M1.5 延迟探针** → M2 决策核心 → M3 交易所接入(末尾**满订阅探针**定档)→ M4 模拟系统 + 首个策略 → M5 运维 → M6 联调与模拟长跑(dev2)→ M7 统一升级与延迟验收 → M8 正式实盘,不设周次;**不设小额实盘**,只有模拟盘与正式实盘。代码在本机 `E:\hft`(`E:\trading` 之外),推到一个**免费 GitHub 组织**下的私有仓库(老板 = Read 角色;组织建好前只做本地提交),CI 是唯一的正式构建环境、只用免费的托管 runner(与旧项目一致:质量门 `ubuntu-latest`,aarch64 发布按 tag 在 `ubuntu-24.04-arm`;组织的 2,000 min/月由 hft 独享,额度规则与应急出包路径见 hft 的 development);长时间 fuzz/DST 门槛(③④)按累计量、只卡正式实盘,**在服务器上跑**:CI 构建验证包,dev2 以最低优先级运行;服务器只装制品、不编译。首个策略在**新开的交易所子账户**上,经三所测试网/模拟盘联调、dev2 上缩小规模的模拟账户 ≥ 14 天、升级主机上的延迟验收与满规模模拟复跑 ≥ 7 天,再做**零成交冒烟**(Admin 冒烟单命令 `SmokeOrder`)与**正式实例 Shadow 3–7 天**(都不开仓),然后开始正式实盘(初始风险上限与第一次放宽的条件写进上线签字记录);dev2 上另有机外看门狗盯升级主机(带维护静默;若 Binance 与 dev2 同 AZ,移到第三 AZ 的 t4g.nano);不接管旧仓位,一个子账户只绑定一个策略实例;cdex 迁移、链上、更多交易所、A/B 类策略、metal 都是可选扩展(可选组件的规格冻结)。

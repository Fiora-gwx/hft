# 01 · 总体架构

> **实现以 [`hft/`](../README.md) 规格为准,本章是设计证据;冲突处以 hft 为准。** 线程计划与主机类归 [hft-core](../apps/hft-core/README.md#线程计划),事件与记录布局归 [event-model](../docs/subsystems/event-model.md) 与 [journal-format](../docs/subsystems/journal-format.md);本章的示意结构只说明思路。
>
> 本章定义系统的逻辑结构:有哪些进程、哪些线程、数据怎么流、状态谁拥有、为什么这样切。硬件与托管见 [02](02-硬件与托管方案.md),网络细节见 [03](03-网络与传输层.md),各层的详细设计见 04–09。

## 1. 一句话架构

**每台机器一个热进程,热进程内部是"绑核忙等线程 + 单写者顺序化事件日志 + 确定性状态机"的 LMAX 形态;所有慢的东西(落盘、指标、Telegram、Python 研究、找币流水线)都是只读日志尾部的冷进程,只能通过一条带序号的控制环向热进程发命令。**

这是 LMAX / Jane Street / Aeron Cluster / Optiver 公开材料里共同的形态(见 [research/04 §5](research/04-oss-frameworks-and-patterns.md)),也是 hftbacktest 实盘拓扑(connector 进程 + iceoryx2 + bot 进程)的思路。我们不采用任何现成框架作为热路径(理由见 04 调研结论 1–3),但大量借用它们的子系统设计。

## 2. 设计原则(按优先级)

| # | 原则 | 含义 | 反例(现有雏形) |
|---|---|---|---|
| P1 | **热路径上只做必须做的事** | 无系统调用(除 send/recv)、无堆分配、无锁、无 async 运行时、无日志字符串格式化 | Python 引擎每 tick 走 `json.loads`、dict、asyncio |
| P2 | **单写者** | 每个数据结构只有一个写线程;跨线程只走 SPSC 环或 SeqLock | 多个 Python 进程各自持有仓位副本 |
| P3 | **日志即真相** | 进入状态机的每个事件先赋序号、写日志,再处理;状态 = f(日志);任何时刻可重放 | 状态散落在 `logs/*.json`、CSV、内存里 |
| P4 | **热冷分离、冷不碰热** | 冷进程只读日志尾部;命令经控制环进入,同样被日志化 | Telegram bot 直接改配置文件、启停进程 |
| P5 | **同一份策略代码跑实盘、模拟账户与回放** | 策略是确定的状态机:输入事件 → 输出意图;实盘与模拟账户只换网关,回放只换事件源 | 回测/研究用 1h 收盘价,执行用秒级 Quoter |

### 3.1 为什么是"每台机器一个热进程"而不是微服务

- 跨进程一跳(共享内存环)≈ 100–250 ns,跨线程一跳(SPSC ring)≈ 50–100 ns,两者都可以忽略;但**跨进程意味着两份状态、两套时钟、两套故障模式**。把行情簿、仓位、订单状态放在一个进程、一个线程(sequencer)里,是消灭一致性问题的最短路径。
- 例外只有两个,都属于 optional 的链上部分:**链节点**(Go 写的 bsc-geth,重 I/O、有 GC,必须隔离)和**跨地域**(Solana leader 73% 在欧洲,必须在法兰克福落一台)。它们都通过"外部 venue"协议接入 sequencer,对策略来说和内部 gw 线程没有区别。

### 3.2 线程按"角色 × venue"切:feed 线程与 gw 线程分开

- 首批 3 个交易所 × 2 个市场(现货、USDT 永续)≈ 6 组 venue,每组 1 条行情 + 1 条下单 + 1–2 条备用 ≈ 20 条连接;每条一个绑核线程太浪费核,所以**一个线程轮询同一角色的多条连接**(`tungstenite` 同步 API,`WouldBlock` 即换下一条),单线程内没有锁。
- **BBO 与深度不同线程**(2026-10-03 五路评审 V5 P0-3):同一个 feed 线程里 BBO 要排在深度突发(每条连接每轮最多 64 帧)、REST 快照解析(40–80 µs)和别的 venue 后面,突发时 BBO 最多等约 0.4 ms。所以同一 venue 拆成 `feed-bbo:<venue>`(只含 BBO 路由,可跨 venue 合并)与 `feed-md:<venue>`(成交/标记价/资金费,以及订阅时的深度)两个任务,升级主机上两者不得同线程;REST 的请求、解密与解析移到 warm 任务 `snap-fetch`(core 只做 BBO 补帧,增量深度启用时另做深度快照),解析结果经环交回;dev2 等小主机可以配 `routes = All`(同一任务),此时每处理完一条非 BBO 帧就 poll 一次全部 BBO 连接。规格归 [hft-venue](../crates/hft-venue/README.md)。
- **多 socket 的 BBO 线程**(第四轮评审 W5 N-P1-2,R8-11):`feed-bbo` 跨 venue 合并后一个线程可能轮询 4–12 个 socket,固定顺序逐个空读的节拍会吃掉 `kernel_rx` 预算;所以承载 ≥ 3 个 socket 的 `Spin` 行情线程每圈可调一次 `epoll_pwait(timeout = 0)`,只读就绪的 socket;BBO 路由每连接每次 poll 至多 `feed.bbo_frames_per_poll`(默认 8)帧、连接之间按帧轮转;TCP 短读即停([03 §3.1](03-网络与传输层.md))。
- **首次上线的行情范围**(R8-11):core 行情是 BBO、成交、标记价/指数价、资金费与 BBO 补帧;全量增量深度与 REST 重同步是可选扩展,需要深度时优先用分档快照流([04](04-行情接入层.md))。
- **下单连接独占 gw 线程**(`gw-<venue>`,只轮询出环 + 下单主/备连接的回报),行情在 `feed-<venue>` 线程。原因是队头阻塞:若同一线程既解析行情又发单,对端所的行情突发(恰恰是 A 类触发的时刻)会让出环里的订单排在一批帧后面([13 R3](13-设计评审与优化.md))。只看行情、不在该所下单的 venue 只有 feed 线程。
- 核预算(一角色一核的布局):6 组 × (feed-bbo/feed-md + gw) + sequencer + advisor + 余量,48 核的 metal 充裕。本书其他章节里的"venue 线程"泛指某 venue 的 feed 与 gw 线程。
- **线程计划数据化与主机类**:线程布局由配置 `[[threads]]` 决定——feed/gw/sequencer 等是可轮转的**任务**(`poll_once`/`step` 非阻塞、每轮有上限),同一线程按固定顺序轮流调用多个任务,连续空闲后按 `IdlePolicy`(`Spin` / `SpinThenPark` / `Park`)退让。**下单连接独占 `gw-<venue>` 线程(规则 T8)对所有主机类没有例外**:同一线程不同时解析行情与发单;核不够就换更大的主机类,不合并 feed 与 gw([M0b 独立评审 P1-11](_work/review-2026-10-03-M0b独立评审.md))。升级只换配置与调优,不改代码;deploy 的隔离核列表、`irqaffinity` 与各 slice 的 `AllowedCPUs` 由线程计划生成,不手写。核号表的唯一归属是 [hft-core 线程计划](../apps/hft-core/README.md#线程计划),这里只记原则:
  - **`dev2`**(现有 2 核服务器,与 cdex 正式账户共机):feed 任务合并为一个线程(`routes = All`)、sequencer 一个线程、联调窗口里每个下单 venue 一个 gw 线程;warm 任务分在几个不绑核的低优先级线程里(`ctl-gateway` + `conn-builder` + `snap-fetch` 一个,`sim-gw`、`advisor`、`persist`、`housekeeping` 各自一个);全部 `SpinThenPark`/`Park`,不隔离核、无大页、无延迟验收,并运行在限 CPU 与内存的 systemd slice 里(dev2 护栏,cdex 优先;hft-core 与批处理分属 `hft-core.slice` 与根级 `hftbatch.slice`)。原设计"warm 任务(含 sim-gw、advisor)合并成一个线程"已被 hft 取代:模型长步骤与阻塞 I/O 会推迟模拟回报与控制命令。
  - **升级主机**(prod + sim 同机,R8-10、R8-11):核 0 承担 housekeeping、系统服务与 ENI-A(管理网卡)IRQ;核 1 **独占** ENI-B(交易网卡)全部队列的 IRQ/软中断,不放任何线程;`c32` 另预留核 28 作第二 IRQ 核(第二块交易网卡 ENI-B2,默认不启用,M3 末探针决定);persist 与段预创建/回收独占一个非隔离核(不在 IRQ 核上,不与 advisor 同核);warm 线程(`ctl-gateway`、`conn-builder`、`snap-fetch`、`acct-fetch`)一核,advisor 另占一核;隔离热核上 `seq`、`feed-bbo-*`(只承载 BBO 路由)、`feed-md-*`、每个下单 venue 一个 `gw-*` 各占一核;sim 用自己的核与独立 ENI-C(IRQ 钉在 sim 的一个核),批处理与冷进程另占核。按这个原则,全部 6 个下单 venue 加 sim 同机需要约 28 个核,所以主机类**默认 `c32`**(`c8g.8xlarge`,32 vCPU/64 GiB);`c16`(首批下单 venue ≤ 4)只在 M3 末满订阅探针达标且启用 `epoll_pwait(0)` 时保留为候选;`c8` 只能承载 prod;档位由 M3 末满订阅探针选定,宁可上更大档位,不砍首批 venue([02 §2.2](02-硬件与托管方案.md)、[11 §3.2](11-实施路线图.md))。
- Binance 合约全量 `bookTicker` 峰值数千条/秒,TLS 解密 + `sonic-rs` 解析每条 2–5 µs,feed-bbo 核有充足余量;收包是中断驱动(IRQ 在独占的 IRQ 核完成协议栈处理,热线程只做非阻塞 `recvmsg`,[03 §3.1](03-网络与传输层.md))。

### 3.3 关键线程职责

| 线程 | 拥有的状态 | 输入 | 输出 | 禁止 |
|---|---|---|---|---|
| `feed-bbo-*` / `feed-md-*` | 本线程行情连接的 socket、TLS 会话、WS 解帧缓冲、原始报文日志(raw journal,自己是单写者);feed-bbo 另有 BBO 补帧状态,feed-md 在增量深度启用时另有重同步状态机 | 网卡;另收 `snap-<venue>` 环里的补帧/快照 | 归一化事件(定长记录,带 RX 时间戳)→ bbo 环 / md 环 | 访问簿/仓位;分配;阻塞;发 REST(归 snap-fetch) |
| `gw-*` | 本 venue 下单连接(主/备)、帧模板、限速令牌的发送侧计数 | 出环(`OutMsg`)+ 下单连接的回报 | 订单帧 → socket;回报事件 → seq 入环 | 修改订单状态(状态只在 sequencer);大块账户查询解码(移到 warm 任务 `acct-fetch`,结果经 hft-venue 内部字节环 `acct-<venue>` 交回 gw,再由 gw 推入 `rep-<venue>`,不直接进 sequencer,W5 P2-2) |
| `sequencer` | **全部业务状态**:所有簿、仓位与权益视图、挂单、执行层目标、风控计数器与 cap、策略快速部分的状态、seq journal | 入环(按优先级:ctl > 实盘回报 > bbo > advice > md > 模拟回报 rep-sim,每环每轮有上限,模拟每轮 ≤ `sim_max_per_round`(默认 32)条;md 逐条处理,每条之后查看 ctl/实盘回报/bbo 环头,非空先处理它们,md 每轮上限取 `md_levels_per_round`(4 096 档)与 `md_round_ns`(50 000 ns)先到者——BBO 最多等正在应用的那一条 md 消息;R8-11 起每处理完一条 BBO 或 advice 也查看 ctl 与实盘回报环头,对冲腿不再排在整批 BBO(≤ 128 条,最多约 77 µs)后面;md/bbo 循环中把下一个定时器到期时刻与当前 TSC 比较一次,到期即让位)+ 定时器(TSC 比较,不用系统定时器) | `OutMsg`(订单决定 + 元数据;帧模板在 gw 线程填)→ 对应 gw 或 sim-gw 出环;日志记录(含空闲轮里一次写完的关键帧,[08 §2](08-数据面与回放.md)) | 任何 I/O(除写 RAM 中的 journal 段) |
| `advisor`(warm 核) | 各策略包慢速部分 `Model` 的状态(打分与分配、长窗口分位、资金费统计、冲击曲线) | journal 尾部 | `Advice`(不透明载荷)→ advice 入环(被 journal 记录,回放确定) | 直接写 sequencer 状态;读系统时钟 |
| `sim-gw`(warm;只在 `sim` 实例里,dev2 与升级主机都一样) | 模拟账户的撮合状态(挂单、已吃流动性记忆、模拟余额与保证金) | Sim 账户的出环 + 实时行情(来源见 [hft-sim](../crates/hft-sim/README.md)) | 模拟回报 → 回报环(与实盘同一组事件,journal Input;优先级最低) | 持有交易所 key;占热核 |
| `ctl-gateway` / `conn-builder` / `snap-fetch` / `acct-fetch` / `housekeeping`(warm 核) | Unix socket 会话与鉴权;握手、登录与会话 key 身份核验;REST 连接(BBO 补帧,以及增量深度启用时的快照:请求、解密、解析);账户查询(保证金与配置的 REST 响应)的解码;watchdog 心跳、每 1 s 一条 `ClockStatus`、TX 软件时间戳 errqueue(可选扩展,默认关) | 冷进程命令;`snapreq-<venue>` 请求;`acctreq-<venue>` 请求与账户查询的 REST 响应;sequencer 心跳计数 | 控制环;登录好的连接交接给 feed/gw;`snap-<venue>` 补帧/快照;`acct-<venue>` 环(解码后的账户报告交回 gw,hft-venue 内部字节环,不进 sequencer);`sd_notify` | 进入热核 |
| `persist`(独占线程) | RAM 热段到冷副本的复制进度;段预创建与回收 | journal 提交游标 | NVMe/EBS 上的 journal 副本(`fdatasync`) | 与任何热任务或 housekeeping 同线程(`fdatasync` 与 `MAP_POPULATE` 会阻塞);升级主机上与 advisor 同核 |
| 冷进程 | 各自的派生状态 | seq journal 尾部(mmap 只读) | Parquet/S3、Prometheus、Telegram、命令 → ctl-gateway | 直接改热进程内存 |

### 3.4 一次跨所下单的事件路径(Binance bookTicker → OKX 下单)

```
 t0  网卡收到 Binance 帧(HW RX 时间戳,SO_TIMESTAMPING / ENA hw-ts);IRQ 与协议栈在独占的 IRQ 核上完成
 t1  feed-bbo 线程(非阻塞 recvmsg):TLS 记录解密 → WS 解帧 → sonic-rs 直解到 BookTickerMsg → 归一化为 Bbo 事件 → 写入 bbo 环
     同时把原始字节追加到 raw journal(不阻塞)
 t2  sequencer:从环取出 → 赋 seq_no → 追加 seq journal → 更新 bbo[inst_id] → 触发订阅了该 inst 的策略
 t3  策略快速部分(经 SDK 视图):读 bbo[binance:X], bbo[okx:X], 权益视图, params
       → OrderIntent{venue=okx, side, px, qty, tif}(或 TargetIntent → 执行层算出本次切片)
     风控(几百 ns):kill、模式与 cap、价格带、名义、仓位、速率令牌(带 LegLink 的开仓同时查两腿所在 venue)→ 通过
     OMS:分配 client_order_id、写入订单槽、产出 OutMsg → 出环
 t4  gw-okx 线程:取 OutMsg → 填预编码帧模板 + WS 掩码 → TLS 加密(≈ 0.1–0.2 µs / 300 B)→ write()
     →(可选扩展)记录 TX 软件时间戳(ENA 没有 TX 硬件戳)
 t5  OKX 回执经 gw-okx(用户流每圈 poll,每解一帧回报就 drain_out 一次)→ 回报环 → sequencer 更新订单槽/仓位
     → 策略收到 Order 事件 / 执行层推进;若是带 LegLink 的第一腿成交,第二腿在同一事件内出环(hedge_host)
```

主机内预算(t0→t4):基准形态(AWS 调优内核,中断驱动收包)目标 **p50 ≤ 22 µs、p99 ≤ 75 µs**,硬线(验收下限)30 / 100 µs(p99.9 只记录;对冲路径以 `rep_to_order` 验收,`hedge_host` 只记录;分配待 M1.5 与 M3 末探针实测,数字唯一归属 [latency-budget §3](../docs/latency-budget.md),判定归 testing §8.2);可选:裸金属 + Onload(触发条件见 [03 §5](03-网络与传输层.md))目标 **p50 ≤ 8 µs、p99 ≤ 25 µs**。详见 [00-目标与延迟预算](00-目标与延迟预算.md)(§4.1 记录了 2026-10-03 的重定,§4.2 记录了硬线与目标的关系)。

可选技巧(默认关;触发条件:升级主机上的直方图显示出环冷热差):Carl Cook 的 cache warming——gw 线程每 tick 把模板填充与 WS 掩码空跑一遍,加密路径用一个独立的 scratch 密钥上下文空跑保持热;sequencer 侧不空跑下单路径(会消耗限速令牌、破坏确定性)。**不能对真实连接预加密**——TLS 1.3 记录序号即 nonce,预加密而不发送的记录无法丢弃([13 R1](13-设计评审与优化.md))。

## 4. 状态所有权与一致性

| 状态 | 唯一写者 | 读者 | 同步方式 |
|---|---|---|---|
| 各 venue 的 L1/L2 簿、最新成交 | sequencer | 策略(同线程)、冷进程(经日志) | 同线程直接读;冷进程读日志重建 |
| 仓位、挂单、余额(引擎视角) | sequencer | 同上 | 同上 |
| 合约静态参数(tick size、lot、费率、限速) | 启动期加载为只读(`&'static RefData`);运行期 `ReplaceRefdata`(只有 Admin 经 cli)只把新 blob 记成 `ConfigBlob`,随后 Drain + 重启才生效 | sequencer、venue 线程 | 进程内不变,不需要同步;变更 = Drain + 重启([hft-refdata](../crates/hft-refdata/README.md))。原设计的"双缓冲 + 原子指针交换"热替换已被 hft 取代,降为可选扩展(触发条件:计划内重启的频率或时长成为运营负担) |
| 策略参数(按策略 schema 编码的 blob) | 控制环命令 → sequencer | 策略 | 命令被日志化,重放可还原 |
| 权益视图(各所现金、现货库存、永续持仓与保证金) | sequencer(`hft-ledger`) | 策略(经 SDK 视图)、冷进程(经日志) | 成交溯源(按净量);交易所推送与 REST 只做校验 |
| 执行层目标与进度 | sequencer(`hft-exec`) | 策略(经 SDK 视图) | 同上 |
| 模拟账户的撮合状态 | sim-gw | sequencer 只经回报环看到结果 | 回报是 journal Input,回放读日志、不重跑撮合 |
| 交易所视角真值(REST 查询到的挂单/成交/仓位/余额) | reconciler 冷进程 | sequencer(经控制环收到 `ReconcileReport`) | 差异按名义分级为 `Recon` cap(只平不开);启动闸门要求差异逐项放行 |
| kill 开关 | 任何冷进程(经控制环)或 sequencer 自身(风控) | 所有线程 | `KillWord`(全系统 `AtomicU32`,位布局归 hft-types;含按账户 HARD 位),gw 线程 send 前也检查 |

**没有任何状态被两个线程写。** 这一条消灭了雏形里"两个实例、多个 Python 进程各持一份仓位"导致的所有对账问题。

## 5. 事件模型

所有进入 sequencer 的东西都是 `Event`:journal 记录头(唯一定义,见 [08 §2](08-数据面与回放.md))+ 按类型的定长体。领域时间戳在事件体里,`proc_tsc` 就是记录头的 `tsc`([13 R5](13-设计评审与优化.md)):

```
(示意;布局与编号的唯一定义在 event-model 与 hft-event)
RecordHeader { len: u32, kind: u16, flags: u16, seq: u64, tsc: u64 }   // 24 B,tsc = sequencer 取出时刻
MarketHdr    { venue, account, inst, ex_ts_ns, ex_send_ns, hw_rx_ns, rx_tsc, sw_rx(常态记录), rx_empty_gap_ns, ... }
kinds: Bbo, L2Batch, L2Snapshot, Trade, Funding, MarkPrice, IndexPrice, Liquidation,
       OrderDecision, SendReport, OrderEvent(回执/拒绝/成交/撤单/改单/过期/结果未知…), PositionReport, BalanceReport,
       FundingSettle, ExternalFill, MarginReport, AccountConfigReport, ExecDecision,
       ControlCmd, CmdResult, ConfigBlob, ReconcileReport,
       Timer, ConnState, Advice(不透明载荷), StateSnapshot, LatencySample, Note, EngineClock, …
       ChainHead, PoolQuote, SwapDecision, TxLifecycle(链上,optional;编号段保留)
```

- **行情、回报、命令、定时器、连接状态**全部走同一条路,这是"状态 = f(日志)"能成立的前提。模拟账户的回报与实盘回报是同一组事件(按账户类型区分),同样是 Input。事件编号与分类的唯一定义在 [event-model](../docs/subsystems/event-model.md)。
- 定时器也是事件:sequencer 每轮循环比较 TSC 与最近的到期时间,到期就自己往日志里写一条 `Timer`,策略看到的是事件而不是系统时钟——回放时定时器来自日志,结果逐字节一致。
- 原始报文(TLS 解密后的 WS payload)另存 raw journal,由 venue 线程写;它不进 sequencer,但重放工具可以用它重跑解码器,验证"解码器变了结果是否变"。

## 6. 三条执行路径的差异

链上两列是可选扩展,cdex 迁移到新框架时启用。模拟账户对策略来说与 CEX 下单完全相同,只是出环进 sim-gw 而不是 gw 线程。

| | CEX 下单(WS) | BSC 链上(optional,free profile) | Solana 链上(optional) |
|---|---|---|---|
| 网关位置 | hft-core 内 gw 线程 | 与 hft-core 同机的 chain-core(外部 venue,cold tier) | fra-sol 上的 chain-core(外部 venue,跨洲) |
| 触发→发出 | ≤ 20 µs(主机内) | 最新块公共 RPC 预检 ≈ 40 ms + 签名 < 0.1 ms + 同一字节并发投 K 个独立运营商(可选 builder profile:≤ 2 ms,L0 + revm + 多 builder 并发) | ≤ 5 ms(本地报价 + 构造 + Jito/SWQoS 双路) |
| 发出→确认 | 1–5 ms(交易所内部) | 出块 0.45 s,包含块数只报告;终局 1.1 s | processed ≈ 0.4–1 s,finalized ≈ 12.8 s |
| 失败语义 | reject 明确 | INCLUDED_REVERTED(失败交易上链只花 gas)/ DROPPED(`maxBlock` 过期)/ UNKNOWN(继续问) | err!=null / blockhash 过期 / UNKNOWN |
| 与 CEX 腿的顺序 | 双腿同时或按信号顺序 | **chain-first**:包含证据 → 立即 CEX 对冲 | 同左 |
| 状态回传 | 同进程 | 共享内存 SPSC 环(同机;跨机 UDP 为可选) | 紧凑 UDP/TCP 消息,东京↔法兰克福 ≈ 120 ms 单程 |

链上路径详见 [06](06-链上执行层.md)。

## 7. 部署形态(逻辑)

| 主机 | 角色 | 热核数(建议) | 关键依赖 |
|---|---|---|---|
| tokyo-cex | hft-core `prod` + hft-core `sim`(同机,sim 只用 warm/cold 核)+ 冷进程(+ chain-core,optional:bsc free profile,cold tier,不占隔离核) | 按主机类的线程计划:`dev2` 合并 feed、gw 仍独占线程;升级主机(默认 `c32`,`c16` 有条件,M3 末探针选定)prod 的 seq、feed-bbo-*、feed-md-*、每个 gw-* 各占一个隔离核,ENI-B 的 IRQ 独占一核(`c32` 预留核 28 给 ENI-B2);可选 `metal` 同样原则,warm/housekeeping 2–4 核,其余给内核/冷进程 | 与 Binance 同 AZ;硬件 RX 时间戳(c8g 上 M1.5 核实) |
| tokyo-chain(可选扩展) | bsc-geth + chain-core(bsc,builder profile) | 节点 8–16 核 + chain-core 2–4 隔离核 | 本地 NVMe ≥ 4 TB(i7ie/i4i);与 tokyo-cex 同 CPG |
| fra-sol(可选扩展) | Solana RPC 节点 + chain-core(solana) | 节点 16–32 核 + chain-core 2 核 | 512 GB–1 TB 内存 |
| research | 存储、研究与报告分析、看板 | 任意 | S3/Parquet、ClickHouse |

硬件选型与 AZ 验证见 [02](02-硬件与托管方案.md)。链上启用时,chain-core(free profile)不需要自建节点,与 hft-core 同机、cold tier(不占隔离核),经共享内存环连接。**BSC 节点(可选扩展)放独立的本地 NVMe 实例(同 CPG)**:c7i.metal 没有实例存储,且 geth 的 GC/压缩会污染同一颗 CPU 的 L3([13 R9](13-设计评审与优化.md));chain-core 经 CPG 内网读节点。

**账户是一等维度**:`AccountId` 进 OMS、风控与 ledger,各自限额、各自 kill(可按账户 HARD)、各自 API key;一个账户(可跨多个交易所的子账户)只绑定一个策略实例,**在同一交易所只用一个市场**(现货或永续;refdata 加载时校验 `SameExchangeMarkets`,理由见 [07 §1](07-策略层.md))。账户有两种类型:`Live`(真实交易所子账户,启动时核验交易所 UID 与账户配置)与 `Sim`(模拟账户,订单进 sim-gw,不持有 key)。ccex 策略用新开的子账户上线,不接管旧仓位;一个交易所子账户只由一个系统、一个策略实例交易(见 [11 交付计划](11-实施路线图.md))。新版本验证 = `replay verify` + 模拟账户。

**实例与模拟账户放在哪**(R8-9):不设小额实盘阶段,只有模拟盘与正式实盘。模拟始终在独立的 sim-only hft-core 实例运行(`instance = "sim"`,refdata 只含 Sim 账户、不加载任何交易所 key、自己的行情连接与 journal);实盘实例(`instance = "prod"`)不含 Sim 账户。同一二进制;sim 实例不交易任何交易所账户,所以不违反"一个账户只由一个系统交易"。

- `dev2`:长期运行 `sim` 实例;交易所测试网/模拟盘联调时另起一个 `prod` 角色实例,指向测试网端点、只持测试网 key、refdata 只含测试网账户,只在联调窗口运行。**dev2 不放正式实盘账户。**
- 统一升级后的主机:`prod` 与 `sim` 两个实例同机。隔离:sim 只用非隔离核,永不占 prod 的热核;独立 `hft-sim.slice`(CPU、内存上限);独立的 journal 与冷盘目录;**独立网卡 ENI-C**(sim 出口 IP = ENI-C 的私有 IP + EIP,不占 prod 的按 IP 限速;ENI-C 的队列 IRQ 钉在 sim 的一个核上,prod 的热核与 IRQ 核从不处理 sim 的包;conn-builder 在交接前经 netdev netlink 核对每条连接的收包网卡,sim 的连接不得落在 ENI-B)。原设计"sim 用 ENI-B 上的第二个私有 IP"已被取代:同一块网卡的收包队列是共享的。主机档位须同时容纳两个实例(默认 `c32`,`c16` 只在 M3 末满订阅探针达标时保留,由该探针选定)。
- 输入环里 `rep-sim` 优先级最低、`sim_max_per_round` 等规则仍是引擎规则,但部署上不再有实盘与模拟同进程的阶段。理由:总目标是延迟优先,模拟不应与实盘争 sequencer 与核([07 §9](07-策略层.md))。

## 9. 明确不做的事

- 不做对外的通用交易平台或产品;策略 SDK 只服务我们自己的策略包。
- 不做撮合引擎式的 L3 全深度重建(除非策略需要队列位置,那时只对少数合约开)。
- 基准形态不做 DPDK/AF_XDP;先把 AZ、独占核、内核调优、WS 下单、二进制行情这五件"便宜且大"的事做完,再用测得的数据决定是否启用可选的内核绕过(见 [03](03-网络与传输层.md))。
- 不把 nautilus_trader / hftbacktest 之类框架放进实盘依赖树;只借鉴设计。不建历史回测系统(hftbacktest 的队列模型只作为 `hft-sim` 的可选 feature)。

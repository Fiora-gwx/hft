# 08 · 数据面、存储与确定性回放

> **实现以 [`hft/`](../README.md) 规格为准,本章是设计证据;冲突处以 hft 为准。** journal 文件格式(目录、段头、引导块、快照)归 [journal-format](../docs/subsystems/journal-format.md),写者/读者/persist 归 [hft-journal](../crates/hft-journal/README.md),段大小与内存归 [hft-core](../apps/hft-core/README.md),回放工具归 [replayer](../apps/replayer/README.md);本章的示意结构只说明思路。
>
> 数据面的核心是两类 journal(raw、seq),它们既是热进程的"真相",也是研究数据与回放输入的唯一来源。存储与研究栈是 journal 的下游。数字与选型依据见 [research/06](research/06-data-plane-replay-observability.md) 与 [research/04](research/04-oss-frameworks-and-patterns.md)。

## 1. 原则

1. **日志即真相**:进入 sequencer 的每个事件先赋序号、写 journal,再处理;状态 = f(journal)。
2. **单写者、多读者**:每个 journal 恰有一个写线程;读者(冷进程)只读尾部,通过缓存行对齐的提交游标感知新数据;读者慢不影响写者(环形段回收由保留策略决定,读者掉队则从段头重读)。
3. **原始与归一化分离**:raw journal(venue 线程写,交易所原始 payload)与 seq journal(sequencer 写,归一化事件 + 决策 + 意图 + 回报)并存;raw 用于解码器验证与取证,seq 用于回放与研究。
4. **段滚动带快照**:seq 段的开头必须自足(引导块:配置内容、所有活跃簿的快照 + 全部状态快照),读者可以从任意 seq 段开始重建——这是现有 WAL 84% 段被隔离的直接修正。**raw 段不要求自足**:从 raw 重跑解码器时用同一 UTC 小时 seq 段的引导块作种子;原设计"raw 段滚动时也请求一次 REST 快照"已被 hft 取代([04 §7](04-行情接入层.md))。
5. **热段在 RAM,持久化在旁路**:写者只写 hugetlbfs/tmpfs 具名文件上的段(启动预触摸,运行期零缺页;2 核 `dev2` 主机类不用大页,热段是 tmpfs 上的小段、4 KiB 页、预触摸 + mlock,段大小有上限(dev2 护栏)——tmpfs 页在内存里、没有回写,与下面的 R2 问题不冲突,代价只是 TLB 开销更大);**独占线程**的 persist 顺序复制到 NVMe/EBS 文件并 `fdatasync`,落后几毫秒。段大小与 RAM 中保留的段数按主机类定义,唯一归属是 [hft-core](../apps/hft-core/README.md#线程计划)。**热写者不碰文件型 mmap**——文件页被内核回写后会重新写保护,下一次写触发 `page_mkwrite` 缺页,遇到 stable pages 要等 I/O 完成(ms 级),与是否 fsync 无关([13 R2](13-设计评审与优化.md))。进程崩溃不丢(RAM 段仍在,重启后先补完复制);整机掉电丢复制滞后部分(交易所侧仍有真值,靠对账收敛)。
6. **journal 自足**:回放需要的配置**内容**(refdata、策略参数、风控参数)以 `ConfigBlob` 事件写入,段首快照带当前 blob;不依赖外部文件([13 R6](13-设计评审与优化.md))。

## 2. journal 格式

```
(示意;唯一定义在 hft/docs/subsystems/journal-format.md)
热段:   /dev/hugepages/hft/<instance>/<journal>/<segment_no>.jrn      seq(hugetlbfs 1G;raw-* 在 /dev/hugepages2M;dev2 全部在 /dev/shm tmpfs)
冷副本: <cold_root>/<instance>/<journal>/<yyyymmdd>/<segment_no>-<first_seq>.jrn   (persist 线程顺序复制 + fdatasync)

SegmentHeader (4 KiB):不可变区(magic、format_version、journal_kind、journal_name、instance、segment_no、first_seq、
  TSC 频率与 (TSC, REALTIME, PHC) 校准对、prev_header_sha256(上一段头的哈希链)、host_profile_sha256、build_git、
  schema 表、config_digest(引导块里全部 ConfigBlob 的摘要))+ 写者行(committed_len、last_seq、state)+ persist 行
Record(全系统唯一的记录头定义,事件体见 hft/docs/subsystems/event-model.md):
  RecordHeader { len: u32, kind: u16, flags: u16, seq: u64, tsc: u64 }   // 24 B,8 B 对齐;tsc = sequencer 取出时刻(proc_tsc)
  body: 定长(zerocopy 结构)或变长 / 多段(raw payload、快照、配置)
  (可选) crc32c: u32
Commit:每条记录最后 Release 写 len;事件边界由记录头 EVENT_END 位标出;committed_len 在段头写者行(读者 Acquire 读)
```

原稿的段头字段名(`journal_id`、`config_hashes[]`、`tsc_offset_ns`、`prev_segment_hash`)与按 `<seq_start>` 命名热段的做法已被 journal-format 取代(下一段要在 `first_seq` 确定之前预创建,所以热段按 `segment_no` 命名)。

- 写者:把记录写入 RAM 热段 → 事件边界 Release 写 `committed_len`;单条 ≈ 50–200 ns(拷贝 32–512 B)。
- 读者:轮询 `committed_len` 增长(冷读者间隔 ≥ 50 µs、同进程的 advisor ≥ 10 µs,避免写者核上的缓存行争用);冷读者不需要低延迟。
- 定长事件体用 Rust `#[repr(C)]` + `zerocopy` 结构定义,**Rust 定义是唯一来源**,生成器从中导出 Arrow schema、Python dtype 与文档表;SBE 只用于解码交易所的 SBE 流,不作内部编码([13 O5](13-设计评审与优化.md));字段演进只追加,`version` 在段头。
- **滚动按 UTC 整点**(与 Parquet 小时分区 1:1 对齐),滚动本身是一个 sequencer 事件:在两个事件之间写入 `StateSnapshot`(所有簿从本地镜像直接导出,**不发 REST、不重连**;仓位、订单槽、策略状态、参数版本一并写入)→ 新段自足;新段文件已由 persist 线程预创建并预触摸(`MAP_POPULATE` 50–100 ms,所以不放在 housekeeping 或任何热核上),切换只是换指针。段在整点之前写满时由大小安全阀滚动,分两级:先在空闲轮滚动,超过硬上限才在事件边界强制滚动(数值归 [hft-journal](../crates/hft-journal/README.md))。
- **关键帧**(2026-10-03 M0-e,R8-11):段内的关键帧 `StateSnapshot{purpose = Keyframe}` 在 `Timer{Sys, Snapshot}` 到期后的第一个空闲轮**一次写完**(预算 ≤ 300 µs,计入 latency-budget 的 p99.9 记录项),周期 `keyframe_period_ms` 默认 300 000,另加事件数触发 `keyframe_max_events`(默认 1 500 000);到期后若一直没有空闲轮,最多推迟 2 个周期,之后在下一个事件边界强制写;**实盘写关键帧不计算 `state_hash`**(头部该字段写 0,由 replayer 与读者侧计算);每个 Live 簿的 `L2Snapshot{Keyframe}` 均摊到同一周期;读者可从任意关键帧起步(恢复时要重放的尾部上界见 [hft-core](../apps/hft-core/README.md) 启动步骤)。每个组件只有一个 `snapshot(&self, w)` 一次写完本 crate 的全部节,hft-journal 没有 `mark/rollback`。**为什么删掉 M0-d 的"按节分片 + 有输入即作废重来"**(W5 N-P0-1):每片 64 KiB、2 MiB 的快照要写 32 片(约 480 µs),按 1 万条/s 的输入估,这期间没有任何输入到达的概率约 e^-4.8 ≈ 0.8%,所以几乎每次都退回到 5 s 后一次写完;而这 5 s 里每个空闲时刻都重新开始一次尝试,到达的事件会碰上写到一半的片,受影响的事件约占 8%,`ingest` p99 再加约 13 µs,超过预算。不分片、在空闲轮一次写完 300 µs,只影响约 5×10⁻⁶ 的事件,落在只记录的 p99.9 里;周期从 60 s 放宽到 300 s 再降五倍。可选扩展:由 advisor 镜像在旁路生成关键帧(镜像在每个 seq 处的状态与 sequencer 相同),sequencer 只写滚动时的引导块——触发条件:实测关键帧停顿超出 p99.9 的记录目标。规则归 [hft-sequencer](../crates/hft-sequencer/README.md),写者 API 归 [hft-journal](../crates/hft-journal/README.md)。
- 持久化完全离开热线程:persist 线程从 RAM 热段顺序 `write` 到冷副本并周期 `fdatasync`;c7i.metal 无实例存储,冷副本放 io2 Block Express(单次 fdatasync 均值 < 500 µs)或 gp3(毫秒级,只影响复制滞后,不影响热路径)。RAM 热段只保留最近几段,更早的段只留冷副本;段大小 × 保留段数必须放得进该主机类的内存预算(例如 `c8` 只有 16 GB 物理内存),取值的唯一归属是 hft-core。
- 时间:`tsc` 原始 TSC 值;段头记录 `tsc_hz` 与一次 `(tsc, CLOCK_REALTIME)` 校准对;读者据此换算 UTC。TSC 不变频(invariant TSC / Graviton `cntvct`)是硬件要求(见 [02](02-硬件与托管方案.md))。

## 3. 三个 journal

| journal | 写者 | 内容 | 典型量 |
|---|---|---|---|
| `raw-feed-<venue>` / `raw-gw-<venue>` | 各 feed / gw 线程 | TLS 解密后的 WS payload 原样 + rx 时间戳 + conn_id(登录帧与含签名的帧不记录) | 按目标订阅实算;现有 WAL 量级 ≈ 160 GB/天(150 合约 × 三所) |
| `seq` | sequencer | 归一化行情、回报、命令、定时器、决策(意图、风控结果)、策略 `note`、快照 | 按目标订阅实算;量级示例:400 个 inst 的 bookTicker 平均 20 条/s ≈ 3 GB/h。原稿"5–20 GB/天"低估约一个数量级,不能作为段大小依据(段大小公式在 journal-format) |
| `chain`(optional,链上启用时) | chain-core | 块头、报价与预检结果、投递与回执、tx 状态迁移(可选扩展另记 L0 状态变化、L1 模拟结果、bundle 投递) | 1–5 GB/天 |

保留:本地冷盘 seq 7 天、raw 3 天;冷进程 `journal-archiver` 持续转 Parquet 上传 S3(同桶、独立前缀,对象键带主机段 `<prefix>/<host>/<instance>/…`——`<prefix>` 正式为 `hft`、M7 测试网期间为 `hft-testnet`;加主机段是因为 dev2 与升级主机的同名实例会写同一个键(W3/W4 C-P0-8),与 collector 的前缀不重叠;键格式唯一归属 [journal-archiver](../apps/journal-archiver/README.md)),Parquet 保留永久。实例名只允许 `prod` 与 `sim`:模拟始终在独立的 `sim` 实例里,有自己的一套 journal 与冷盘目录;`dev2` 上 `sim` 长期运行,`prod` 角色实例只在交易所测试网/模拟盘联调窗口运行(测试网 key 与账户);统一升级后两者同机([07 §9](07-策略层.md))。

## 4. Parquet 与研究栈

- `journal-archiver` 尾随 seq/raw/chain journal(只含交易所需的订阅),按 `(exchange, dataset, symbol, hour)` 分区写 Parquet(zstd)到独立前缀,沿用现有 `s3-store` 的上传核验做法,不要求与 collector 的 Parquet schema 兼容;每小时一个文件组 + manifest(记录/字节数、首末 seq、SHA-256),与 AGENTS.md 的封存纪律一致。
- 研究查询:DuckDB / Polars 直接读 S3 Parquet(现有 `analysis/` 工作流不变;大范围行情研究仍读 collector 的数据,与交易 journal 按时间戳对齐);量大后加 ClickHouse 作为热查询层(跨所 tick 对齐、lead-lag、价差序列),数据源仍是 Parquet。
- 不引入 kdb+/QuestDB/Timescale/ArcticDB(ArcticDB 为 BSL 1.1,生产需付费许可):DuckDB+Parquet 已满足研究,ClickHouse 覆盖交互式;减少运维面。Parquet 写入遵循 DuckDB 指南:row group 10 万–100 万行(< 5 千行会慢 5–10×)、单文件 100 MB–10 GB、按过滤列排序。
- 数据字典:每个事件类型一份 schema 文档由 SBE schema 自动生成;时间戳五字段语义写死在文档与列名里(`ex_ts_ns`、`ex_send_ns`、`hw_rx_ns`、`rx_ns`、`proc_ns`)。

## 5. 确定性回放与模拟重演

```
replayer verify:seq journal 的 Input 记录 ──▶ sequencer{策略快速部分, 执行层, 风控, OMS}(同一二进制)
                 ──▶ Output 记录与实盘逐字节比对
replayer sim:   录下的行情事件 ──▶ sequencer{同一策略} ──▶ sim-gw(模拟撮合)──▶ 模拟回报注回
                 ──▶ 复现与排障(不评估收益)
```

- 回放的用途是**正确性验证与排障**;上线评估不用回放(理由见 [07 §9](07-策略层.md))。重构修订(2026-10-29):另设研究模式 `replayer research`/`parity`(参数变体 + 进程内模拟撮合 + Parquet 输出,带校准哈希、对账误差与种子方差),只用于研究与参数筛选,见 [replay-as-research-tool](../.agents/notes/proposed/architecture/2026-10-29-replay-as-research-tool.md)。下列两种模式都是 core:
  - *验证*(`replayer verify`):输入实盘 journal 的全部 Input 记录(行情、回报、命令(含预热注入 `InjectWarmup`)、定时器、`Advice`、模拟账户回报),要求 Output(意图、风控结果、执行层决定)与当时逐字节一致 → 证明代码改动没有改变行为(CI 金标准)。
  - *模拟重演*(`replayer sim`):把录下的行情喂给模拟网关 + 同一策略,复现某段时间的问题。结果不要求与当时的模拟账户逐字节一致(当时 sim-gw 的回报时刻受实时调度影响),但同一 journal + 同一模拟配置与种子重演两次必须一致。
  - 删除了旧设计的"假设模式"与参数扫描(fork hftbacktest 评估新策略/参数)。hftbacktest 的队列模型只保留为 `hft-sim` 的可选 feature,给挂单类策略用。
  - *相对比较*(`replayer sim --ab <paramsA> <paramsB>`,R8-10):同一段已录 journal、同一模拟撮合器,只输出两组参数的**差值**;默认关闭(需显式参数),报告首行强制标注"相对比较,不是收益估计,不得用于定仓"。它让参数研究不必每组都等数周实时模拟,但不是回测。
  - *逐决策比对*(`replayer compare --a <prod journal> --b <sim journal> --map <prod 账户>=<sim 账户> --out <dir>`):正式实例 Shadow 3–7 天期间,与同参数 sim 实例逐决策比对,差异需解释([11 §5](11-实施路线图.md))。
  - 每日 `--advice recompute` 从当日归档的 Model 检查点起算(`replayer verify --model-checkpoint <path>`;journal-archiver 每天把每个策略实例在 UTC 00:00 之后写出的第一份检查点归档到 S3);当日无检查点则跳过当日 recompute 并报 P2;当日检查点的路径节被丢弃(版本不符)时,从下一个分位带边界 + 平滑窗长度之后开始比较。`hft-replay-verify` 每次运行补跑所有缺少报告的 UTC 日(不只前一日),联调与混沌窗口里的迟到报告视同当日;它运行时 archiver 与 pipeline 暂停(`ExecCondition`),避免在 dev2 的批处理内存里被 OOM 杀掉(R8-11,W4 P1-10)。
  - *延迟统计*(`replayer latency`,R8-11):从 seq journal 对**每条带 `MarketHdr` 的行情记录**(含 TopN 快照;集合归 hft-telemetry)离线计算 `kernel_rx`、`ingest`、`feed_host`(记录头 tsc + `MarketHdr` 的 hw/sw/rx 时间戳与 `rx_empty_gap_ns`),实现是 hft-telemetry 的离线模块 `event_weighted()`。它按事件加权(探针按时间抽样会低估突发时段的尾部),热路径零成本,门槛 ⑩ 的 `kernel_rx`/`ingest` 读这份([00 §4.2](00-目标与延迟预算.md));规格归 [replayer](../apps/replayer/README.md)。
- **决定性要求**:时钟、随机数、参数全部来自事件流;策略与模型代码里不允许 `Instant::now()`、全局可变状态、HashMap 迭代顺序依赖(用 `IndexMap` 或数组);CI 里用 `#![deny(clippy::disallowed_methods)]` 禁用。策略慢速部分(`Model`)的产出以 `Advice` 记入 journal,回放读日志、不重算,所以模型可以用浮点。`Advice` 带 `basis_seq`/`basis_tsc`(依据的最后一条记录),策略据此判过期,回放与实盘看到同一判断;跨启动的过期只由策略按 `basis_seq < Now.boot_seq` 判定,sequencer 不加标志。
- **引擎时间跨重启连续**:`Now.engine_ns` 由 journal 记录的运行区间累加得到(停机不计),所以它本身也是确定的;策略、ledger、risk 的持久状态只存 `engine_ns`,TSC 只在单次启动内使用。OMS/exec 的 `recovery_end` 平移规则保留([M0b 独立评审 P1-3](_work/review-2026-10-03-M0b独立评审.md))。
- **Model 检查点与预热**(设计理由见 [07 §2.2](07-策略层.md)):
  - 检查点是 journal 之外的冷盘文件,只是预热优化、不是正确性条件——verify 回放从不需要 Model 状态。检查点分两节(R8-11):**原始样本节**(如两侧基差样本环、资金费环;布局由 `ModelLayoutDesc` + `LAYOUT_VERSION` 管)与**路径状态节**(分位带及其时刻、平滑窗、上次发送的载荷摘要等路径依赖的派生状态;自带 `Model::PATH_VERSION`,经 `Model::snapshot_path`/`restore_path` 读写,作为检查点第一块写出)。恢复时 `PATH_VERSION` 不符只丢路径节,派生状态按原始样本重算,写 `Note{ModelPathReset}`(短暂不一致可接受)——所以改打分逻辑仍不丢长窗口统计,而有路径节时"检查点 → 恢复 → 续算"与连续运行逐字节相同。原写法"只存原始样本、派生状态恢复后重算"与"每日 recompute 逐字节一致"冲突(分位带的更新时刻与平滑窗是路径依赖的),每日 recompute 会失败、⑦ 过不了(W2 P1-4)。结构参数变化按 group 重置并自动预热;快照按 group 分块写出(advisor 每次 poll 只写一块)。键只含 `kind_id`、`Model::LAYOUT_VERSION`、`schema.id`、`strategy_instance`、`last_seq`;参数版本、refdata 版本、二进制 SHA 都不使它失效(参数变化随重放经 `model_on_params` 重新应用)。周期 `advisor.model_checkpoint_ms`(默认 600 000);丢弃时写 `Note{ModelCheckpointDiscarded}`。接口唯一归属 [hft-strategy-sdk](../crates/hft-strategy-sdk/README.md)。
  - 冷启动预热数据作为 **Input** 注入:控制命令 `InjectWarmup{instance, local_kind, chunk_no, last, payload ≤ 4096 B}`(主体 Trader 或 pipeline)记入 journal,路由到该实例的 Model,回放时同样从日志读,结果确定。预热样本由 pipeline 的策略插件生成(组合携带:交易所 REST K 线或 collector 数据),引擎不解释载荷。
- **模拟账户的 journal 语义**:
  - 模拟是账户类型(`AccountMeta.kind = Sim`),不是运行模式。Sim 账户的 `OutMsg` 与实盘一样是 Output 记录;sim-gw 产生的回报经同一回报环进入,记为 Input,与实盘回报是**同一组事件**,不加新 kind,按账户类型区分。
  - 因此 verify 回放不重跑 sim-gw,直接读日志里的模拟回报——模拟账户与实盘账户一样可以逐字节验证。
  - 模拟专用命令(`SimReset`、`SimTransfer`)是普通 `ControlCmd`,同样进 journal;reconciler 与 kill-switch 进程跳过模拟账户(Sim 账户上的 `Kill` 与实盘一样经检查链生效)。
  - 模拟回报在 sequencer 输入环里优先级最低(`rep-sim`,每轮 ≤ `sim_max_per_round` 条),它们进入 journal 的位置由这个顺序决定;verify 回放按日志顺序读,不受影响。模拟在 `sim` 实例,它的 journal 同样可以 verify。
  - 模拟报告(PnL 分解、成交率、两腿间隔、裸敞口、保证金占用)由冷进程从同一份 journal 产出,ops_bot 展示时标注"模拟"。
- **速度**:一天 seq journal(10 GB)回放目标 < 10 分钟(单核 20–50 M 事件/分钟)。
- **上线前验证**:新版本二进制以生产 journal 离线 verify 回放,与现版本比对 Output;新策略或新参数先在模拟账户上运行;实盘只有一个实例(`prod`),不设第二个实盘实例(同机的 `sim` 实例只含模拟账户、不持交易所 key,不是第二实盘实例);不设小额实盘阶段,正式实盘在统一升级后的主机上开始,切 Live 前先做零成交冒烟与正式实例 Shadow 3–7 天(不开仓,[11 §5](11-实施路线图.md))。上线门槛的唯一定义在 [hft/docs/testing.md §8](../docs/testing.md)。

## 6. 快照与恢复

- 热进程冷启动:/dev/shm 空间检查扣除本实例已有的段(否则崩溃后可能因自己的残段起不来);先把 RAM 热段中尚未复制的尾部补到冷副本 → 读最新段的 `StateSnapshot` + 之后的事件 → 重建状态 → 连接交易所 → 启动闸门 → 放行。目标 < 30 s。advisor 同时从 Model 检查点恢复并重放追上(§5)。
- **人工停机后不自动恢复开仓**(R8-11,汇总 M-6):kill-switch 的 `stop_core` 在 `systemctl stop` 之前写持久标记 `/var/lib/hft/kill-switch/stop-marker.json`(`{req_id, scope, utc_ns}`,fsync);hft-core 启动时读到它,就写一条 Input `ControlCmd{Kill{scope, 非 HARD, 不带 flatten}}`(issuer `cli:systemd`)再把标记改名 `.consumed`——这条 Kill 进 journal、可回放,解除仍要交易员 `/resume kill`。否则 `stop_core` 之后一次干净重启就会自动恢复开仓,撤销老板的停止。`stop_core` 停机失败时 kill-switch 把标记改名为 `stop-marker.json.aborted` 并 P0,hft-core 启动只读 `stop-marker.json`(R8-12)。规则归 [hft-core](../apps/hft-core/README.md) 与 [kill-switch](../apps/kill-switch/README.md)。
- 停机时间不计入对冲截止:`hedge_deadline_ms` 只按引擎运行时间(`engine_ns`)累计;闸门放行时,对仍未对冲的链接先做一次 `SecondRetry`,再按正常截止判断——否则 30 s 的冷启动本身就会把每条在途链接判成 Broken。
- 启动闸门(唯一归属 [hft-risk](../crates/hft-risk/README.md)):对账(本轮差异全部可忽略,或逐项 `AdoptExchange` / `SetBalanceBaseline` 处置;资金费条目不进闸门,只告警并由 ledger 自动校正,见 [07 §10](07-策略层.md))、交易所身份(按 key 查交易所 UID 与登记的账户比对)、账户配置(持仓/保证金模式与 `VenueCaps` 要求一致)全部通过才放行开仓。恢复时重算的决定与当时已发出的单不一致 → 该 (venue, 账户) 全部订单置 Unknown、闸门严格化;同一输入连续导致崩溃 → 隔离该输入、从最近快照起步并按日志尾部丢失处理。毒丸分两层:恢复期崩溃由 hft-core `boot_guard` 管,运行期崩溃由 sequencer 的 InputHash 管,计数都在 `DurableMeta`([hft-sequencer](../crates/hft-sequencer/README.md))。交易所身份按**每把 key** 核验(Ed25519 会话 key 与 HMAC REST key 分别查 UID;kill-switch 自检与 reconciler 启动同样查),不等于登记的 `venue_uid` → 退出 2 + P0。
- 交易所侧 `Unknown` 订单在对账后收敛;链上在途交易(optional)由 chain-core 自己的 journal 恢复生命周期状态机。
- 段头链式哈希(`prev_header_sha256`)让离线校验能发现缺段。

## 7. Python 访问

- `hft-py`(PyO3):`open_journal(path).events(kind=..., inst=..., t0, t1) -> Arrow RecordBatch`,零拷贝到 Polars;`pnl(journal) -> DataFrame`(与热进程同一记账代码);不提供回放式的参数评估。
- 研究流程:Parquet(历史)+ journal(今天)统一为 Arrow;在模拟账户与实盘的报告上分析 → 参数候选 → 开新的模拟账户验证 → 人工接受后经控制环下发。
- Python **不**直接 mmap 写任何 journal;它对热进程的唯一写入口是控制命令。

| 现有 | 新 |
|---|---|

# 09 · 可观测性、风控与控制面

> **实现以 [`hft/`](../README.md) 规格为准,本章是设计证据;冲突处以 hft 为准。** 时间点与分段名归 [latency-budget](../docs/latency-budget.md),命令、权限与模式归 [control-plane](../docs/subsystems/control-plane.md) 与 [hft-ctl-proto](../crates/hft-ctl-proto/README.md),Telegram 鉴权归 [ops_bot](../python/ops_bot/README.md),告警规则归 [watchtower](../apps/watchtower/README.md),事故处置归 [incident-response](../docs/runbooks/incident-response.md);本章的命令表与示意只说明思路。
>
> 测量是这套系统的第一公民:没有分段时间戳与常驻直方图,任何"更快"都是猜。风控在热路径里(见 [05 §3](05-CEX执行层.md)),本章讲它的**外围**:kill 开关、死手、对账、降级、引擎与策略的风控边界、保证金分档与资金监控,以及所有冷进程如何安全地影响热进程。

## 1. 延迟分解:每个事件带五个时间戳

```
交易所事件时间 ex_ts ─▶ 交易所发送 ex_send ─▶ 网卡 HW RX hw_rx ─▶(内核软件戳 sw_rx)─▶ 用户态读完 rx_tsc ─▶ sequencer 取出 proc_tsc
   ─▶ 策略/风控/OMS 完成 decided_tsc ─▶ write() 返回 sent_tsc ─▶ 交易所回执到达 ack_hw_rx(含交易所时间)
```

| 分段(仓库内名称) | 含义 | 谁能改 |
|---|---|---|
| `wire_in` = `hw_rx − ex_send` | 交易所内部排队 + 网络单向(需时钟同步 < 100 µs 才有意义) | AZ、专线、交易所 |
| `kernel_rx` = `rx_tsc − hw_rx` | 网卡 → 内核 → 用户态(内核路径);`sw_rx` 常态记录后再拆成 `nic_to_kernel` 与 `kernel_to_user` 两段诊断 | IRQ 核独占、中断合并参数、隔离核;Onload |
| `ingest` = `proc_tsc − rx_tsc` | TLS + 解析 + 入环 + 在环中排队 + sequencer 取出 | 解析器、环、BBO 独立线程、md 可抢占 |
| `decide` = `decided_tsc − proc_tsc` | 簿更新 + 策略 + 执行层 + 风控 + OMS | 我们的代码 |
| `egress` = `sent_tsc − decided_tsc` | 出环 + 模板填充 + TLS 加密 + write() | 模板预编码、cache warming |
| `rep_to_order` = 由某条回报触发的下一单 `sent_tsc` − 该回报帧 `hw_rx` | 回报路径(gw 解码 → rep 环 → sequencer → out 环 → gw 发送)的主机内部分;门槛 ⑩ 对冲路径的硬项 | 用户流每圈 poll、每帧回报后排空出环、sequencer 每条 BBO/advice 后查看 rep 环头 |
| `hedge_host` = 第二腿 `sent_tsc` − 第一腿成交帧 `hw_rx` | `rep_to_order` 的子集(LegLink 第二腿),含回报在 gw 与回报环里的等待;只记录 | 同上 |
| `order_rtt` = `ack_hw_rx − sent_tsc` | 网络 + 交易所撮合 + 回执 | AZ、交易所 |

- `hw_rx` 来自 `SO_TIMESTAMPING` 的 RX 硬件戳(ENA 自 2025 支持;c8g 上是否可用在 M1.5 核实,不可用时退化为软件时间戳并标记,HW 与 SW 样本分开统计),其余是 TSC。ENA **没有 TX 硬件戳**:原图中的 `hw_tx` 与"`hw_tx − sent_tsc` 内核 TX 路径""`ack − hw_tx`"两段已被 hft 取代;内核 TX 软件戳 `tx_sw`(`kernel_tx` 分段)是可选扩展,默认关。
- 每个订单的首个交易所响应把八个时间点(触发事件的五个 + `decided_tsc`、`sent_tsc`、`ack_hw_rx`)合成一条 `LatencySample` 记录进 seq journal(尾部追加 `sw_rx`);撤单与改单同样由 hft-oms 记时间戳并合成样本,`LatencySample.action`(New / Cancel / Amend)区分,`order_rtt` 只统计新单、`rep_to_order` 含三种 action;样本按触发事件的 kind 区分 `tick_to_trade`(行情触发)与 `rep_to_order`(回报触发),`link_role` 保留,带 LegLink 的第二腿样本另算 `hedge_host`;冷进程据此填直方图。**热路径只做时间戳读取(≈ 20 ns/次)**,不做任何统计。
- 行情类分段(`kernel_rx`、`ingest`、`feed_host`)不靠订单样本:从 seq journal 对**每条带 `MarketHdr` 的行情记录**(含 TopN 快照;集合归 hft-telemetry)离线计算(hft-telemetry `event_weighted()`、`replayer latency`),按事件加权,突发时段不被低估;`MarketHdr.rx_empty_gap_ns` 另给出 `kernel_rx` 的上界,⑩ 报告并列上下界([00 §4.2](00-目标与延迟预算.md))。含 PHC 端点的分段按 1 s 一条的 `ClockStatus` 插值换算,误差界 > 1 µs 的样本计入 `unsynced_cal`、不进分位数。

## 2. 直方图与导出

- 冷进程 `watchtower`(指标导出与健康检查合一)尾随 journal,按 `(venue, inst 类别, stage)` 维护 `hdrhistogram`(3 位有效数字,1 ns–10 s),每 10 s 导出 p50/p90/p99/p99.9/max 与计数到 Prometheus;Grafana 看板按 stage 分层。
- 每日回放同一份 journal 得到的"纯计算分段"(`decided − proc`)是回归基线:代码变更后该分段 p99 上涨 > 10% 阻断发布。从 M1.5 起,每个里程碑结束时另在按需租用的参考机(与 M1.5 同型)上跑 `bench-gate --reference`(相对回归 + 单 crate 上限),不在 CI 里([11 §3.1](11-实施路线图.md))。
- 验收口径(R8-11):p50、p99 不劣于硬线(验收下限)为通过,基准形态是目标,落在两者之间需 Admin 签字;p99.9 只记录(固定节拍突发与关键帧下);n < 1,000 不报 p99、n < 10,000 不报 p99.9;同机干扰每组两侧各 n ≥ 10,000 才作硬判定。订单类样本靠只绑非正式账户的 `latency-probe` 策略在主网行情负载下补([00 §4.2、§6](00-目标与延迟预算.md));判定唯一归属 testing §8.2。
- 交易所侧指标:`ack − sent` 的 p50/p99 按所按连接;`hw_rx − ex_send` 按所(时钟同步状态附带);`RateLimitHit`、`Reject` 计数;连接切换次数。
- 链上指标(optional,链上启用时):每端点/运营商的健康度与限速命中、`SourcesLow` 时长、包含块数与被抢跑率(只报告)、UNKNOWN 持续时长分布;builder profile(可选扩展)另有块首达时间(块流 vs 本机节点)、bundle 每 builder 接收/包含率、块内排位、L0 drift 次数。
- 业务指标:每策略每 group 的信号数/放行数/成交数、价差捕获(信号价差 vs 成交价差)、双腿间隔、库存暴露时长、PnL 分解(价差/基差/资金费/手续费/相对到达价的滑点;链上另有 gas/出价)、保证金占用。模拟账户产出同一套指标,标注"模拟";正式实盘开始后同参数模拟账户(同机 sim 实例)与实盘并列出差异(校准)。

## 3. 低开销的诊断

- 事件本身就是 trace:`seq_no` 贯穿意图→帧→回执;不需要额外 tracing 框架在热路径上。
- 热路径的"日志"是定长 `Note` 记录(kind + 8×u64),冷进程翻译成文本;`tracing`/`log` 宏只在冷进程与启动期使用。
- 需要深入时用 `perf`(硬件计数器:cache-miss、branch-miss、L1d)与 `bpftrace` 的 uprobes 对热进程做**短时**采样,平时不挂。
- 时钟:chrony 对 AWS Time Sync(或 PTP 硬件时钟,若实例支持,精度亚微秒);housekeeping 每 1 000 ms 写一条 `ClockStatus`(含 `(tsc, phc, calib_err_ns)` 校准对与偏移、抖动;原写"每分钟"不够,换算误差可达数十 µs,[02 §5](02-硬件与托管方案.md));偏移 > 200 µs 时 `hw_rx − ex_send` 类指标标记为不可信。

## 4. 风控外围

### 4.1 kill 开关

| 级别 | 触发 | 效果 |
|---|---|---|
| venue(× 账户) | 连接异常、限速风暴、交易所公告、人工 | 该 venue 停止开仓,按默认参数撤挂单 |
| 账户 | 人工、账户级风控 | 该账户全部 venue 停止开仓 |
| 全局 | 进程健康检查失败、人工 | 全部账户停止开仓 |
| HARD 位 | 人工(Trader);全局或**按账户** | 连对冲腿与平仓单也拦截(会故意留下裸腿,只在确认交易所侧异常时用);按账户 HARD 让一个账户失控时不必连其他账户的对冲一起封 |

- 策略层面的停止用 `SetMode`(Shadow / CloseOnly),不再有策略级 kill。
- 日亏熔断按账户锁存为 CloseOnly(不是全局 kill);恢复需要 `Resume{DailyLoss}` 并重设触发线。
- 除 HARD 外,任何降级都放行 OMS 发出的风险递减单(对冲第二腿、平仓、HedgeFix),避免把已成交的第一腿留成裸腿。
- 带自动平仓的 kill(`Kill{…, flatten}`,执行层 `engine_flatten`)对处于 Broken 的 group 同样生效:先对永续腿 reduce-only 减仓(`PerpFirst`,受 `max_reduce_notional`),再处理现货腿(§4.8)。它同时置账户级 `flatten_lock`:直到 `Resume{Kill}` 前,该账户只接受比当前更接近 0 的目标与 Reduce/Flatten 意图,策略的新目标覆盖不了清仓。`Kill{flatten}` 在启动闸门未放行与 DRAINING 期间**也允许**(仍需确认;control-plane 把它写成"升级类的例外",R8-11)——恢复期或排空期恰恰可能需要清仓。
- **紧急停止 `/stop` 的语义**(R8-9):= 非 HARD、不带 flatten 的 `Kill{Global | Account(a)}`——禁止新开仓、撤销挂单;已成交第一腿的对冲与平仓照常(`RISK_REDUCING` 放行),不会把第一腿留成裸腿。老板(`Viewer`)唯一的写权限就是它,经 ops_bot 确认后发出(§5.3);不能 `Resume`,不能发任何其他写命令。
- **hft-core 不健康时的停止路径**:hft-core 心跳过期或 ctl-gateway 不可达 10 s 时,ops_bot 改为经 kill-switch 的本地触发套接字(只接受 ops_bot uid)发 `stop_core`:kill-switch 先撤单,再经 polkit **只允许** `systemctl stop hft-core@prod`(SIGTERM → Drain,不平仓)——ctl 不可达而 sequencer 仍活着时,光撤单挡不住新单。ops_bot 把这次停止记为"待补 Kill"(`/var/lib/hft/ops_bot/pending_kill.json`);hft-core 恢复、ctl 可达后先自动补发 `Kill`,再允许交易员 `/resume`,否则重启后的 `/resume recovery` 会让兜底停止失效。同时向值班交易员发 P0;`/stop` 失败或 10 s 内无结果 → P0。kill-switch 仍只撤单,不平仓(R8-10;规格归 [kill-switch](../apps/kill-switch/README.md) 与 [ops_bot](../python/ops_bot/README.md))。
- **停机标记与二次确认**(R8-11,汇总 M-6):"待补 Kill"依赖 ops_bot 活着;为了让 `stop_core` 之后的干净重启也不会自动恢复开仓,kill-switch 在 `systemctl stop` 之前写持久标记 `/var/lib/hft/kill-switch/stop-marker.json`(`{req_id, scope, utc_ns}`,fsync),hft-core 启动时读到即写一条 Input `ControlCmd{Kill{scope, 非 HARD, 不带 flatten}}`(issuer `cli:systemd`,权限表只为"启动时由停机标记触发的 Kill"开这个主体)再把标记改名 `.consumed`,解除仍需交易员 `/resume kill`([08 §6](08-数据面与回放.md));停机失败时 kill-switch 把标记作废为 `.aborted` 并 P0,是否另发 Kill 由人决定(R8-12)。另外,任一账户 MarginStress ≥ L2、有 Broken 或在途链接时,ops_bot 的兜底只撤单 + P0,停引擎需要第二次确认(`/stop … core`)——这些情形下停掉引擎会让对冲、补腿与 L3 一起停摆。
- 降级类命令不带账户参数时作用于全部账户;升级类命令必须显式写账户。完整模型见 `hft/docs/subsystems/control-plane.md`。

### 4.2 死手(dead man's switch)
- 交易所侧能力差异很大(research/06 §6):Binance 合约 `countdownCancelAll`、OKX `cancel-all-after` 可用;Bybit DCP 仅机构账户(默认 10 s,窗口 3–300 s,需订阅 `dcp` 主题);**Binance 现货与 Bitget 没有死手接口**,必须靠主机侧看门狗 + 一个独立的 kill-switch 冷进程(持有撤单权限的 REST 凭证,在热进程心跳消失时撤单;另有只接受 ops_bot uid 的本地触发套接字,§4.1;自检时用自己的 key 查 UID 与登记的 `venue_uid` 比对)。刷新周期 5–30 s,countdown 超时 ≥ 2 × 刷新周期;进程崩溃 → 交易所自动撤单或 kill-switch 进程撤单。
- 主机侧:systemd `WatchdogSec`;sequencer 主循环只递增一个缓存行上的心跳计数,housekeeping 线程每秒确认计数前进后才 `sd_notify`(`sd_notify` 是 `sendmsg` 系统调用,不能在热线程里做,见 [13 R7](13-设计评审与优化.md));心跳停 → 重启进程(冷启动 < 30 s,见 [08 §6](08-数据面与回放.md))。
- **机外**(R8-10;五路评审 V4 P1-8):kill-switch、watchtower、ops_bot 都与 hft-core 同机,整机宕机或 AZ 故障时它们一起消失。所以 dev2(另一个 AZ)上运行只用 Python 标准库的 `hft-offbox-watchdog.service`:每 15 s `GET` 升级主机 ENI-A 私有 IP 上 watchtower 的 `/healthz`(`healthz_bind` 只绑 ENI-A、安全组只放行 dev2,与只绑 127.0.0.1 的 `/metrics` 分开;返回 hft-core 心跳年龄与状态、kill-switch 存活、最近一次对账时刻),连续 60 s 不可达或报告不健康 → 用独立的 Telegram token 与电话类告警通道(供应商待选型)告警。随后按 incident-response 的"交易主机失联"一节处置:两名授权人(名字待负责人指定,持有各所网页权限与划转二次验证)在各所网页手工撤单/减仓,再从 AMI + EBS/S3 重建主机并以 `--recover-from-snapshot` 恢复(换 AZ 时用预建的第二 AZ 待命清单与 ENI,并改看门狗目标——目标是看门狗主机上的本地配置文件)。看门狗与电话告警演练是正式实盘前置(门槛 ⑪)。**维护静默**(R8-11):`/healthz` 返回 `maintenance_until`(本机命令 `hft-maint start <分钟>`,≤ 30 min),静默期间看门狗只发 Telegram、不打电话——激活 `cold` 组会停 watchtower,GRUB 重启也会让 `/healthz` 不可达,原规则下每次都会误打电话。**观察点独立性**:若 az-probe 证实 Binance 所在 AZ 与 dev2 相同(看门狗与升级主机同 AZ,AZ 故障时一起消失),另开 t4g.nano(约 $3–4/月,`[需授权]`)在第三个 AZ 跑看门狗。
- 链上侧(optional):包装合约内的 `maxBlock` 守卫构成死手(free profile `maxBlock` = 发送块号 + 3;builder profile 与 bundle 有效期一致),过期后交易即使上链也只会 revert;只有 bundle 有效期不够,签名交易在 nonce 用掉前一直有效。

### 4.3 对账与降级
- `reconciler` 每 30–60 s 比对各 core venue 现货与永续的挂单、成交、仓位、余额(现货库存)与保证金数据(覆盖范围按 `VenueCaps`);差异按名义分级 → 忽略 / 告警 / `Recon` cap(两轮确认后只平不开)。
- 引擎仓位以 `Fill` 溯源(按净量)为准;交易所用户流为校验;自身强平/ADL/人工成交以 `ExternalFill` 入账;用户流断线期间漏掉的 ADL,由 reconciler 第二轮按"永续同号缩小、无在途、无 Unknown"且两轮都无用户流断开、用户流已稳定 ≥ 1 个对账周期标 `AUTO_EXTERNAL`,sequencer 在这条 `ReconcileReport` Input 内确定地合成成交并 P0,不另写记录;hft-ledger 记 `auto_held`,之后补推的同向强平/ADL 先抵扣(R8-11、R8-12;现货差异与反向差异仍走人工)。启动闸门与 HARD 解除要求本轮差异全部可忽略,或逐项 `AdoptExchange`(采纳交易所侧仓位或余额)/ `SetBalanceBaseline`(登记非策略资产基线)处置;出现日志尾部丢失或恢复不一致(`RecoverMismatch`,P0)时禁用"干净重启后自动解除 Recovery"。
- **资金费差异只告警、不进闸门**:资金费条目不进 `RECONCILED` 闸门、不触发 `Recon` cap;reconciler 分级前先用同组报告的 Funding 条目修正结算资产的余额差,资金费差额不再经"余额"条目混进 cap 与闸门;ledger 查不到历史(`NoHistory`)的条目在窗口结束后按交易所金额入账并写 `Note{FundingCorrected}`(P1)。reconciler 的 `Funding` 条目带交易所逐笔资金费(账户、venue、inst、结算时刻、金额);ledger 对结算时刻早于 `funding_recon_lag_ms`(默认 600 000)的差额自动入账为 `AdjustDelta::Funding` 并写 `Note{FundingCorrected}`,比对窗口最近 48 h;差额 > `funding_diff_alert`(默认 1 USDT 或 1%)→ watchtower P1。理由:资金费合成值与流水每期都可能有小差异(只推费率的所尤其如此),进闸门会让一条资金费差异把开仓永久卡住([M0 独立评审 P1-5](_work/review-2026-10-03-M0独立评审.md))。
- 链上仓位(optional):以 `INCLUDED_OK` 且 finalized 为会计口径;钱包余额定期扫描。

### 4.4 健康检查(冷进程 `watchtower`)
- **watchtower 只告警,不发降级命令**。自动降级只来自 sequencer 自己的 cap(行情序号断裂/静默 → 簿 `Stale`,策略对该 inst 不开仓;persist 落后或磁盘余量低 → housekeeping 写 `Timer{PersistLag|DiskLow}` Input → `Storage` cap 禁开、超阈值 Drain;保证金数据过期 → MarginStress L1)或人工命令。
- 每 venue 行情静默 > T(按所频率)→ 告警。
- 双路行情 `update_id` 落差 > N → 告警(主备切换由 feed 线程自己做)。
- 直方图任一 stage p99 超预算 → 告警;连续 3 个窗口 → P1。
- 对账:读 `Recon` cap 与带名义阈值的告警级差异(不再以"严重级别 ≥ CloseOnly"为条件——reconciler 不发 CloseOnly);`StaleGenFill`、`ExternalFill`、带成交的 `ForeignOrder` → P0(裸敞口告警与 ledger 同源,看不见漏记成交,所以这几条必须单独报)。
- 保证金 L2/L3 → P0;资金费数据过期 → P1;资金费差额 > `funding_diff_alert` → P1。
- 断腿自动处置:`Note{ExecAutoFixFailed}` → P0;`Note{ExecAutoFixDone}` → P1(仍需人工 `Resume{HedgeFailure}`)。
- advisor 滞后 > `advisor_max_lag_ms`(默认 5 000)→ `AdvisorLag` P1;`AdvisorLag` 唯一定义在 [hft-event](../crates/hft-event/README.md)(滞后 = `engine_ns` 差,超阈值时每 10 s 至多写一次),watchtower 只读它。
- 策略自己的 Note 按策略描述符(`StrategyDesc.notes`:码、名、级别、字段含义)通用翻译与分级;实盘与模拟日报按 `StrategyDesc.report` 的字段与聚合方式通用汇总——新增策略不改 watchtower。
- 时钟偏移、磁盘余量、hugepages 余量、隔离核上出现其他进程(`/proc/sched_debug`)、dev2 上的 swap-in 速率与 PSI(`HostPressure`,阈值与 dev2 护栏一致:`MemAvailable < 600 MiB`)→ 告警。
- 跨所行情旁证 `MarkDivergence`:同一资产跨 venue 的 mark/mid 偏离 > `mark_div_bp` 持续 > 30 s → P1。单个 inst 静默但它的连接仍有回帧时,报价照常视为有效("安静 ≠ 过期"),这条规则只告警、不降级。
- `healthz` 监听:供机外看门狗读取(§4.2)。

### 4.5 引擎与策略的风控边界

引擎负责**全账户**的硬约束:硬限额(名义、仓位)、kill(含按账户 HARD)、保证金分档、裸腿(LegTracker 把在途算进裸敞口;开仓前检查第二腿;任一 group `Broken` → 账户级 `HedgeFailure` cap;Broken 的有界自动处置,§4.8)、限速(为风险递减单预留令牌)、对账与启动闸门(对账、交易所身份、账户配置)、交易所能力约束(`VenueCaps`)、存储退化、下架。策略负责自己的进出场、止损、仓位规模与资金口径(从权益视图自己算,引擎不提供"可用资金"公式)。原先写进引擎的策略规则(资金公式 `wallet × leverage × deployable`、cdex 补腿 5% 阈值与残余清理)移到策略参数或策略代码。详见 [07 §6](07-策略层.md)。

### 4.6 保证金分档(`MarginStress`)与外部事件

- 强平价 `liq_px`、保证金率(维持保证金 / 保证金余额,各所换算写在 venue 适配层)、ADL 档由 venue 适配层按 `VenueCaps.margin_data`(推送或轮询)产出 `MarginReport`。
- **按到强平价的距离分档**([M0b 独立评审 P0-3](_work/review-2026-10-03-M0b独立评审.md)):每个 (account, venue) 的 `liq_dist = min over 永续持仓 |liq_px − mark| / mark`,交易所 `liq_px` 与 ledger 估算取更保守者。三档(默认待标定):L1 `liq_dist ≤ 25%` 禁开(数据过期也按 L1)→ L2 `≤ 15%` 通知策略 30 s 内减仓 → L3 `≤ 10%` 或截止已过时执行层按比例减永续敞口(每步 20%,先减永续;处于 Broken 的 group 一并减,§4.8);原比率作交叉校验(≥ 0.8 → 至少 L2)。旧的比率分档在默认值下 L1 到强平只剩约 0.4% 的价格空间。参数唯一归属 [hft-risk](../crates/hft-risk/README.md),设计理由见 [07 §6](07-策略层.md)。组合携带在持仓币普涨 50–60% 时永续所就接近强平,所以这一条不能只靠告警。
- 自身强平、ADL、交割 → `ExternalFill`(入账、更新 LegTracker、P0、通知策略;策略截止内未处理 → 执行层平掉多出的一腿)。人工网页成交 `ExternalFill{Manual}` 不做引擎默认处理(不自动平),该 cell 置 `manual_hold`——补腿、ResidualTrim、外来成交默认处理与自动平仓计时一并暂停,`Note{ExecManualHold}` P1——由策略按自己的规则处理(组合携带把该 group 冻结到人工处理或两腿重新对齐);只有策略的非清除类动作、人工 `HedgeFix` 或引擎目标解除它(R8-11,[05 §4.3](05-CEX执行层.md))。下架公告与结算周期变化经控制命令 `VenueNotice` 进入(下架 → 该 inst CloseOnly + 通知策略)。

### 4.7 资金监控与划转建议(`treasury`,core)

跨所资金只告警并给划转建议,**不自动划转**,交易 key 不带提现权限。`treasury`(Python 冷进程)每小时汇总各账户各所的现金、现货库存、保证金余量与利用率,给出划转建议推到 ops_bot;人工执行后登记,使引擎视图与对账知道这笔在途资金。保证金危急时的自动动作只有引擎的分档减仓(§4.6),不靠划转。规格见 [python/treasury](../python/treasury/README.md)。

### 4.8 断腿(Broken)的预防与处置

独立评审指出([M0 独立评审 P0-2、P0-3](_work/review-2026-10-03-M0独立评审.md)):对冲所报价过期或滑点稍大时,对冲腿 3 s 内就会被判 Broken;Broken 之后只能人工 `/hedgefix`,夜间可能裸几个小时;而 L3 与 `Kill{flatten}` 反而跳过 Broken 的 group——最危险的裸永续空单不减。按 R8-8 修成"先少进 Broken,进了也有界":

**预防(开仓前与对冲时)**,检查链唯一归属 [hft-risk](../crates/hft-risk/README.md),执行规则归 [hft-exec](../crates/hft-exec/README.md)/[hft-oms](../crates/hft-oms/README.md):

1. 带 `LegLink` 的开仓检查链(B1)加入第二腿的报价有效性:第二腿 venue 的 BBO 连接健康(连接 Live、非重同步、最近任一帧——数据、pong、心跳——距今 ≤ `conn_liveness_ms` 2 000;BBO 连接每 `bbo_ping_ms` 1 000 主动 ping),否则拒(`LINK_STALE`)。第二次独立评审指出旧口径"BBO 年龄 ≤ 500 ms"在安静行情下会把对冲、自动平仓一起卡死([M0b 独立评审 P0-1](_work/review-2026-10-03-M0b独立评审.md)),所以对冲腿、风险递减单、自动平仓、L3 减仓都改用连接健康;`max_mid_age_ms` 退役。
2. 第二腿可负担性:现货买入腿要求该账户该 venue 可用计价资产 ≥ `link_notional × (1 + funds_buffer)`;永续腿要求可用保证金 ≥ `link_notional / 杠杆 × (1 + funds_buffer)`,杠杆取 `AccountConfigReport` 读到的实际值(`funds_buffer` 默认 0.05),否则拒(`LINK_FUNDS`)。
3. 对冲腿对手价偏离超过 `max_slip` 时按 `rr_max_cross` 上限改价照发 IOC,超过 `rr_max_cross` 才是门控拒绝(不计执行失败次数)。
4. 第二腿数量 = min(按成交净量算出的量, 当前该方向裸量);gw 对无法归属的成交暂存 `gw.unmatched_hold_ms`(默认 5 000)才发 `ExternalFill{Unknown}`——避免重复对冲。
5. 冷启动:`hedge_deadline_ms` 只按引擎运行时间(`engine_ns`,跨重启连续、停机不计)累计;闸门放行时对仍未对冲的链接先做一次 `SecondRetry`。

**处置(已经 Broken)**:

| 情形 | 动作 |
|---|---|
| Broken 持续 `broken_auto_fix_ms`(默认 120 000)且期间无人工 `HedgeFix`(且该 cell 不在 `manual_hold`;启动后的恢复期只在多出那一腿所在 venue 的对冲闸门子集满足且该 venue 已对账时计时,账户闸门未放行而裸量持续超限 → P0 `ExecGateHeldNaked`,R8-12) | 执行层自动发起**一次可执行的**"平掉多出的一腿":永续腿 reduce-only;现货腿卖出,数量取 min(库存, 可用余额);按 `max_reduce_notional` 切片,总量 ≤ 当前裸量;报价不可用、限速退避、对手价越过上限时先等待,门控拒绝与零成交重试,都不消耗这一次(R8-11)。成功 → `Note{ExecAutoFixDone}`(P1),cell 回到 Idle,`HedgeFailure` cap 仍需人工 `Resume`;交易所拒单、MinOrder、SignFlip、残余或可执行时长超过截止 → `Note{ExecAutoFixFailed}`(P0),保持 Broken 等人工 |
| 残余低于最小下单量,HedgeFailure 解不开 | 装配期校验 `dust_notional ≥ 交易腿最小名义的最大值`(不符退出 2,`DustBelowMinNotional`);仍出现时 Admin 用升级命令 `WriteOffResidual{account, group}` 对静止的 group(Broken 或非 Broken)核销多出那一腿的已成交裸量(移到未归属持仓,ledger `AdjustDelta::WriteOff`),并清零该 group 全部腿的残余,Broken 随之可解除(R8-11、R8-12) |
| 保证金 L3(`force_deleverage`)或 `Kill{flatten}`(`engine_flatten`) | 对 Broken 的 group 同样生效:先永续腿 reduce-only(`PerpFirst`,受 `max_reduce_notional`),再现货腿;`Kill{flatten}` 另置 `flatten_lock`。非 Broken 的 cell 只要求永续腿报价可用,另一所行情断开时退回串行路径 `SerialFallback`(永续先减,接受短时现货裸多 + P0);引擎单限价与名义按 `cap_cross_px` 与风控上限截取([05 §2.3](05-CEX执行层.md)) |
| HARD kill | 不做自动处置(HARD 的含义就是连风险递减单也拦);HARD 解除时对裸量超过补腿阈值(超 `tol` 且名义 > 尘埃线)、不在 `manual_hold` 的 group 判 Broken(`resolve_broken`);其他 kill 与锁存的解除、Recovery 的自动解除都不判,放行后的补腿与外来成交默认处理按新窗口处理(R8-12) |

自动处置只做一次、量以裸量为上限、与重试和补腿共用门控,所以不会自激成循环;"需要人工 `Resume` 才能恢复开仓"不变,且解除 `HedgeFailure` 要求该账户已无 Broken cell(否则 `CmdResult{Rejected}`)。自动解除 Broken 只按**已成交**裸量 × mark ≤ `dust_notional` 且无 Pending*/Unknown/在途判定(按含在途裸量判定时,自动平仓 IOC 一发出就会被当成已解除)。冷启动续接对冲只等对冲腿 venue 的闸门子集,超过 `resume_hold_max_ms`(30 000)→ Broken + P0。操作步骤归 [runbooks/incident-response](../docs/runbooks/incident-response.md)。

## 5. 控制面

### 5.1 控制环
- 单 SPSC 环 `ctl`:多个冷进程经本机 Unix socket 连到 hft-core 内 warm 核上的 `ctl-gateway` 线程(按 socket 对端 uid + 命令签发者鉴权),由它唯一写入控制环 → sequencer;命令带 `cmd_id`、`issuer`、`version`、`expires_tsc`。
- sequencer 把每条命令作为 `ControlCmd` 事件写 journal 后执行,并回 `CmdResult` 事件;冷进程从日志尾部读到结果——**命令与结果都可回放**。

### 5.3 ops-bot(Telegram)是纯冷进程
- 只读 journal 与 Parquet → 面板(仓位、PnL、直方图摘要、名单状态);发命令只经控制环。
- **权限模型修正**(现有 bot 用 `chat.id` 白名单、任何收通知者都能交易):按 `from.id` 鉴权,角色 = `Admin` / `Trader` / `Viewer`;**老板 = Viewer**:只读,外加唯一的写权限"紧急停止";登记过的群聊只放行权限表"群聊"列的命令——只读命令、Trader/Admin 的默认参数 `Kill`、Viewer 的 `/stop`(事故中在群里也要能停),其余回复"请私聊执行"(原设计"群聊只允许只读命令"已被 hft 取代);降级类命令(Kill/CloseOnly)门槛低于升级类,升级类(Live/加仓上限)需 Trader 且二次确认;所有命令与结果进 journal(审计)。
- **紧急停止**(R8-8、R8-9):ops_bot 命令 `/stop [account]`(中文提示"紧急停止"),不带账户 = 全局。发出的是非 HARD、不带 flatten 的 `Kill{Global | Account(a)}`:停开仓 + 撤挂单,对冲第二腿、平仓等风险递减单照常放行,老板按下停止不会把已成交的第一腿留成裸腿。确认只认同一人的预览(`cmd_hash` + TTL 60 s,不比对状态版本);hft-core 心跳过期或 ctl-gateway 不可达时改走 kill-switch 的本地触发入口(撤单 + 经 polkit 停 `hft-core@prod`,记"待补 Kill",kill-switch 另写停机标记;任一账户 MarginStress ≥ L2、有 Broken 或在途链接时只撤单,停引擎要第二次确认 `/stop … core`,§4.1)并 P0 告警值班交易员;`/stop` 失败或 10 s 无结果 → P0。Viewer 不能 `Resume`,不能发任何其他写命令;审计照常。
- 参数编辑与面板**按策略 schema 与策略描述符通用**:新增策略不改 ops_bot 代码;人工开平经通用的 `StrategyCmd`;模拟账户的仓位与报告标注"模拟"。多个账户是不同的 `AccountId`(各自 API key、限额与 kill),`/account` 切换的是 bot 的默认账户视图;模拟账户始终在独立的 `sim` 实例里(dev2 上长期运行;升级后与 `prod` 同机,[07 §9](07-策略层.md)),ops_bot 按实例读 journal、发命令,`/params <实例> set` 只写该实例的覆盖项。ops_bot 用 Python 实现,读 journal 经 `hft-py`,发命令经 ctl-gateway。
- 现有 cdex 的 Telegram bot(`/engine`、`/p /b /pl`、`/hedgefix`、`/pipeline` 等)继续服务旧框架;cdex 迁移(optional)时再把这些语义映射到命令集。

# 04 · 行情接入层(feed handler · 簿 · 时间戳)

> **实现以 [`hft/`](../README.md) 规格为准,本章是设计证据;冲突处以 hft 为准。** feed 运行时、快照任务与重同步归 [hft-venue](../crates/hft-venue/README.md),各所字段归 `venue-*`,事件布局归 [event-model](../docs/subsystems/event-model.md),raw journal 归 [journal-format](../docs/subsystems/journal-format.md);本章的示意结构只说明思路。
>
> 行情层运行在各 venue 线程里,把交易所的字节流变成带时间戳的定长事件,并在 sequencer 里维护每个合约的簿。各所通道选择依据 [research/02](research/02-exchange-connectivity.md),传输细节见 [03](03-网络与传输层.md)。
>
> **首次上线的行情范围**(2026-10-03 M0-e,R8-11):core 行情 = BBO、逐笔成交、标记价/指数价、资金费,以及 BBO 补帧(REST)。全量增量深度与 REST 快照重同步改为**可选扩展**(触发条件:某个策略需要全深度),规格保留;需要深度时优先用分档快照流(§5)。理由:首个策略 portfolio-carry 默认不订阅深度,却要为 6 个产品线实现增量深度、序号链与 REST 重同步;去掉它还直接减轻 IRQ 核上深度整点突发的负载([03 §3.1](03-网络与传输层.md))。下文 §2、§3、§6 中关于增量深度与快照重同步的部分,只在该扩展启用时适用。

## 1. 目标

| 指标 | 现状 | 目标 |
|---|---|---|

| 时间戳 | 事件时间/接收 UTC/单调 | 事件时间、交易所发送时间(若有)、**网卡 HW RX**、用户态 RX TSC、sequencer 处理 TSC 五个,全部进事件 |

## 2. feed 线程内部

```
(示意)
socket(非阻塞) ─▶ TLS 记录层(rustls,解密到复用缓冲) ─▶ WS 解帧(tungstenite,不复制 payload)
   ─▶ 分派(看前 32–64 字节判定消息类型/频道,不解析整条) ─▶ sonic-rs 直解到专用结构体
   ─▶ 归一化(字符串价格 → i64 定点,符号 → inst_id,时间单位统一 ns)
   ─▶ BBO 路由写 bbo 环(feed-bbo 线程);成交/标记价/资金费/分档快照(TopN)写 md 环(feed-md 线程;增量深度启用时也在这里)
   └─▶ raw journal 追加(payload 原样 + rx 时间戳 + 连接 id),不阻塞
BBO 补帧:feed-bbo ─SnapReq{Bbo}▶ snapreq-<venue>-bbo ─▶ snap-fetch(warm:请求、解密、解析)─▶ snap-<venue>-bbo ─▶ feed-bbo
         (不拆分的 feed:<venue> 用 snapreq-<venue>/snap-<venue>;环的存在条件归 hft-venue)
深度快照(只在增量深度启用时):feed-md ─SnapReq▶ snapreq-<venue> ─▶ snap-fetch ─▶ snap-<venue> ─▶ feed-md
```

- **多连接单线程轮询**:每个 feed 线程以固定顺序轮询自己的行情连接(下单连接在独立的 gw 线程,见 [01 §3.2](01-总体架构.md)),读到 `WouldBlock` 或短读即换下一条;承载 ≥ 3 个 socket 的 `Spin` 线程每圈先调一次 `epoll_pwait(timeout = 0)`,只读就绪的 socket(不阻塞、不唤醒任何线程);BBO 路由每连接每次 poll 至多 `feed.bbo_frames_per_poll`(默认 8)帧、连接之间按帧轮转,非 BBO 路由按 `feed.frames_per_poll`;没有调度器;收包是中断驱动(IRQ 在独占的 IRQ 核),热线程不做 busy poll([03 §3.1](03-网络与传输层.md))。
- **BBO 与行情分线程**(2026-10-03 五路评审 V5 P0-3):同一 venue 拆成两个任务——`feed-bbo:<venue>` 只承载 BBO 路由(可跨 venue 合并到一个线程),`feed-md:<venue>` 承载成交、标记价、资金费与(订阅时的)深度路由;升级主机上两者不得同线程。原设计"一个 feed 线程按 BBO → 其他路由的顺序轮询、REST 快照也在 feed 线程上解析"会让 BBO 在突发时排在 64 帧深度、40–80 µs 的快照解析与别的 venue 后面(约 0.4 ms),已被 hft 取代。dev2/c4 这类小主机可配 `routes = All`(同一任务),此时每处理完一条非 BBO 帧就 poll 一次全部 BBO 连接。
- **分派不解析**:交易所消息的类型字段位置稳定(Binance `"e":"bookTicker"`、OKX `"arg":{"channel":...}`、Bybit `"topic":`);先用 memchr/固定偏移取类型,再选对应结构体;`serde_json::Value` 禁止。
- **字符串价格 → 定点**:自写解析(逐字节),≈ 20–40 ns/字段;不经 f64。指数**按资产**取自 refdata(同一资产在所有 venue 同一 `px_exp/qty_exp`,跨所比较零换算;见 [13 R4](13-设计评审与优化.md))。
- **符号 → inst_id**:启动期由 refdata 建完美哈希/预热表;热路径用交易所消息里的符号做一次查表(或 SBE/数值 id 直接映射);refdata 在进程内只读,变化 = `ReplaceRefdata` 把新 blob 记进 journal、Drain、重启后生效(没有运行期热替换,[01 §4](01-总体架构.md))。
- **压缩**:一律关闭 permessage-deflate(OKX/Bitget 等可协商);若某所只提供压缩流,使用 `yawc` 且单独测成本。
- **心跳/重连**:venue 线程自己处理 ping/pong 与重连(不经 sequencer),但**连接状态变化是事件**(`ConnState{venue, conn, Up/Down/Resync}`),策略与风控据此降级。BBO 连接每 `bbo_ping_ms`(1 000)主动发 WS ping,保证盘口不动时也有回帧。BBO 视图的连接健康**按成员聚合**:每个 venue 的 BBO 连接占一个槽(`MAX_BBO_CONN_SLOTS = 8`),sequencer 为每个 inst 维护它的 BBO 连接成员位图 `bbo_member_mask`;SDK `Views::bbo(i)` 按值返回 `BboView`,`conn_up` = 任一成员 Up,`conn_live_tsc` = Up 成员的最大值,`resync` = 成员或簿的重同步标志之或,另带最近一条 Bbo 的 `rx_tsc` 与 `hw_rx_ns`。原写法"按最近一条 Bbo 所在连接投影健康"会在赛马胜出的连接退役(Binance 每 24 h 强断)后把安静 inst 判为不可用(五路评审 V5 P1-2 / V1 P1-3)。

## 3. 事件类型与归一化语义

名称与字段是原始设计草图;kind 编号、字段与布局以 [event-model](../docs/subsystems/event-model.md) 与 [hft-event](../crates/hft-event/README.md) 为准(例如深度默认产出一条交易所消息一条的 `L2Batch`,逐档 `L2Delta` 默认不产出;资金费事件名是 `Funding`)。

| 事件 | 字段 | 语义约定 |
|---|---|---|
| `Bbo` | bid/ask px、qty、`ex_ts`、`update_id` | 所有所的最优一档;qty 为该档总量;`update_id` 用于去重与序号 |
| `L2Batch`(草图里是逐档 `L2Delta`) | 一条交易所深度消息的全部档位变化、`first_id/last_id` | 增量(可选扩展,增量深度启用时才产出);序号连续性由 feed-md 校验,断裂则发 `Resync` |
| `L2Snapshot` | N 档数组 | `origin = TopN`:分档快照流的每条消息(core 的深度形态,簿按"整替换"应用,无序号链);增量深度启用时另用于订阅初始化或断裂恢复(REST 快照经 snap-fetch,或带快照的频道);seq 段滚动时的引导块与关键帧(`L2Snapshot{Keyframe}`,周期 `keyframe_period_ms` 默认 300 000,各 Live 簿均摊到同一周期)由 sequencer 从本地簿镜像导出,**不发 REST**(修复 WAL 无快照被隔离 84% 的问题;关键帧规则见 [08 §2](08-数据面与回放.md)) |
| `Trade` | px、qty、side(taker)、trade_id、`ex_ts` | aggTrade 与 trade 各所统一为 taker 方向 |
| `Funding` / `MarkPrice` / `IndexPrice` | 值、下次结算时间、**实际结算周期** | 携带类策略的输入;周期变化(交易所会把高波动币改成 1 h)由 `hft-strat-lib` 的资金费统计检测;下架与周期变更公告另经控制命令 `VenueNotice` 进入 |
| `Liquidation` | 若所提供 | G 类策略 |
| `ConnState` | up/down/resync/rotated | 风控输入 |

时间戳字段:`ex_ts_ns`(交易所事件时间)、`ex_send_ns`(交易所发送时间,若有,如 Binance `T` vs `E`)、`hw_rx_ns`(网卡时间戳,SO_TIMESTAMPING;不可用时为 0)、`rx_tsc`(用户态读到最后一个字节)、`proc_tsc`(sequencer 取出)。这五个时间戳是 [09](09-可观测性、风控与控制面.md) 里所有延迟分解的来源;**不再把不同数据集的延迟混算成一个"订单簿延迟"**(AGENTS.md 的教训)。

## 4. 簿(sequencer 拥有)

- 每 inst 一个 **按 tick 索引的稠密数组簿**:`levels[(px − base) / tick]`,窗口覆盖 mid ± W 个 tick(W 按合约波动配置,例如 2000),窗口外的档位落入两端的"溢出桶";mid 漂出窗口一半时重新居中(O(W) 复制,罕见)。这是 hftbacktest ROI 向量簿与 Optiver "sorted vector 胜 node-based 容器"的同一结论。
- 缓存 `best_bid_idx/best_ask_idx`,更新后按需向内扫描找新最优档(通常 ≤ 几步)。
- `Bbo` 与 `L2` 两路都维护:触发型策略(如 A 类)只看 `Bbo`(最快、最频繁);执行层的切片(按弱侧可见深度)、冲击估算与 B 类看 `L2`;两路序号独立。core 行情不含增量深度,所以执行层切片的可见深度在该 inst 有 TopN 订阅时读簿,否则用 BBO 顶档的量(R8-11);portfolio-carry 的快速部分不订阅深度。
- 每个簿有 `state: Live | Stale | Resyncing`;`Stale` 期间策略对该 inst 自动不开仓,`ImpactModel` 返回"不可用"。
- **报价新鲜度按连接健康判定,不按"该 inst 最后一次变化"**([M0b 独立评审 P0-1](_work/review-2026-10-03-M0b独立评审.md)):连接 Live、非重同步、`now − conn_live_tsc ≤ conn_liveness_ms`(2 000)即有效,报价取该连接上的最新值(盘口无变化也有效)。安静的 inst 几秒无推送不算过期;对冲腿、风险递减单、自动平仓、L3 减仓与带 `LegLink` 开仓的第二腿检查都用这一判定([05 §3](05-CEX执行层.md));旧的 `max_mid_age_ms` 退役。
- 不做 L3;若日后 B 类策略需要队列位置,只对少数合约开 L3(Binance 现货 SBE 有逐笔;合约没有)。

## 6. 断裂、恢复与重连

第 1、2 步只适用于可选的全量增量深度;分档快照流(TopN)没有序号链,断线只需重连重订,下一条快照即整替换;BBO 在全部 BBO 连接都断过时经 snap-fetch 补帧(REST),该 inst 下一条转发的 `Bbo` 结束补帧。

1. feed-md 检测 `update_id` 断裂 → 发 `ConnState::Resync{inst}` → sequencer 把簿置 `Stale`。
2. feed-md 经 `snapreq-<venue>` 环请 warm 任务 `snap-fetch` 拉 REST 快照(snap-fetch 拥有快照用的 REST 连接,负责请求、读取、解密与解析,同时在途的快照数有上限),解析好的分片经 `snap-<venue>` 环交回;feed-md 把原始响应写进 raw journal(标 REST)并驱动重同步:快照 → `L2Snapshot` 事件 → 簿重建 → `Live`。或者重订阅带快照的频道。REST 快照的系统调用与解析因此不在任何热线程上。
3. 全连接断开:BBO 路由的备用连接已在线(双连接同订阅赛马,feed-bbo 按 `update_id` 去重,先到为准)——**BBO 双路是默认配置**,单路是降级。深度、成交、标记价路由是**单路**,断开即重连 + 重同步。原设计"L2 也双路去重是默认"已被 hft 取代(两路批次能否一致各所待实测,收益只在断线那一刻),L2 双路合并降为可选扩展。
4. **重连必须伴随重同步**,没有例外(混沌测试必测)。

## 7. raw journal

- feed(与 gw)线程是各自 raw journal 的唯一写者;记录 = `RawRx{conn, rx_tsc, hw_rx_ns, len, payload}`(布局归 journal-format);按 UTC 整点或大小安全阀滚动。**raw 段不要求自足**:滚动时不写快照、不请求 REST;从 raw 重跑解码器时,用同一 UTC 小时 seq 段的引导块作种子。原设计"raw 段滚动时由 sequencer 触发 `SnapshotAtRoll`,把全部订阅的簿快照请求一次"已被 hft 取代——它会在整点制造一次 REST 风暴,而 seq 段的引导块已经能从本地簿镜像自举([08 §1](08-数据面与回放.md))。
- 用途:解码器金样测试、协议变更时重跑解码、争议成交取证、研究用的"未归一化真值"。
- 成本:写进 RAM 热段(大页;dev2 为 tmpfs),每条 ≈ 50–200 ns;persist 线程旁路复制到盘。原设计"顺序 mmap 写、磁盘 IO 由内核回写"已被取代:文件型 mmap 的页被回写后重新写保护,下一次写会在热线程上触发毫秒级缺页([13 R2](13-设计评审与优化.md))。

## 8. 与现有 collector 的关系

- **collector 保持独立**:它继续按 collection-policy 采集 150+ 合约 × 多所、产出 `book_ticker.v2` 等 Parquet,服务研究;新框架不吸收它。新框架的 raw + seq journal 只记录交易所需的订阅,订阅集合由交易需要决定、不为研究扩大(扩大订阅会增加热线程负载);冷进程 `journal-archiver` 只归档交易 journal,写独立 S3 前缀,不要求与 collector 的 schema 兼容,两者按共同的时间戳语义(交易所事件时间、接收 UTC)对齐。
- 两套解码器并存是接受的代价:collector 的 raw WAL 作为新框架解码器金样的来源之一,并有离线的"同一时段两边 BBO 序列一致性"对照。2 核主机上两者不长期同时运行,研究窗口按 collection-policy 单独排期。
- 现有 `crates/binance|okx|bitget` 里的字段知识(时间戳语义、序号规则、快照对齐流程)是直接可迁移的资产;实现改为 `sonic-rs` 专用结构体 + 同步非阻塞 socket。
- AGENTS.md 的时间戳纪律(事件时间、交易所发送时间、接收 UTC、接收单调分开)在事件头里成为强制字段。

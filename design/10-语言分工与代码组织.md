# 10 · 语言分工、代码组织与工程纪律

> **实现以 [`hft/`](../README.md) 规格为准,本章是设计证据;冲突处以 hft 为准。** 构建剖面、CI 工作流与分钟预算归 [development.md](../docs/development.md),测试金字塔与上线门槛归 [testing.md](../docs/testing.md),分层与依赖规则归 [crates/AGENTS.md](../crates/AGENTS.md)。
>
> 依据:[research/04 开源框架与模式](research/04-oss-frameworks-and-patterns.md) 的决策表与热路径编码清单。本章回答"用什么语言写哪一层、仓库怎么切、怎么保证不退化"。

## 1. 语言决策

| 层 | 语言 | 理由 | 明确不用 |
|---|---|---|---|
| 热路径(venue 线程、sequencer、执行层、OMS、风控、策略包、journal)、模拟撮合;chain-core(optional,cold tier) | **Rust** | 无 GC、零成本抽象、`sonic-rs`/`rustls`/`tungstenite`/`revm`/`disruptor`/`iceoryx2` 全部成熟;内存安全对一个管真钱的系统是硬收益;团队与 AI 协作效率高 | C++:没有任何证据显示 C++ WS/TLS/JSON 栈快于 Rust 对应物(04 §4);两套语言的工具链与招聘成本不值 |
| 厂商网卡库绑定(可选:裸金属 + Onload) | **C(仅 FFI)** | Onload `ef_vi`/TCPDirect、XLIO 是 C 库;XLIO/Onload 的 socket 加速是 `LD_PRELOAD` 级,Rust 代码不用改;`ef_vi` 直通才需要写几百行 `unsafe` 绑定 | 自写用户态 TCP/TLS |
| 链节点(optional) | Go(bsc-geth,外部进程)/ Rust(reth-bsc,评估中)/ Rust(Solana Agave) | 只作为进程运行,不链接 | 自研节点 |
| 研究与模拟结果分析、选币/名单流水线、资金监控、运维 bot、面板 | **Python** | Polars/DuckDB/Jupyter 生态;通过 PyO3 读 journal、调用 Rust 记账库;不做回测 | Python 出现在任何事件级路径;策略的慢计算(属于策略包的 `Model`,Rust) |
| 内核调优、部署 | Bash + systemd 单元 + tuned/ansible 清单 | 与现有 releasectl 纪律一致 | — |
| 智能合约(optional) | Solidity(BSC 原子 swap 合约 `SwapGuard`) | 最小合约,Foundry 测试 | — |

**一句话:Rust + Python 两种语言,C 只以 FFI 形式出现,不写 C++。** "不限语言"的自由用在选最合适的库上,而不是多养一套工具链。

跨语言的数据格式只有一份实现:策略参数的编解码在 SDK(Rust),Python `pipeline` 经 `hft-py` 调用它,不写纯 Python 编码器;schema 统一由 `hft-core schemas --out <dir>` 导出为 `<kind_id>-<name>.schema.json` + `index.json`([M0 独立评审 P1-8](_work/review-2026-10-03-M0独立评审.md))。

## 2. 仓库与 workspace 布局

独立 workspace `hft/`(规格骨架在 [`../hft/`](../README.md),每个目录的 README 是该组件的实现规格;组件取舍见 [13 §5](13-设计评审与优化.md))。规格修订期间在 `E:\trading\hft`;实现开始时复制到 `E:\trading` 之外的新目录、在负责人个人账户下建私有仓库 `Fiora-gwx/hft`(2026-10-07 负责人决定,不建 GitHub 组织),CI(免费的 GitHub 托管 runner,与旧项目一致,见 §5)是唯一的构建与测试环境,服务器不编译([11 §2](11-实施路线图.md))。可选组件(`venue-gate`、`venue-bybit`、`venue-kucoin`、`venue-hyperliquid`、`hft-chain-evm`、`hft-ext-proto`、`hft-amm`、`hft-chain-solana`、`apps/chain-core`、`apps/chain-grpc-relay`、`apps/mock-exchange`、`contracts/`)的规格冻结(`status: frozen`),不随 core 规格同步,解冻时先按 core 规格复核(R8-10)。不与现有 collector 混编;collector 保持独立服务研究,它的发布链不受影响。

依赖方向只能向下:

- L0 `hft-types ← hft-refdata ← hft-event`,被所有人依赖。
- `hft-strategy-sdk` 只依赖 L0。L1 引擎 crate(`hft-oms`、`hft-ledger`、`hft-risk`、`hft-exec`)**可以**依赖 SDK(为了用 SDK 定义的视图类型与意图类型);`hft-sequencer` 依赖 SDK 与 L1。
- `hft-strat-lib` 只依赖 L0 + SDK;`strategies/*` 只依赖 SDK 与 `hft-strat-lib`。
- **任何引擎 crate 都不依赖 `strategies/*`**;策略的装配只发生在 `strategies/registry` 唯一一次 `strategy_set!` 调用里,`apps/hft-core`、`apps/replayer` 依赖它(新增策略 = 新 crate + registry 里加一行)。**`hft-testkit` 不依赖 registry**(含 dev 依赖;否则引擎 crate 的测试会经 testkit 间接依赖策略);需要真实策略的集成测试放在 `strategies/registry/tests/` 或 `apps/hft-core/tests/`([M0b 独立评审 P2](_work/review-2026-10-03-M0b独立评审.md))。
- `venue-*` 只依赖 `hft-event/hft-refdata/hft-types/hft-venue-proto`(不依赖 `hft-net`、`hft-venue`、`hft-sequencer`);`apps/*` 只装配。

机检:`cargo xtask deps`(依赖图,机器可读形式 `tools/xtask/deps.toml`;引擎 crate 的 dev 依赖同样检查)、`cargo xtask doc-check`(引擎 README 不出现策略族名(含小写 `cdex`)或某个策略的规则数字;同样扫 `python/` 目录,框架代码里不得出现策略族名;`scope` 与 [11](11-实施路线图.md) 一致)、`cargo deny` + workspace lints;CI 的**解耦门槛**——新增第二个测试策略时引擎 crate 的 diff 必须为零;解耦门槛的豁免标签需 Admin 批准,并在 CI 报告中逐条列出。分层与依赖规则的唯一归属是 [crates/AGENTS.md](../crates/AGENTS.md)。

## 4. 热路径编码规则(强制,CI 检查其中可检查的部分)

**线程**:热角色是可轮转的任务(`poll_once`/`step`,非阻塞);线程布局由配置的线程计划决定——升级主机(默认 `c32`,`c16` 有条件)与 `metal` 上 prod 的每个热任务(seq、feed-bbo、feed-md、每个 gw)一个 OS 线程、`sched_setaffinity` 到隔离核、永不 `park/await/sleep`、等待一律 `spin_loop()`(承载 ≥ 3 个 socket 的行情线程每圈可调一次 `timeout = 0` 的 `epoll_pwait`,不阻塞,T7),ENI-B 的 IRQ 独占一个不放线程的核;`dev2`(2 核)上多个任务合并到一个线程,全部任务空闲后按 `IdlePolicy` park(任务内部仍永不阻塞);下单连接独占 `gw-<venue>` 线程(T8)在任何主机类上都没有例外,核不够就换更大的主机类;同机的 sim 实例只用非隔离核;单写者;不读系统时钟(TSC 一次读取随事件传递);cache warming(gw 线程空跑模板与加密路径)是可选项,默认关。

**内存**:启动期预分配一切(对象池、订单槽、环、解析缓冲、簿数组);热路径 `Vec::push` 超容量视为 bug;显式 hugetlbfs + `mlockall`,启动时预触摸;THP 在 Graviton 上设 `madvise`(GRUB 不写 `transparent_hugepage=never`,它是 hostprobe 的 required 项;x86 metal 剖面才关 THP,[02 §4.3](02-硬件与托管方案.md));`#[repr(C)]/#[repr(align(64))]`,高频写字段与只读字段分离;数组索引优先于 HashMap。

**数值**:价格/数量 i64 定点(按资产指数)、乘积用 i128、`#[repr(transparent)]`;策略快速部分与执行层无 f64,策略慢速部分(`Model`,advisor 线程)允许 f64 但必须确定;`enum + match` 编译期分派,不用 `dyn`;JSON 专用结构体、借用字段;事件结构体内无 `String`/`Vec`。

**控制流**:热路径无 `panic!/unwrap/expect`,发布剖面 `panic = "abort"`(`ci` 剖面显式 `unwind`,见下);错误聚合成位标志一次判断;冷操作(日志、指标)只写定长记录经环发出;依赖冷配置的分支改为启动期特化。

**构建**(剖面的唯一归属是 [development.md](../docs/development.md) 构建剖面):`release` = thin LTO、`codegen-units = 16`、`panic = "abort"`、关 overflow-checks、`debug = "line-tables-only"`;`release-hot` = 在 `release` 上改 fat LTO + `codegen-units = 1`,**只用于正式版的 `hft-core` 与 `kill-switch`**;`ci` = 不做 LTO、`codegen-units = 16`、不增量,开 debug-assertions 与 overflow-checks,显式 `panic = "unwind"`(测试要 unwind,否则依赖可能被编两遍,R8-11),workspace 成员 1 级优化且无调试信息、依赖仍 3 级(M2 测试树的构建撑破 PR 时限后改);`bench` 与 `release-hot` 相同,只用于参考机与正式版基准——PR 的基准冒烟用 `ci` 剖面(每个基准二进制都做 fat LTO 会撑破 PR 的分钟上限,W4 P1-11);`-C target-cpu=<目标实例族>`;PGO 用真实重放日志训练(可选)。原稿"全部 fat LTO + `codegen-units = 1`"已被取代:`ci` 剖面继承 fat LTO 会让每个测试二进制都做 LTO,免费 CI 的分钟数撑不住(五路评审 V4 P0-1)。

完整清单见 [research/04 §9](research/04-oss-frameworks-and-patterns.md)。

**累计门槛 ③④ 在服务器上跑**(R8-10):原设计"不在 `dev2` 上跑 fuzz 或 DST、③④ 按 CI 每夜累计、账本存 CI artifact"已被取代——按 Trading 仓库的实测用量,免费 CI 要 4–8 个月才攒得够。现在 CI 只构建验证包,服务器仍不编译:dev2 上 `hft-verify.service`(oneshot + timer,根级 `hftbatch.slice`、`Nice=19`,全部 hft 单元中最先被杀;`ExecCondition=` 查护栏标志、联调窗口标志与 `hft-core@prod`;只装在主机清单 `verify = true` 的主机上)以最低优先级常态运行。批处理 slice 不设 `CPUQuota`,设 `CPUWeight=idle`(cgroup `cpu.idle`;线程级 SCHED_IDLE 不跨 cgroup 生效,所以放在根级 `hftbatch.slice` 而不是 `hft.slice` 之下),I/O 用 `IOReadBandwidthMax=`/`IOWriteBandwidthMax=`——`IOSchedulingClass=idle`/`IOWeight` 在 EBS 的 `none` 调度器下不起作用,CPU 配额又会让整机 PSI 触发护栏(W4 P0-1、P1-5;X4 N-P1-1)。升级主机只在 M7 期间、门槛 ⑩ 的 7 天测量窗口之外运行;正式实盘开始后升级主机不再运行,后续版本在 dev2 上继续。计量与账本:③ 按子进程 CPU 时间计,单输入超时按线程 CPU 时间判定,`ASAN_OPTIONS=quarantine_size_mb=16` 加 `-malloc_limit_mb`(否则 ASan 默认 256 MB 的 quarantine 在受限主机上撞内存上限,产生假"发现");受限主机上的 OOM/超时先记"疑似",CI 以默认限额复现才清零;SIGABRT/SIGSEGV 一律算失败;只有失败清零,漏跑不清零;跨版本只累计 `path_digest` 与候选版本相同的运行;账本丢失用 `hft-verify ledger rebuild` 从本机与 S3 的运行记录重建;开正式实盘所用版本的验证包本身还要按 testing 的补跑量补跑、零失败。数值(CPU·h、种子数、运行次数)只在 testing §8。规格:`hft-verify` 归 [tools](../tools/README.md),账本规则归 [testing.md §6](../docs/testing.md),阈值归 testing §8,部署归 [deploy](../deploy/README.md)。

**分钟预算(GitHub Free 个人账户)**:hft 仓库是负责人个人账户下的私有仓库 `Fiora-gwx/hft`(2026-10-07 负责人决定,不建组织;负责人 = Admin,老板是协作者——个人私有仓库没有只读角色,老板实际有写权限,已知取舍),私有仓库每月 2,000 分钟**与 Trading 仓库共享**,artifact 存储 500 MB、每仓库 cache 10 GB。分配:每夜只做回归冒烟,发布、开发构建与验证包构建有预留,其余给 PR 与 `main` 推送(分钟数归 development);**额度规则**(R8-11、R8-12):阈值、用量估算(GitHub 的用量接口已关闭,quota-gate 按作业时长自估、每周与计费页对账)、Admin 覆盖、过阈值后 PR 的作业范围与额度耗尽时的应急出包路径,唯一归属 development;额度一旦用尽,个人账户全部私有仓库(含 Trading)的 Actions 全停到下月,到月初前无法在 CI 出包,所以靠阈值与每周对账预防。M1 第一周按实测重算并写进 ops-log。免费个人账户的私有仓库没有受保护分支,所以生产安全以"发布工作流 `preflight` 证实该 SHA 的 `ci.yml` 全绿且 `decoupling-gate` 通过"为准。`ubuntu-24.04-arm` 在个人私有仓库可用已由 Trading 8–9 月 20 次成功运行证实;hft 同在该账户,计费倍率 M1 第一周核实。CI 拉 S3 fixtures 时只对需要的作业开 GitHub OIDC(`id-token: write`),扮演只读 fixture 桶的角色(`[需授权]` IAM)。预算表唯一归属 [development.md](../docs/development.md);不够时减批量,而不是加付费资源或自托管 runner。原稿"与 Trading 仓库共享 2,000 min、每夜 x86 ≤ 20 min、发布预留 ≥ 300 min"已被取代。

## 6. 工程纪律(延续并扩展 AGENTS.md)

- **发布**:CI 按 tag 在 `ubuntu-24.04-arm` 托管 runner 上产出 aarch64 不可变归档 + SHA-256 + `RELEASE.json`;冷部署;保留一个已验证回滚版本;服务器只安装制品,不编译。新增:**内核参数、ethtool、IRQ 亲和、hugepages、tuned profile 全部随发布归档**("调优即代码"),激活时校验实际生效值并写入日志首条 `HostProfile` 事件。
- **配置**:交易所静态参数、策略参数、名单都有版本与哈希;热进程启动记录全部版本到 journal;回放时用日志里的版本而不是当前文件。
- **变更类别**:代码/协议/内核参数/策略包代码 → 完整 CI + 发布;策略参数/名单/运行模式 → 控制环命令(参数按 schema 校验),不触发构建。
- **可观测门槛**:任何 p99 预算被突破(见 [09](09-可观测性、风控与控制面.md))自动告警;连续 3 日突破视为回归,阻断发布。
- **ADR**:每个重大取舍(例如"tungstenite 同步而非 tokio"、"chain-first")一页 ADR,记录当时的证据与推翻条件。

## 7. 人力与节奏(建议)

- 核心 2 人 + AI 代理:一人负责地基、交易所接入与 sequencer/OMS/风控,一人负责策略 SDK、执行层、模拟系统、首个策略与冷进程;Python 组件由 AI 代理完成并由人复核。
- 按 [11 交付计划](11-实施路线图.md) 的里程碑 M0–M8(含 M1.5 延迟探针)推进,不设周次;每个里程碑必须带测试与回放结果(`dev2` 上的直方图只记录;M1.5 起每个里程碑末有参考机 `bench-gate --reference` 的结果;延迟验收在统一升级后),不接受"功能完成但没测"。

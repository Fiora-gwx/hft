# 07 · 策略层

> **实现以 [`hft/`](../README.md) 规格为准,本章是设计证据;冲突处以 hft 为准。**
>
> 策略层由四部分组成:**策略包**(`strategies/<name>`,一策略一 crate)、策略唯一依赖的稳定接口 **策略 SDK**(`hft-strategy-sdk`)、可复用的 **执行层**(`hft-exec`)、通用规则构件(`hft-strat-lib`)。策略包的快速部分在 sequencer 线程里是纯状态机(不做 I/O、不分配、不读系统时钟),慢速部分在 advisor 线程里运行;两者的输出都进 journal,回放确定。本章讲为什么这样切、边界划在哪里、我们要跑哪些策略;接口与规则的细节在 `hft/` 的 README:[hft-strategy-sdk](../crates/hft-strategy-sdk/README.md)、[hft-exec](../crates/hft-exec/README.md)、[portfolio-carry](../strategies/portfolio-carry/README.md)。

## 1. 我们要跑什么

新框架首要服务 CEX-CEX(ccex)。cdex 继续在旧框架运行,迁移不急(§8)。

| 策略 | 腿 | 边来自哪里 | 延迟敏感度 | scope |
|---|---|---|---|---|
| **组合携带**(`portfolio-carry`) | 永续空 × 现货多,多币截面组合;两腿在不同交易所 | 正资金费 + 入场基差 − 两腿成本 | 中:调仓是分钟级,但两腿一致性要求第二腿在同一事件内出环 | **core,首个实现** |
| 跨所永续 × 永续资金费差 | 两所永续反向 | 两所资金费差 | 中 | 可接入(新策略包 + 配置,引擎不改) |
| 同所现货 × 永续 | 同一所现货多 + 永续空 | — | — | **不做**(R8-8,见下文) |
| 跨所价差吃单(`cross-taker`,原 A) | 快所行情 → 慢所吃单,快所对冲 | 传播延迟:Binance 先动,慢所报价过时 10–21 ms([现状测量 §3.4](现状测量与升级分析-2026-10-01.md)) | **极高** | optional |
| 挂单 + 吃单对冲(`maker-taker`,原 B) | 慢所 post-only 挂单,成交后快所对冲 | 被动收窄价差;撤单速度决定逆向选择损失 | 高 | optional |
| cdex(`cdex`,原 D、E 及 C 的 CEX-DEX 形态) | Binance 永续空 + BSC 池子现货多;股票代币是参数变体 | 池子相对 CEX 过时 + 资金费 | 高(链上腿块级) | optional,见 §8 |
| 链上 backrun(原 F) | 单腿链上原子套利 | 薄池尖峰回归 | 块级 | optional,在 chain-core 里,见 [06 §7](06-链上执行层.md) |
| 其他事件驱动(原 G) | 预测市场、清算瀑布、上币公告 | 事件 | 各异 | 研究中 |

方向只做"空永续、多现货";反向(需要现货借币)不做。

**不做同一交易所的现货 × 永续**([round8-decisions R8-8](_work/round8-decisions.md)):一个账户在同一交易所只用一个市场(现货或永续)。原因是 OKX 统一账户、Bitget UTA 这类账户里现货与永续可能共用一个钱包,而 ledger、SDK 权益视图、风控与模拟都按 venue 记现金——同一笔 USDT 会在两个 venue 各记一份,策略按约 2 倍资金分配,第二腿余额不足被拒,留下裸腿([M0 独立评审 P0-1](_work/review-2026-10-03-M0独立评审.md))。与其给全系统加"余额域",不如在入口把这种组合排除:refdata 加载时一个 `AccountId` 的 venue 集合里不得有两个同交易所的 VenueId(`SameExchangeMarkets`,Sim 账户同样适用),`SetParams` 校验同一 group 的两腿不在同一交易所(`InvalidArgs{SameExchangeLegs}`)。因此系统不建模余额域。

组合携带的盈亏主要由手续费与滑点、两腿一致性、跨所保证金、资金费核算决定,不由主机内微秒决定。但框架的总目标仍是**延迟优先,其次正确性与可扩展**([00 §1](00-目标与延迟预算.md)):两腿间隔、A/B 类策略都需要微秒级栈,而这套栈对携带类策略是"免费的上限"。对携带类真正要紧的是执行层与风控的正确性——这是本章 §4–§6 的重心。

## 2. 策略包:快速部分 + 慢速部分 + 参数 schema

### 2.1 为什么要解耦

旧规格里新增或修改一个策略要动引擎:全部策略在一个 crate 的封闭枚举里;参数是封闭枚举 `ParamsBody`(新增策略要改配置工具与控制协议);慢计算要在公共事件 crate 登记 `AdviceKind`,载荷固定 6 个整数;sequencer 里写死了资金公式 `wallet × leverage × deployable`;OMS 的补腿器写死了 cdex 的 5% 阈值与残余清理规则;流水线按策略写死。每改一次策略就要重新验证引擎,这会让"慢慢研究策略"变得不可能。

所以定为硬要求:**新增或修改策略不改任何引擎 crate**(sequencer、OMS、risk、ledger、exec、journal、venue、event、refdata、ctl);装配处只加一行注册;参数热更新,策略代码变化走正常发布。

### 2.2 策略包的三部分

| 部分 | 运行位置 | 规则 | 例子 |
|---|---|---|---|
| **快速部分**(`Strategy`) | sequencer 线程,`on_event` | 不分配、不阻塞、不读系统时钟、不 panic、无 `dyn`、**无 f64**;时间只来自事件 | 读模型产出的目标权重与带宽,算出每个 group 的目标仓位,发目标意图;处理成交、执行进度、风控事件 |
| **慢速部分**(`Model`) | advisor 线程(warm,不占热核) | 允许 f64 与分配;**必须确定**:只用事件时间、无 I/O、无系统时钟、无 `HashMap` 迭代;输入 = 它订阅的 journal 事件,输出 = 不透明载荷的 `Advice`(≤ 4096 B,`local_kind` 由策略自定) | 截面打分与分配(`powf`、迭代封顶)、168 h 分位带、资金费统计、冲击曲线 |
| **参数 schema**(`ParamSchemaDesc`) | 编译期常量 | 每个字段有名称、单位、范围、默认值、是否按 group 覆盖、说明 | 配置工具、控制协议、ops_bot 按 schema 通用处理,新增策略不改它们的代码 |

- `Advice` 由 advisor 写入 advice 环、被 journal 记录;回放时从日志读,不重算——所以慢速部分可以用浮点,确定性仍成立。引擎不解释载荷,只按策略 id 路由。
- **Advice 按依据判新鲜,不按到达**:`EventRef::Advice` 带 `basis_seq`/`basis_tsc`(模型算这条建议时依据的最后一条 journal 记录),策略按依据时刻判过期;跨启动的 Advice 只由策略按 `basis_seq < Now.boot_seq` 判过期(sequencer 不加标志)。否则 advisor 落后或重启重放时,旧数据算出的建议会被当成新的;advisor 滞后(按 `engine_ns` 差计)超过 `advisor_max_lag_ms`(默认 5 000)时写 `AdvisorLag`(定义唯一归属 hft-event,每 10 s 至多一次),watchtower 报 P1([M0 独立评审 P1-1](_work/review-2026-10-03-M0独立评审.md))。
- **跨重启的时间用引擎时间**([M0b 独立评审 P1-3](_work/review-2026-10-03-M0b独立评审.md)):`Now.engine_ns` 是跨重启连续、停机不计的引擎时间(由 journal 的运行区间累加,确定)。策略、`hft-strat-lib`、ledger、risk 的持久状态(确认窗口起点、节流、再入场冷却、保证金截止等)一律存 `engine_ns`;TSC 只在单次启动内使用。否则重启或换机后 TSC 基准变了,存下来的 TSC 截止会立刻到期或永不到期。
- advisor 在自己的 warm 线程上(dev2 上是一个不绑核的低优先级线程;升级主机上另占一核,不与 persist 同核,[hft-core 线程计划](../apps/hft-core/README.md#线程计划)),模型计算切片,每次 `poll_once` 最多一个模型步骤(≤ 1 ms);检查点按 group 分块写出(SDK `Model::snapshot_chunk`,每次 poll 只写一块)。原稿"advisor 与 ctl-gateway 同线程、切片是为了不饿死 ctl-gateway"已被 hft 取代。
- **Model 内存由策略声明**(R8-10):SDK `Model::mem_bytes(p, n_groups)` 与 `Model::snapshot_bytes(p, n_groups)` 给出上界,hft-core 按主机类与实例配置 `advisor.mem_budget_mib`,装配时求和超预算 → 退出 2,`SetParams`/绑定时超预算 → `ParamInvalid{ModelMemBudget}`。所以"新增策略零改动"也包括 hft-core 的规格,最多需要运维调大预算(否则改一个分位窗口参数就可能把 advisor 撑爆)。
- **Model 检查点不随日常运维失效**:组合携带的 168 h 分位每次从空起步要约 42 h 才能开仓,所以 advisor 定期(`advisor.model_checkpoint_ms`,默认 600 000)把 Model 状态写到冷盘,重启时恢复并从检查点的 `last_seq` 重放 journal 追上。检查点键只含 `kind_id`、`Model::LAYOUT_VERSION`(策略声明的状态布局版本)、`schema.id`、`strategy_instance`、`last_seq`;**改参数、换 refdata、发新版都不使它失效**(参数变化随重放经 `model_on_params` 重新应用)。只有布局版本或 schema 变化、文件缺失或损坏才丢弃(`Note{ModelCheckpointDiscarded}`)。检查点只是预热优化,不是正确性条件——Advice 是 Input,回放从不需要 Model 状态。**检查点分两节**(R8-11;W2 P1-4):原始样本节(两侧基差样本环、资金费环、K 线补到的时刻;布局由 `ModelLayoutDesc` + `LAYOUT_VERSION` 管)与路径状态节(分位带及其时刻、平滑窗、上次发送的载荷摘要等路径依赖的派生状态;自带 `Model::PATH_VERSION`,接口 `Model::snapshot_path`/`restore_path`,作为检查点第一块写出)。改打分逻辑只需升 `PATH_VERSION`:恢复时只丢路径节、按原始样本重算派生状态并写 `Note{ModelPathReset}`,仍不丢 168 h 统计;有路径节时"检查点 → 恢复 → 续算"与连续运行逐字节相同,每日 recompute 照常要求逐字节一致(路径节被丢弃的当日从下一个分位带边界 + 平滑窗长度之后开始比较)。前提是 Model 的每项状态都在两节之一;来自 `Notice` 的下架等公告状态目前不在两节内(第五轮评审 X2 P1-3),它进检查点还是改由只读视图推出:策略研究后定(R8-12)。原写法"检查点只存原始样本、派生状态恢复后重算"做不到这一点:分位带的更新时刻与平滑窗依赖从哪一刻开始算,恢复后重算出的值与连续运行不同,每日 recompute 会失败、⑦ 过不了。为此 portfolio-carry 的分位带更新时刻对齐 UTC(`band_update_ms` 的整数倍边界)。CI 的检查点金样比对布局描述 `ModelLayoutDesc`(节标签、元素类型、长度规则),不比对字节。**结构参数允许热更**(如分位的箱宽):SDK `FieldDesc.structural` 标出这类字段,`Model::on_params` 返回 `ModelParamEffect{None, ResetGroups, ResetAll}`,被重置的 group 写 `Note{ModelGroupReset}`、由 pipeline 自动预热;在 Live 实例上改结构字段的 `SetParams` 属升级类(需确认,预览显示受影响 group 数与预计不能开仓的时长),pipeline 插件不得拥有结构字段;group 的资产或腿变了(`GroupSpec::fingerprint()` 不同)同样重置。`GroupId = (StrategyId << 24) | 实例内计数器`(计数器 1..=0xFF_FFFE,单调、永不复用),唯一性由构造保证——原写法"每实例一个分配器"会让 dev2 上两个模拟实例撞号(W2 P1-5)。
- **冷启动预热是通用的 Input 通道**:首次启动或检查点被丢弃时,由 pipeline 的策略插件生成预热样本(组合携带:交易所 REST K 线或 collector 数据),经控制命令 `InjectWarmup{instance, local_kind, chunk_no, last, payload ≤ 4096 B}` 分块注入;它像其他命令一样记入 journal,路由到该实例的 Model(`EventRef::Warmup`),回放确定。载荷格式由策略定义,引擎不解释。
- 参数是每 (策略实例, 账户) 一个 blob:通用头 + 引擎理解的 `GroupSpec`(每个 group 的资产、各腿 venue/inst、`open_allowed`;引擎据此建订阅、做账户绑定、LegTracker 与 ledger 归属;引擎订阅另含该账户有持仓或现货库存的 inst 与每个 `ref_inst`,即"持仓驱动",规则归 hft-sequencer)+ 只有策略自己解码的 `body`(按 schema 顺序的定点整数)。编码的唯一定义在 [hft-event](../crates/hft-event/README.md)。

### 2.3 装配:静态编译、一行注册

全仓唯一的策略列表在 `strategies/registry`(一次 `strategy_set!{ PortfolioCarry, … }` 调用,生成静态分派的策略枚举),`apps/hft-core` 与 `apps/replayer` 依赖它;`hft-testkit` 不依赖 registry,需要真实策略的集成测试放在 `strategies/registry/tests/` 或 `apps/hft-core/tests/`。不做动态加载:没有 `dyn`、没有 ABI 问题、可以内联,回放与实盘是同一份机器码。代价是改策略代码要重新发布——参数可以热替换,这个代价可以接受。

### 2.4 由机检保证

- 依赖方向检查:引擎 crate 不依赖任何 `strategies/*`;策略 crate 只依赖 SDK 与 `hft-strat-lib`(后者只依赖 L0 + SDK)。规则见 [10 §2](10-语言分工与代码组织.md)。
- doc-check:引擎 README 不出现策略族名(含小写的 `cdex`;链上策略在引擎文档里用"链上策略"等通用说法)或某个策略的规则数字。
- **解耦门槛**:CI 里新增第二个测试策略,引擎 crate 的 diff 必须为零(上线门槛之一,[testing.md §8](../docs/testing.md))。

## 3. SDK 接口要点

完整签名在 [hft-strategy-sdk](../crates/hft-strategy-sdk/README.md);这里只说为什么是这个形状。

- **`Strategy`**:静态元数据(名称、全局稳定只追加的 `kind_id`、版本、schema)、`Params`(已解码已校验的定点参数)、`Model`(无慢速部分则 `NoModel`)、`subscriptions`、唯一热入口 `on_event`、`on_params`(校验失败旧参数继续生效)、`snapshot`/`restore`。
- **只读视图 `Views`**(静态分派,引擎实现,测试用 mock):事件时间 `now`、BBO 与簿、资金费(含实际结算周期)、mark、按账户按 venue 的**权益视图**、group 持仓、各腿净量/在途/残余、执行层当前目标与进度、订单、合约元数据、交易所能力表 `VenueCaps`、有效模式、风控状态(生效 cap、保证金档位)。策略不拿到任何可变引用。
- **`Ctx`**(固定容量,sequencer 在每个输入事件后排空):下订单意图、设/清目标意图、撤/改、定时器、`note`。满了返回 `CtxFull`,策略按"本事件放弃"处理。
- **参数 schema 的字段属性**:除 `structural` 外,R8-11 加 `FieldDesc.minor_change: MinorChange { None, RelPct(u16), Abs(i64), Any }`——门槛 ⑦ 的"小改不重新计时"由工具按它通用判定,取代原来按策略手写的"小改白名单"(不可机检)。
- **只追加的能力**(R8-11):Model 可订阅本实例的 `Exec`/`Order`/`Manual` 事件(只读、来自 journal、确定);hft-sim 的压力用例可按 venue 单独变价(`StressScope::Venue(v)`);latency-probe 增加 `target` 模式(走 `TargetIntent` → hft-exec 切片路径)。
- **`EventRef`**:行情(BBO、簿、成交、资金费、mark)、订单回报、**执行进度**(`Exec`:Progress/Done/Stuck/Broken)、**外部成交**(`External`:强平、ADL、人工、交割)、**风控事件**(`Risk`:MarginStress、HedgeBroken、cap 变化)、**交易所通知**(`Notice`:下架、结算周期变化、维护)、定时器、本策略模型的 `Advice`(带 `basis_seq`/`basis_tsc`)、预热数据 `Warmup`(只给 Model)、人工命令 `Manual{payload}`、模式变化、连接状态;`Swap` 只给链上策略(optional)。
- 新增的事件(外部成交、保证金报告、账户配置报告、执行决定)都是通用的,任何策略都用得上,所以放在引擎;策略特有的东西只走 `Advice` 载荷、参数 `body`、预热载荷与人工命令载荷。
- **策略自己的可观测与人工出口也走描述符**([M0 独立评审 P1-7](_work/review-2026-10-03-M0独立评审.md)):`StrategyDesc` 带 `notes`(该策略的 Note 码表:码、名、级别、`v[]` 各字段含义)与 `report`(报表字段:名、单位、聚合方式 Count/Sum/Last/Max/P99),随 schema JSON 导出;watchtower 与 journal-archiver 按描述符通用汇总策略 Note,生成实盘与模拟日报。人工开平不再是引擎里带策略语义的 `ManualOpen/ManualClose`,而是通用的 `StrategyCmd{instance, group, payload ≤ 256 B}`,载荷含义由策略定义。新增策略不改 watchtower、archiver、控制协议与 ops_bot。

## 4. 两层输出:目标意图与订单意图

组合策略想的是"每个币该持多少",套利策略想的是"现在下哪一单"。旧规格只有订单意图,目标跟踪型策略就得自己写切片、两腿协调、重试、补腿——每个策略写一遍,而这正是雏形 portfolio-arb 出 P0 的地方(超时按原数量重下、两腿量不同取 min 记账、两腿都报错当两腿都未成交,见[评审 §6](_work/review-2026-10-02-主策略适配与执行正确性.md))。所以输出分两层,策略按需选用:

| 层 | 策略说什么 | 谁来执行 | 适合 |
|---|---|---|---|
| **目标意图**(`TargetIntent`) | 某 (账户, group) 各腿的目标净量、原因(`Rebalance`/`Exit`/`MarginStress`/`Hard`/`Manual`;策略的成本门只对 `Rebalance` 生效)、紧急度、不交易带 `band`、执行算法 `ExecSpec` | 执行层 `hft-exec`:切片、两腿协调、对冲、补腿 | 组合携带、资金费差、任何"想要多少"型策略 |
| **订单意图**(`OrderIntent`) | 具体订单,可带 `LegLink`(OnFill / Simultaneous) | OMS 直接执行,第二腿由 OMS 在同一事件内发 | 跨所吃单、挂单对冲等需要逐 tick 控制的策略 |

- 目标在被替换或清除前一直有效,策略不需要每个 tick 重发;执行层在每个相关事件(BBO、成交、定时器)推进一次,O(腿数)、零分配。
- 两层都过同一个模式门与风控检查链:目标中**增仓**的部分受模式门与 Open 规则约束,**减仓**的部分按 Reduce/Flatten 分类——降级时不会挡住减仓。
- 执行层的每次决定(选了什么算法、切了多大、为什么)写成 Output 记录 `ExecDecision`,复盘与回放都看得见;进度经 `EventRef::Exec` 回到策略。

## 5. 执行层(`hft-exec`)

执行算法是可复用的工程模块,策略在 `ExecSpec` 里选用、用参数调;规格的唯一归属是 [hft-exec](../crates/hft-exec/README.md)。

| 算法 | 做什么 | 为什么需要 |
|---|---|---|
| `TakerSlice` | 单笔 = min(\|差额\|, 弱侧可见深度 × `depth_frac`, `max_chunk_notional`),≥ `min_chunk`;同 group 两笔间隔 ≥ `cooldown_ms`;可见深度在该 inst 有分档快照(TopN)订阅时读簿,否则取 BBO 顶档的量(首次上线不做增量深度,[04](04-行情接入层.md)) | 雏形的"单笔 = min(\|Δ\|, 弱侧一档 / 3, $500)"的通用形式;不让单笔吃穿薄的一侧 |
| `PairOnFill` | 两腿:先下 `first_leg`,按其**成交净量**下另一腿 IOC;`first_leg = ByLiquidity \| PerpFirst \| SpotFirst \| Fixed` | 两腿一致性:第二腿在第一腿回报的同一事件内出环(≤ 20 µs) |
| `Simultaneous` | 两腿同发,失败反向(`on_fail = Reverse \| Hold`) | 对价格变化敏感、能承受偶发反向成本的策略 |
| `MakerFirst` | 先挂单,成交后对冲 | 预留(optional),给挂单对冲类策略 |

几条规则写在执行层而不是策略里,因为它们是"怎么执行才不留裸腿",与策略无关:

- **腿顺序按原因选**:`reason ∈ {MarginStress, Hard}` 强制 `PerpFirst`——保证金压力下要先减的是永续空头(释放保证金、流动性更好);若先卖现货而现货卖不掉(余额被手续费扣过、交易所拒单),永续空头就平不掉([评审 §2.1](_work/review-2026-10-02-主策略适配与执行正确性.md))。常规开仓默认 `ByLiquidity`(流动性差的一腿先做),可由参数覆盖。
- **按净量对冲**:现货手续费可能从买到的基础资产里扣(各所规则写在 `VenueCaps.fee_asset_rule`),仓位、库存与对冲量一律按扣费后的净量;现货卖出量取 min(库存, 可用余额)。
- **对冲量有上限**:对冲量 ≤ 触发成交净量 × 比例 + 1 lot,名义 ≤ `max_hedge_notional`;超限 → `Broken` + P0,不发单。防止解码或单位错误(张数 × 乘数、`1000PEPE` 类指数)把一笔成交放大成千倍的对冲单。
- **重试保留角色**:第二腿重试仍是第二腿(继承开仓/平仓的 reduceOnly 语义),补腿单只用于"平掉多出的一腿";重试与补腿共用计次、冷却与截止,HARD 下抑制——避免开仓对冲重试被当成 reduceOnly 而必被拒,也避免补腿自激成循环。
- **第二腿量以裸量为上限**:OnFill 的第二腿数量 = min(按成交净量算出的量, LegTracker 当前该方向的裸量)。这同时消掉"无 client id 的成交先按外部成交处理、后又匹配到槽"造成的重复对冲;gw 对无法归属的成交先暂存 `gw.unmatched_hold_ms`(默认 5 000)才发 `ExternalFill{Unknown}`。
- **两腿 lot 对齐**:切片与第一腿数量按两腿 lot 的较粗者取整,保证第二腿量 ≥ 其 `min_qty` 且为其 lot 的整数倍;不能整除时取最小公倍数,名义 > `max_chunk_notional` 时 `SetParams` 拒绝(`InvalidArgs{LotMismatch}`)。否则每片都留下不可对冲的残余([M0b 独立评审 P1-2](_work/review-2026-10-03-M0b独立评审.md))。
- **报价有效 = 连接健康**:对冲腿、风险递减单、自动平仓与 L3 减仓用的报价,只要该 BBO 连接健康(连接 Live、非重同步、最近任一帧距今 ≤ `conn_liveness_ms` 2 000)就有效,盘口不动不算过期([05 §3](05-CEX执行层.md);[M0b 独立评审 P0-1](_work/review-2026-10-03-M0b独立评审.md))。
- **对冲超滑点改价而不失败**:对手价偏离超过 `max_slip` 时,对冲腿按 `rr_max_cross` 上限定价照样发 IOC;只有超过 `rr_max_cross` 才算门控拒绝(不计执行失败次数)。否则对冲所报价一跳就在 3 s 内判 Broken([M0 独立评审 P0-3](_work/review-2026-10-03-M0独立评审.md))。
- **断腿(Broken)有界自动处置**:某 (账户, group) 处于 Broken 持续 `broken_auto_fix_ms`(默认 120 000)且期间无人工 `HedgeFix`,执行层自动发起**一次**"平掉多出的一腿"(永续腿 reduce-only;现货腿卖出,数量取 min(库存, 可用余额)),按 `max_reduce_notional` 切片,总量 ≤ 当前裸量;"一次"是一次**可执行的**尝试——报价不可用、限速退避、对手价越过上限时先等待,门控拒绝与零成交按重试处理,都不消耗这一次([05 §2.3](05-CEX执行层.md));成功写 `Note{ExecAutoFixDone}`(P1),cell 回到 Idle,但 `HedgeFailure` cap 仍需人工 `Resume`;失败或被门控拒绝写 `Note{ExecAutoFixFailed}`(P0),保持 Broken 等人工。HARD kill 下不执行。之前 Broken 只能人工 `/hedgefix`,夜间可能裸几个小时;现在最长裸露约 2 分钟加一次平仓,且只做一次,不会自激。
- **冷启动不立刻判 Broken**:`hedge_deadline_ms` 只按引擎运行时间累计(停机时间不计);恢复后启动闸门放行时,对仍未对冲的链接先做一次 `SecondRetry`,再按正常截止判断——否则冷启动约 30 s 本身就超过 3 s 的截止。
- **引擎默认减仓**:保证金进入强制档、或外部成交(强平/ADL)后策略在截止时间内没有处理,执行层按默认规则减仓(§6)。保证金 L3(`force_deleverage`)与 `Kill{flatten}`(`engine_flatten`)对 Broken 的 group **同样生效**:先对永续腿 reduce-only 减仓(`PerpFirst`,受 `max_reduce_notional`),再处理现货腿——最危险的正是 Broken 组合里的裸永续空单,旧规格却把它排除在外([M0 独立评审 P0-2](_work/review-2026-10-03-M0独立评审.md))。`engine_flatten` 同时置账户级 `flatten_lock`:直到 `Resume{Kill}` 前,该账户只接受比当前更接近 0 的目标与 Reduce/Flatten 意图,策略的新目标不能覆盖清仓。引擎目标设下时先撤该 inst 上本账户的全部非 EXEC 挂单(`cancel_resting_on`),否则策略挂着的 reduce-only 单会让风控拒掉引擎减仓单;L3 每步取"当前目标与按比例目标中更接近 0 者";L3 的越价上限按 inst 所属价格带类别取值(R8-11,[05 §2.3](05-CEX执行层.md))。
- **人工操作期间不自动补腿**(R8-11):收到 `ExternalFill{Manual}` 的 cell 置 `manual_hold`,补腿、ResidualTrim、外来成交默认处理与自动平仓计时一并暂停,直到策略对该 group 给出非清除类动作、人工 `HedgeFix` 或出现引擎目标([05 §4.3](05-CEX执行层.md))。

与 OMS 的边界:OMS 只管订单槽状态机与 `LegLink` 机制;"下什么单"由执行层决定;补腿阈值、残余/尘埃规则、重试次数与截止全部是参数。执行层在 sequencer 线程里运行,预算落在 [00 §4](00-目标与延迟预算.md) 的 `decide` 分段(p50 ≤ 5 µs、p99 ≤ 15 µs)内,各入口的预算与基准名在 hft-exec README。

| 归引擎(通用机制,阈值由参数给) | 归策略(策略代码或策略参数) |
|---|---|
| 全账户硬限额(单笔/单币/总名义、仓位上限)、kill(全局/venue/账户/HARD,可按账户 HARD) | 进出场规则、止损、持有时长 |
| 保证金分档(`MarginStress`,按到强平价的距离) | 资金口径与仓位规模(从权益视图自己算) |
| 裸腿:LegTracker 把在途算进裸敞口;带 `LegLink` 的开仓先查第二腿(所在 venue 可用、BBO 连接健康、资金可负担——永续腿按账户实际杠杆);任一 group `Broken` → 账户级 `HedgeFailure` cap 挡该账户全部开仓;Broken 持续 2 分钟自动一次有界平仓 | 跨币分配、滞回门、结算前闸门 |
| 速率:每 venue 令牌桶,为风险递减单预留份额 | 自己的残余/尘埃规则(以参数交给执行层) |
| 对账与启动闸门(对账逐项放行、交易所身份核验、账户配置核验) | 对外部成交(强平/ADL/人工)的处置(截止内) |
| 交易所能力约束(`VenueCaps`:reduceOnly、最小名义、步长、扣费资产、资金费推送方式) | 对下架、结算周期变化的处置 |
| 存储退化(`Storage` cap)、下架(该 inst 的开仓被拦,不改 cell 有效模式,规则归 [hft-risk](../crates/hft-risk/README.md#下架与公告venuenotice)) | — |

从引擎移出的策略规则:资金公式 `wallet × leverage × deployable`(引擎不再计算"可用资金",旧 `CapitalView` 删除,策略从权益视图自己算)、cdex 的 5% 补腿阈值与残余清理规则、`FundingGate` 常数——它们进入 `strategies/cdex` 的参数或代码。

**保证金分档**是组合携带最需要的一条。按雏形的默认(可部署 60%、永续所占总资金约 40%)估算,持仓币普涨 50% 时永续所权益只剩总资金约 10%(约 9 倍杠杆),普涨 60% 时约 4%,接近维持保证金;现货浮盈在另一所,补不过来([评审 §2.2](_work/review-2026-10-02-主策略适配与执行正确性.md))。

**度量改为到强平价的距离**([M0b 独立评审 P0-3](_work/review-2026-10-03-M0b独立评审.md)):旧规格按比率 r = 维持保证金 / 保证金余额 分档(L1 0.60 / L2 0.70 / L3 0.80)。永续空头的 r = m(1+X)/(e−X)(X 为涨幅,e 为初始权益占名义的比例,m 为维持保证金率),L1 到强平(r = 1.0)之间只剩约 0.67·m 的价格空间:e = 0.30、m = 0.5% 时 L1 在 +28.93%、L3 在 +29.19%、强平在 +29.35%,几乎不给减仓时间。所以按每个 (account, venue) 的 `liq_dist = min over 永续持仓 |liq_px − mark| / mark`(空头为 `(liq_px − mark)/mark`)分档,来源取 `MarginReport` 的交易所 `liq_px` 与 ledger 估算中更保守者;原比率保留为交叉校验。默认值待标定,唯一归属 [hft-risk](../crates/hft-risk/README.md):

| 档 | 条件 | 动作 |
|---|---|---|
| L1 | `liq_dist ≤ liq_dist_block_open`(默认 0.25),或保证金数据过期 | 禁开 |
| L2 | `liq_dist ≤ liq_dist_reduce`(0.15),或比率 ≥ 0.8(交叉校验,至少 L2) | 通知策略(`RiskEvent::MarginStress`),`deleverage_deadline_ms`(30 000)内须减仓 |
| L3 | `liq_dist ≤ liq_dist_force`(0.10),或 L2 截止已过 | 执行层按比例减永续敞口,每步 `force_step` 20%,`PerpFirst`,原因 `MarginStress`;处于 Broken 的 group 一并减(先永续腿 reduce-only) |

回退带 `liq_dist_hyst`(0.02)防抖。hft-sim 的"单边 +30%(1 h 内)"压力用例是上线门槛 ⑦ 的必过项(不得出现强平);另有一个必过的 **L3 路径变体**(按 `max_perp_leverage` 上限杠杆或 1 h +45%,要求依次出现 L1/L2/L3 且无强平)——默认 2 倍杠杆下 +30% 只到 L2,测不到 L3。永续杠杆不再是常量:hft-risk 的 `LINK_FUNDS` 用 `AccountConfigReport` 读到的实际杠杆(删除 `perp_leverage` 默认 1)。

**永续的安全阀不靠 `perp_margin_frac`**(五路评审 V2 P1-9,R8-10):开仓按可用保证金的增量判断时,反复开仓收敛到的永续名义只取决于交易所杠杆与资金分布,与 `perp_margin_frac` 无关;交易所杠杆若留在默认的 10–20 倍(待核实),不利几个百分点就进 L1。所以两道与策略参数无关的约束:组合携带对每个永续 venue 加硬上限 `Σ|永续名义| + 新增 ≤ margin_balance / perp_min_equity_ratio`(默认 0.40,待标定);SDK 暴露实际杠杆 `Views::leverage(a, i)`,hft-risk 的 `RiskParams.max_perp_leverage_x100`(默认 300,即 3 倍)——任一交易中的永续 inst 实际杠杆超过它 → `ACCOUNT_CFG` 不符(禁开)+ P1。交易所杠杆的设置步骤写在 [launch.md](../docs/runbooks/launch.md)。

强平价、保证金率与 ADL 档由各所 venue 适配层按 `VenueCaps.margin_data`(推送或轮询)产出 `MarginReport`;自身强平、ADL、人工网页成交产出 `ExternalFill`,入账、更新 LegTracker、通知策略;强平/ADL/交割报 P0,策略在 `external_deadline_ms` 内没有处理,执行层默认"平掉多出的一腿";用户流断线期间漏掉的 ADL 由 reconciler 第二轮按"永续同号缩小、无在途、无 Unknown"补成 `ExternalFill{Unknown}`(`AUTO_EXTERNAL`)入账并 P0。人工网页成交(`Manual`)不做引擎默认处理,该 cell 置 `manual_hold`(连补腿也停,P1),由策略决定(组合携带把该 group 冻结,直到人工清除或两腿重新对齐)。L3 与 flatten 对非 Broken 的 cell 只要求永续腿报价可用,另一所行情断开时退回串行路径(永续先减,接受短时现货裸多 + P0,[05 §2.3](05-CEX执行层.md))。跨所资金只告警并给划转建议(`treasury`,core),交易 key 不带提现权限,不自动划转([09 §4](09-可观测性、风控与控制面.md))。

## 7. ccex 策略族

### 7.1 组合携带(`portfolio-carry`,core,首个实现)

结构取自老板给的策略雏形 portfolio-arb(`Trading/portfolio-arb`,Rust):**全币打分 → 分配 → 目标 − 实际 → 双向切片调仓 + 滞回门**。它是策略内容的说明,不修、不迁移、不作为验收对照基准;规则与参数的唯一归属是 [portfolio-carry README](../strategies/portfolio-carry/README.md),这里只说它怎么落到策略包的三部分上。

| 雏形里的东西(原值,仅作说明) | 落到哪里 |
|---|---|
| 入场打分(资金费 0.6 / 基差 0.3 / 流动性 0.1)→ score^1.3 → 单币份额上限 20% 迭代封顶 → 绝对上限(受限币 $1,500、普通币 $10k)→ 同 venue 超额再分配 → 60 s 平滑 | **Model**(advisor,f64 与迭代都在这里),输出目标权重 `Advice` |
| 7 天(168 h)分位带,5 s 采样;资金费高时入场分位下沉 | **Model**,输出触发价位/带宽 `Advice`;普通重启、改参数、发版都从 Model 检查点恢复;首次启动经 `InjectWarmup` 预热(pipeline 插件从交易所 REST K 线或 collector 数据生成样本,§2.2) |
| 24 h 已实现资金费统计、结算周期推断 | **Model**;结算周期以 `Funding` 事件携带的实际值为准,`hft-strat-lib` 的资金费统计检测周期变化 |
| 总资金 = 永续所保证金余额 + 现货所现金 + 现货代币 × bid;可部署比例、现金储备 | **快速部分**,从权益视图计算(引擎不算) |
| 目标 − 实际,15% 比例噪声门 | 快速部分算目标;噪声门 = `TargetIntent.band` |
| 单笔 = min(\|Δ\|, 弱侧一档 / 3, $500),平仓先于开仓 | `ExecSpec::TakerSlice` / `PairOnFill` 参数 |
| 结算前 5 min 闸门、成本-机会滞回门(回本 ≤ 5 天) | 快速部分的规则,参数化;成本门写成 `cost × 1天 ≤ max_break_even_ms × gain_daily`(旧写法量纲错),只对 `Rebalance` 生效,`Exit`/`Hard`/`MarginStress` 不受约束;平仓收益 `close_gain_daily = max(0, max(best_other_T, 0) − T_i)`(活跃集为空时 `best_other_T = 0`)——只算换仓机会时,资金费转负且没有别的币可换,平仓门永不放行,组合持续付负资金费([M0 独立评审 P1-6](_work/review-2026-10-03-M0独立评审.md))。平仓方向的成本只算平仓两腿:`close_cost = fee(perp).taker + fee(spot).taker + (spread(perp) + spread(spot)) / 2`(开仓费已沉没);倍数条件只用于开仓;`gain_daily` 一律取 `FundingSummary.realized_daily`(五路评审 V2 P1-2,R8-10) |
| 夜间网格寻优 + 自动热加载 | **不迁移**:不做历史回测;换参经模拟账户验证 + 人工接受 |

**单 group 强制退出**([M0b 独立评审 P1-10](_work/review-2026-10-03-M0b独立评审.md)):`open_allowed = false` 只停开仓,平仓仍走成本门,正资金费且无更优币时永远不平。所以加 per-group 参数 `force_exit: Bool`(默认 false)与 `StrategyCmd` 命令 `exit`(`reduce_only = true`):该 group 目标设 0、`reason = Exit`,跳过成本门。

**默认生效的负资金费退出与整体退出**(R8-10):`neg_funding_exit_periods`(默认 3,0 = 关闭)——连续 N 次结算的实收资金费率 < 0,该 group 目标 0/0、`reason = Exit`(不经成本门),N 的取值在模拟中研究;实例级 `StrategyCmd exit_all`(`reduce_only = true`)对全部 group 执行 `exit`;`CloseOnly` 下组合携带**持有**(不开新仓,不强制退出),超配部分(`actual > cap_i × (1 + overweight_tol)`,默认 0.10)按减仓处理,只受 `close_cost` 回本门约束;但超配 > 2 × `overweight_tol` 或 `open_allowed = false` 持续 `close_only_rounds`(默认 3)轮后,按 `stress_step_ms` 每步减 `stress_reduce_frac`,不受成本门约束(R8-11,pc 内部规则)——否则本池资金费最高的币在普涨中被动超配却永远平不掉。第五轮评审指出现行默认参数下逐步减仓第一步后即停住、只平不开约 30 s 就触发清仓(X2 P1-1、P1-2):逐步减仓的节奏与只平不开的触发口径,策略研究后定(R8-12)。快速部分不订阅深度(首次上线不做增量深度)。规则唯一归属 [portfolio-carry](../strategies/portfolio-carry/README.md)。

雏形的已知缺陷不照搬([评审 §6](_work/review-2026-10-02-主策略适配与执行正确性.md)):超时/发送失败按原数量重下、两腿都报错当都未成交(→ 本框架的 `Unknown` 语义与执行层);两腿量不同取 min 记账、按 USDT 金额买入导致少买、对账只改记账不补腿(→ 按净量的目标跟踪与补腿);没有保证金/强平/ADL/下架保护、风险退出可能被分位条件无限期挡住(→ §6 的引擎分档与外部事件;硬退出不受入场分位约束);`drift_override` 让成本-机会门几乎失效、各币目标之和可超过可用资金(→ 门的规则在策略 README 重写并测试);资金口径混用(→ 权益视图统一口径);tune 与实盘公式不一致(→ 同一份 Model 代码,不存在第二份)。

**交易所不写死**:每个 group 的两腿(永续腿 venue/inst、现货腿 venue/inst)在 `GroupSpec` 里给出,两腿必须在不同交易所(§1);策略代码不出现交易所名字,手续费扣币、reduceOnly、最小名义、资金费推送方式等差异来自 `VenueCaps`。首批交易所是 Binance、OKX、Bitget 的现货 + USDT 本位永续([11 §1](11-实施路线图.md))。

**策略规则不急着定**:框架交付不等策略定稿;M4 起在模拟账户上研究与改进(§9),正式实盘开始后同参数模拟与实盘并行校准。

### 7.2 同族可接入的变体

腿模型是通用的(一个 group 最多 4 条腿,每条腿 = venue + inst + 方向),所以下面这种只需要新策略包或新配置,不改引擎:

- **跨所永续 × 永续资金费差**:两所永续反向持仓。两边都是永续保证金,`MarginStress` 按账户在两边各自生效;执行用 `PairOnFill`(`ByLiquidity`)。

**同所现货 × 永续不做**(§1):refdata 与 `SetParams` 校验会拒绝这种配置。若将来要做,需要先给 ledger、SDK 权益视图、风控与模拟加"余额域"(同一钱包被两个 venue 共用),那是引擎改动,要单独决定。

### 7.3 optional:跨所价差吃单(`cross-taker`)与挂单对冲(`maker-taker`)

- **cross-taker(原 A)**:快所 BBO 更新 → 与慢所比 → 扣成本线后 ≥ 阈值 → 立即对慢所发 IOC(不做确认窗口;"确认"是 `LeadLag` 的统计置信度)。用**预计算触发价**:慢所报价变化时算出快所需要到达的价位,tick 到来只做一次整数比较([13 R10](13-设计评审与优化.md))。这是唯一需要 [03](03-网络与传输层.md) 全部手段的策略。领先-滞后证据:Binance → Bitget/OKX 命中率 59–90%、跟随延迟中位 10–21 ms;但扣除双边费用后是否可交易尚未证明。触发条件:可交易性分析([待测量 A1](待测量与待决定事项-2026-10-01.md))显示扣费后有边。
- **maker-taker(原 B)**:慢所 post-only 挂在略优于对手的价位,成交后快所 IOC 对冲;核心是撤单速度(fast 所一动立刻撤/改)。需要 L2 判断队列前方深度;执行层的 `MakerFirst` 与 `hft-sim` 的挂单撮合为它预留。触发条件:某所挂单 + 吃单经数据证明有边。
- 规格分别在 [strategies/cross-taker](../strategies/cross-taker/README.md)、[strategies/maker-taker](../strategies/maker-taker/README.md)。

## 8. optional:cdex(CEX-DEX 携带、chain-first、股票代币)

cdex 现在在旧框架(Python `spread_engine`)上以正式账户运行,迁移不急。规则与参数整体搬到 [strategies/cdex](../strategies/cdex/README.md),连同 `hft-strat-lib` 里 cdex 专用的构件(Sizer 因子、ClosePolicy、FundingGate 常数、换仓候选、72 h 价差统计口径)。触发条件:决定把 cdex 迁到新框架;那时同时启用 [06](06-链上执行层.md) 的 chain-core free profile、流水线的 cdex 插件、迁移手册,且 cdex 用与 ccex 不同的交易所子账户(一个账户只给一个策略实例)。

保留的设计要点(写给迁移时):

## 9. 运行模式与模拟账户

**运行模式**只有 `Shadow`、`CloseOnly`、`Live` 三种,按 (策略, 账户, group) 设置;期望模式与 cap 分离:`SetMode` 只写期望模式,kill、日亏熔断、对账、Unknown 超时、冷启动恢复、保证金分档、存储退化、下架等都是独立的 cap,有效模式取最严;Shadow 只在该 cell 无仓位、无在途时生效,否则先按 CloseOnly 运行到归零。模式状态归 `hft-risk::mode`,优先级表归 [control-plane](../docs/subsystems/control-plane.md),"各模式下目标意图与订单意图怎么处理"的行为表归 [hft-strategy-sdk](../crates/hft-strategy-sdk/README.md)。

**不做历史回测,做模拟账户。** 回测一定不准:成交、队列、延迟、冲击、资金费与保证金的路径依赖都只能近似,而组合携带的盈亏恰恰由成本与执行质量决定。Shadow 也评估不了目标跟踪型策略——只记录意图不成交,实际仓位永远不变,每个事件都会算出同一个差额。所以评估与改进策略用**模拟账户**:

- 模拟是**账户类型**(`AccountKind::Sim`),不是运行模式。策略在模拟账户上以正常模式(通常 `Live`)运行,策略代码与实盘完全相同;sequencer 把该账户的订单路由到 sim 实例进程内的 **sim-gw**(warm 线程,不占热核),回报经同一回报环进入并记入 journal(Input),所以回放仍然确定([08 §5](08-数据面与回放.md))。
- 撮合用实时行情:吃单在"下单时刻 + 模拟延迟"(按实测往返/回执分布抽样)对实时 L2/BBO 逐档成交;**已吃流动性记忆**(同一档被我们吃掉的量在一段时间内从可见量中扣除,避免连续下单重复吃同一档);部分成交;按 refdata 与 `VenueCaps` 执行拒单规则;手续费与扣费资产;资金费在结算时刻按真实费率结算;永续全仓保证金与强平;现货余额;跨所划转以控制命令模拟。规格归 [hft-sim](../crates/hft-sim/README.md)。
- **模拟不能拖慢实盘**(总目标是延迟优先;[M0 独立评审 P1-4](_work/review-2026-10-03-M0独立评审.md)):
  - 模拟始终在一个**独立的 sim-only hft-core 实例**里运行(`instance = "sim"`:refdata 只含 Sim 账户、不加载任何交易所 key、自己的行情连接与 journal);实盘实例(`instance = "prod"`)不含 Sim 账户。同一份二进制;sim 实例不交易任何交易所账户,所以不违反"同一账户只由一个系统交易";journal 实例名只允许 `"prod" | "sim"`。实例内的输入环优先级 `ctl > rep(实盘回报)> bbo > advice > md > rep-sim`、`sim_max_per_round`(默认 32)仍是引擎规则。每个研究中的策略预置 `sim_pool = 2` 个模拟实例;dev2 的 sim 容量按"2 个研究策略 × 2 个池实例 × 32 group"定(R8-11;数值归 hft-core),portfolio-carry 的 sim 实例默认 ≤ 32 group。
  - `dev2`(R8-9):长期运行 `sim` 实例;交易所测试网/模拟盘联调时另起一个指向测试网端点、只持测试网 key 的 `prod` 角色实例(只在联调窗口运行,refdata 只含测试网账户)。dev2 不放正式实盘账户。
  - **统一升级后 sim 与 prod 同机**(R8-9、R8-10):sim 只用非隔离核,永不占 prod 的热核;独立 `hft-sim.slice`(CPU、内存上限);独立的 journal 与冷盘目录;独立网卡 ENI-C(出口 IP = ENI-C 的私有 IP + EIP,不占 prod 的按 IP 限速,收包 IRQ 在 sim 的核上)。主机档位须同时容纳两个实例(默认 `c32`,`c16` 只在 M3 末满订阅探针达标时保留,由该探针选定)。
  - **参数覆盖按实例分开**(R8-9;[M0b 独立评审 P0-2](_work/review-2026-10-03-M0b独立评审.md)):pipeline 主体的 `SetParams` 在 Live 账户上同样是中性的(含新增 group、`open_allowed` 0→1),不需确认;但人工覆盖项按实例分键(`overrides/<instance>.toml`),校准写共享覆盖项必须显式 `scope = pair`(默认 `instance`),所以 sim 实例上的参数试验不会流到 prod。作用于 Live 实例的人工修改在 ops_bot 侧仍需确认。
- 可同时开多个模拟账户跑不同参数;报告给出 PnL 分解(资金费、基差、手续费、相对到达价的滑点)、成交率、两腿间隔、裸敞口、保证金占用,以及按策略报表描述符(§3)汇总的策略专项指标,ops_bot 展示时标注"模拟"。
- **校准**:正式实盘开始后,同参数的模拟账户(同机 sim 实例)与实盘并行,量化滑点、成交率、延迟的差异,回写模拟参数。
- **压力用例**:hft-sim 的"单边 +30%(1 h 内)"与 L3 路径变体必须不出现强平(门槛 ⑦ 必过,§6);基差扩大、15 min 内 +30%、上涨中 gw 断开 10 min、盘口量 × 0.2、上涨中 hft-core 重启是非门槛变体,可按 venue 单独变价(`StressScope::Venue`);交易 inst 的分档 MMR 必须在 refdata 中。门槛 ⑦ 对**每个上线策略**计时,绑定(发布版本, StrategyParams SHA, RiskParams SHA),停机累计超过上限即重新计时;策略、执行层、风控、hft-oms 与 SDK 代码变化或参数改动超出 `FieldDesc.minor_change` 即重新计时,"决策不变的修复"(最近 7 天 journal 回放逐字节一致、只改 venue/网络/冷进程/部署)不重新计时;dev2 缩小规模的 ⑦ 通过后才进入统一升级,切 Live 前在升级主机 sim 实例上满规模再跑 ≥ 7 天;护栏停掉 sim 后资源回落 ≥ 30 min 自动重启 sim(每天至多一次)。数值与规则唯一归属 testing §8。重新计时的完整路径范围(第五轮评审 X2 P1-4:hft-sim、hft-sequencer、hft-ledger、hft-types 与 `[sim]` 配置不在现表内)与压力用例的变价方向:策略研究后定(R8-12)。
- **适用范围**:sim 线程全部低优先级、延迟模型取实测分布,它评估不了 10–20 ms 窗口的跨所吃单类策略;对组合携带够用。
- 已知失真:我们自己的成交对他人行为的影响、挂单队列位置、看不见的流动性(如 Binance RPI 订单不出现在 bookTicker/depth)、延迟尾部、ADL;这些靠校准缩小,不靠模型"做准"。
- 把录下的 journal 行情喂给模拟网关重演(`replayer sim`)只用于排障与复现,**不用于评估收益**;`replayer sim --ab` 只给两组参数的差值,默认关闭、报告强制标注"相对比较,不是收益估计"([08 §5](08-数据面与回放.md))。

## 10. 仓位、权益与记账

- 引擎维护按账户、按 venue 的**权益视图**:各资产现金(free/locked)、**现货库存**(资产 → 数量,按 group 归属或未归属)、永续持仓(数量、入场价、按 mark 的未实现)、保证金余额(= 钱包 + Σ 未实现)、维持保证金、可用保证金、保证金率(统一口径,各所换算写在 venue 适配层)、到强平距离 `liq_dist`、合计权益(USDT;现货按 bid、永续按 mark,估值规则是参数)。数据归 [hft-ledger](../crates/hft-ledger/README.md),视图类型归 SDK。
- 仓位由成交溯源(按净量);资金费按 `VenueCaps.funding_settle`:推送带币种的直接入账,只推余额的所由 sequencer 按"结算时刻持仓 × mark × 费率"合成每币资金费(Binance 全仓是否不带币种待核实)。非策略资产用 `SetBalanceBaseline` 登记基线,避免成为永久对账差异。
- **资金费差异只告警、自动校正,不进启动闸门**([M0 独立评审 P1-5](_work/review-2026-10-03-M0独立评审.md)):合成值与交易所流水每期都可能差一点(只推费率的所尤其如此),若进 `RECONCILED` 闸门或触发 `Recon` cap,一条资金费差异就能把开仓永久卡住。所以 reconciler 的 `Funding` 条目带交易所逐笔资金费(账户、venue、inst、结算时刻、金额),分级前先用同组报告的 Funding 条目修正结算资产的余额差(否则资金费差额会经"余额"条目混进 `Recon` cap);ledger 对结算时刻早于 `funding_recon_lag_ms`(默认 600 000)的差额自动入账为 `AdjustDelta::Funding` 并写 `Note{FundingCorrected}`(比对窗口最近 48 h);差额超过 `funding_diff_alert`(默认 1 USDT 或 1%)时 watchtower 报 P1;ledger 查不到历史(`NoHistory`)的条目在窗口结束后按交易所金额入账并写 `Note{FundingCorrected}`(P1),不要求人工。
- `reconciler` 冷进程用 REST 拉交易所真值(各 core venue 的现货 + 永续:挂单、成交、仓位、余额),差异按名义分级成 `Recon` cap;启动闸门要求本轮差异(资金费条目除外)全部可忽略,或逐项 `AdoptExchange` / `SetBalanceBaseline` 处置后才放行。
- 研究侧的盈亏与热进程用同一份 Rust 记账代码(`hft-ledger`,PyO3 暴露),只有一套口径。

## 11. 实盘、模拟与回放同码

```
实盘:      feed/gw 线程 → Event → sequencer{策略快速部分, 执行层, 风控, OMS} → gw 线程 → 交易所
模拟账户:  同上;Sim 账户的出环 → sim-gw(实时行情撮合)→ 同一回报环(最低优先级)→ journal(Input)
           (始终在独立的 sim 实例里,同一二进制;升级后与 prod 同机)
advisor:   journal 尾部 → 各策略 Model → Advice → advice 环 → journal(Input)
验证回放:  journal 的 Input 记录 → 同一 sequencer → Output 与当时逐字节一致(CI 金标准)
重演排障:  录下的行情 → sim-gw + 同一策略 → 复现问题(不评估收益)
```

确定性前提:时钟、随机数、参数、定时器全部来自 Input 记录;策略与模型代码不允许 `Instant::now()`、全局可变状态、`HashMap` 迭代顺序依赖(CI 用 `clippy::disallowed_methods` 禁用)。

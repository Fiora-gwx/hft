# 06 · 链上执行层(chain-core)

> 依据:[research/03 链上调研](research/03-onchain-bsc-solana.md)。本章把调研结论落成组件设计。链上腿的延迟结构与 CEX 完全不同:主机内 µs 不是重点,**"什么时候知道、以什么顺序上链、失败怎么判定"**才是。
>
> **本章整体是可选扩展(optional)**:新框架首要服务 CEX-CEX;cdex 继续在旧框架运行,迁移到新框架时才启用本章组件(`apps/chain-core`、`hft-chain-evm`、`hft-ext-proto`、`hft-amm`、`contracts/` 的 `SwapGuard`、`chain-grpc-relay`、`hft-chain-solana`、`strategies/cdex`)。外部 venue 协议与链上事件编号段在架构上保留,以便日后接入。
>
> 启用时的基准形态是 **chain-core free profile**:新框架内的 cold tier 进程,只用免费公共 RPC;规则(多运营商证据、`SwapGuard` 链上过期、本地 nonce、gas 上限)与付费通道无关。自建节点、块流、builder 直投、L0 池镜像 + revm、纯链上 backrun、Solana 都是**可选扩展**,各自写明触发条件;它们改变数据源与投递通道,不改变本章的状态机与证据规则。规格以 [hft-chain-evm](../crates/hft-chain-evm/README.md) 与 [apps/chain-core](../apps/chain-core/README.md) 为准。

## 1. 约束与事实(2026-09)

| 链 | 出块 / 终局 | 订单流结构 | 对我们的含义 |
|---|---|---|---|
| BSC | 0.45 s / Fast Finality ≈ 1.1 s(2–3 块) | 87–96% 的块由 48Club Puissant 与 BlockRazor 两家 builder 打包;有价值的流走私有通道;builder 自 2025-05 起自营套利合约 | 机会窗口 2–3 块;free profile 走公共 mempool,**包含速度与被抢跑不因本设计改善**(只报告不设目标);要改善必须并发直投多家 builder(可选扩展,§10) |

现状对照:Python 用公共 RPC `eth_call` 报价(≈ 40 ms/次)、每 400 ms 轮询、公共 RPC 发单、0.5 s 轮询回执、链上成交中位 1.3 s、80% 被抢跑。

基准形态的目标:**任何传输错误不产生错误的仓位动作;每笔交易最多 `maxBlock` 终局后必知结果;成交确认 → CEX 对冲 ≤ 20 µs(hft-core 内,收到包含证据的同一事件出环);签名 < 0.1 ms,同一字节并发投递。** 包含块数、被抢跑率只报告不设目标([latency-budget §4.1](../docs/latency-budget.md))。可选扩展 builder profile 的目标另列:信号 → bundle 发出 ≤ 2 ms、下一块包含率 ≥ 70%(§10)。

## 2. 组件(基准形态:free profile)

chain-core 是 **cold tier** 进程:一个 tokio 运行时(端点 I/O、ctl、会话 I/O)+ `ChainSeq` 单写者状态机 + journal 线程,不绑核、不占隔离核,不在 tick-to-trade 路径上;与 hft-core 同机,经**外部 venue 协议**的共享内存 SPSC 环会话([external-venue-protocol](../docs/subsystems/external-venue-protocol.md))。`send.profile = "free" | "builder"` 选择后端,下文除标注外两者共用。

```
                    ┌──────────────────────── chain-core(cold tier)──────────────────────┐
 公共 RPC(HTTP)──▶│ ┌──────────────┐   ┌──────────────┐   ┌──────────────┐               │
 ≥ 3 个独立运营商   │ │ 端点表        │──▶│ 报价 / 预检   │──▶│ 意图门控      │               │
 免费 WS newHeads ─▶│ │ 令牌桶/冷却/ │   │ eth_call +   │   │ (cap、gas    │               │
                   │ │ 封禁/降权     │   │ estimateGas  │   │  上限)       │               │
 hft-core ────────▶│ └──────────────┘   │ 两个独立运营商 │   └──────┬───────┘               │
 SwapIntent        │                    └──────────────┘          ▼                       │

                   │ │ 本地 nonce    │──▶│ 签名          │──▶│ 并发投递      │──▶ K 个独立运营商的
                   │ │ 槽 → 候选集合 │   │ SwapGuard     │   │ 同一字节      │    eth_sendRawTransaction
                   │ └──────────────┘   │ maxBlock      │   └──────┬───────┘               │
                   │                    └──────────────┘          ▼                       │
```

### 2.1 数据源:公共 RPC 端点表

- 多个免费公共 RPC(HTTP)与可用的免费 WS(`newHeads`);端点表、令牌桶、冷却、封禁、降权全部配置化。并行 multicall 曾把 IP 从所有公共节点封禁——速率治理是这一档的前提,不是优化。
- 证据来源按**运营商 = 封禁/限流域**计:同一家的多个 URL、同一限流账号或同一 CDN 后的端点只算一个域。回执来源配置 ≥ 3 个独立运营商。
- 可用独立来源 < 2 持续 `sources_low_blocks` 块 → `SourcesLow` cap + P0 + 转人工,不推断任何交易的结果。

### 2.2 块头与回执

- 块头:免费 WS `newHeads`;无 WS 时轮询 `eth_blockNumber`(默认 200 ms);回执轮询默认 150 ms。
- 终局判定用 `finalized` 块号与块哈希,向 ≥ 2 个独立域取证。
- 可选扩展(§10.1/§10.2):自建节点与块流能更早看到新块与自己交易的包含证据,不改变证据规则。

### 2.3 报价

- `PoolQuote` 由 chain-core 在每个新块上经公共 RPC `eth_call`(Multicall/Quoter)计算后推给 hft-core,替代现有 400 ms 轮询;受端点令牌桶约束,每块覆盖的池数按预算配置。
- 多跳路由:WBNB/BNB/ETH/BTCB 计价池经 `bsc_route` 的一跳桥接(现有逻辑翻译到 Rust,V3 `exactInput` / V4 Universal Router 一笔)。
- 可选扩展(§10.3):L0 事件驱动池镜像,报价 < 50 µs;free 档以免费 WS `logs` 可靠为前提。

### 2.4 预检

- 发送前在 `latest` 上用公共 RPC `eth_call` + `eth_estimateGas` 预检完整 calldata(`SwapGuard` 外壳 + 路由器 calldata),向两个独立运营商取结果;不满足 `limit` → `MinOutUnmet`;revert → `SimRevert`;两个来源结论不一致 → 取第三个,仍不一致按 `SimRevert`(保守)。预检只复核,不放宽界限;`gasLimit` 取估算 × 1.2–1.3。
- 每次发送前都在**最新块**上再检一次(对应 AIN 事件里"复核用的还是同一瞬间的状态"的教训:ConfirmWindow 要求跨 ≥ 2 块,预检在发送前一刻校验)。
- 可选扩展(§10.4):本机 revm 精确模拟,热缓存下亚毫秒。

### 2.5 签名与出价

- BSC base fee 恒 0、最低 gasPrice 0.05 gwei、BEP-95 烧 10%。free profile 每意图一笔交易;gasPrice = clamp(端点中位价 × 倍数, 下限, 上限);**无出价**(`bribeTo = 0`)。builder profile 的 bundle 出价见 §10.5。
- 每笔交易经最小包装合约 `SwapGuard` 执行(校验 `minOut`、可选多池路径、失败 revert、合约内 `require(block.number <= maxBlock)`);free profile `maxBlock = 发送时块号 + N`(`free.max_blocks`,默认 3);路由器路径另设 `deadline`。裸 `eth_sendRawTransaction` 不经 `SwapGuard` 的交易禁止在热策略里使用。

### 2.6 并发投递

- 同一笔已签名交易(同一字节)并发 `eth_sendRawTransaction` 到 K 个独立运营商的端点(`free.send_fanout`,默认 3);`Sent` = **至少一个端点接受**(返回哈希或 `already known`);全部投递都是传输错误 → `Unknown`。`nonce too low` 只是查证线索。
- `maxBlock` 之前对查不到本交易的端点重播同一字节;过了 `maxBlock` 不重播,**同一意图不提价加速**——价格变化后由 hft-core 以新意图、新 `minOut` 重来。
- 传输:HTTP 长连接;每端点独立超时;任何 HTTP 错误只更新端点健康度,状态只进 UNKNOWN。
- 失败交易会上链:`IncludedReverted` 只花 gas(公共 mempool 没有"失败不上链"),由 §2.10 的 gas 上限兜底。

### 2.7 tx 生命周期状态机(P7 原则的落地)

```
SENT ──(回执 status==1,≥2 个独立运营商一致)──────▶ INCLUDED_OK   → 触发对冲(latest 证据)
  │ ──(回执 status==0,≥2 个独立运营商一致)──────▶ INCLUDED_REVERTED(只花 gas;free profile 失败交易上链,builder profile 下 bundle 失败通常不上链)
  │ ──(finalized 高度 > maxBlock 且 nonce 未被本交易消耗)▶ DROPPED  → 零成本重来(迟到上链只会被合约 revert)
  └──(403/429/5xx/超时/断连)───────────────────────▶ UNKNOWN       → 继续问其他源;绝不触发反向操作
```

- 回执来源:≥ 3 个独立运营商的公共 RPC;≥ 2 个独立域的回执 `status`、块号与块哈希一致才迁移;一个域有、另一个查无 → 继续等;块哈希或 status 不同 → `Unknown`,向更多域取证,以终局块为准。INCLUDED_OK 即触发对冲,**会计等 finalized**。
- 有界 UNKNOWN,前提是**交易本身有链上过期**:签过名的交易在 nonce 被用掉之前一直有效——公共 mempool 滞留、端点或中继泄露、重组后节点把交易放回 txpool 广播,都能让它在"DROPPED"之后迟到上链,留下无人知道的裸仓。`SwapGuard` 的 `maxBlock` 让迟到上链只会 revert(`IncludedReverted{LATE_LANDING}`),绝不出现 `DROPPED → INCLUDED_OK`;这样"`maxBlock` 终局后必知"才成立。例外只有可用独立来源 < 2(§2.1)。见 [13 §10](13-设计评审与优化.md)。
- 成功还要校验目标事件(`Swapped.intentId` 匹配、Swap 日志、余额差),防"成功但没换到"(现有余额核对逻辑保留);日志不符 → `Unknown(LOG_MISMATCH)`。

### 2.8 nonce 分配器

- 公共节点的 `pending` 计数不可信(会漏掉未广播或被替换的交易)→ **本地单调分配 + 在途表**,按"nonce 槽 → 候选交易集合"管理(同 nonce 的替换交易是同一槽里的候选),只在 INCLUDED/DROPPED 后推进或回收;启动时用 chain journal 恢复槽表,再向 ≥ 2 个独立域读 `latest` 计数校准;计数 > 预期且无已知候选消耗 → 钱包 `Tainted`。
- 专用执行钱包,只由 chain-core 发交易;每个钱包同时最多 1 个开放槽,避免 nonce 依赖;并发靠多钱包轮转。
- 公共 mempool 下同 nonce 复用必须提价 ≥ 12.5%;被替换者判 `DROPPED(NONCE_SUPERSEDED)`;滞留不去的旧交易用 `Cancel`(0 值自转账,按提价规则)清掉。

### 2.9 与 hft-core 的接口(外部 venue 协议)

| 方向 | 消息 | 频率 | 载体 |
|---|---|---|---|
| hft-core → chain-core | `BboSnapshot{group, bid, ask, qty, ex_ts}`(名单内币种) | 每次变化,峰值数千/秒 | 同机共享内存 SPSC 环(`hft-rt::ShmSpsc`,两条环);跨机 UDP(带序号/确认)是可选扩展;协议见 `hft/docs/subsystems/external-venue-protocol.md` |
| hft-core → chain-core | `SwapIntent{route, amount_in, min_out_bp, valid_blocks, hedge_plan}` | 稀疏 | 同上,带序号与确认 |
| chain-core → hft-core | `TxLifecycle{intent_id, state, amount_out, block, gas, builder}` | 每次状态变化 | 同上 |
| chain-core → hft-core | `PoolQuote{group, buy_px_for_size, sell_px_for_size, block}`(free profile 每块 `eth_call` 计算,替代现 Multicall 轮询;可选 L0 计算) | 每块或每次池子变化 | 同上 |

策略在 sequencer 里看到的是 `PoolQuote` 事件与 `TxLifecycle` 事件,和 CEX 的 `Bbo`、`Fill` 同等地位;chain-first 的对冲由 OMS 的 `LegLink` 在收到 `IncludedOk` 的那个事件里完成。

### 2.10 gas 上限与门控

- 每笔上链交易的 `gas_used × effectiveGasPrice` 记入 `TxLifecycle`;`IncludedReverted` 的 gas 计入发起它的 group,不计入仓位。
- 每钱包日 gas 上限与每路由连续 revert 上限,触及即自动非 hard 暂停(`GasBudget` cap,只放行 `risk_reducing` 意图);`risk_reducing` 意图另有 gas 硬上限(单笔 gasPrice、gas 与每日合计),会被超过时不发送、P0、转人工。
- 门控与 hft-core 同一 cap 模型:hft-core 心跳的每账户 KillBits、ctl `Pause`、`GasBudget`、`SourcesLow`、会话断开、`Draining`(见 [hft-chain-evm 门控](../crates/hft-chain-evm/README.md))。

## 4. 执行顺序:chain-first 为主

- DEX 只做 taker,只在池子相对 CEX "过时"时做:`|pool_mid − cex_mid| > 池费 + gas + 出价(free profile 为 0)+ 预期冲击 + 竞争折价`。
- chain-first(默认):交易带合约内 `maxBlock` 守卫 → 包含证据 → 立即 CEX 对冲;失败 = 无仓位。free profile 下失败交易上链只花 gas(计入 group,受 §2.10 上限约束);builder profile 下 bundle 不上链不付费,迟到上链被合约 revert,只花 gas。
- hedge-first 只在 builder profile 下、三条件同时满足时启用:机会来自 CEX 大幅跳价且池子肯定滞后;bundle 投给了 in-turn validator 对应的主 builder 且历史包含率 > 90%;对冲腿可在 1 块内低成本撤回。否则 hedge-first 的失败模式就是 9/24 的"CEX 有仓、链上没成交"。free profile 不启用 hedge-first。
- 现有实盘数据(9/24–9/26)也支持 chain-first:币安腿 1.4 s 内漂移中位 0、p99 0.1%,链上腿才是漂移与抢跑的来源。

## 5. 可选扩展:Solana

触发条件:Solana 侧 D/E 类机会经离线统计证明有净边,且付费数据/发送服务预算获批。接入后 chain-core 以同一个外部 venue 身份执行 Solana 腿([hft-chain-solana](../crates/hft-chain-solana/README.md))。

### 5.1 东京接入
- 数据:Helius LaserStream(Yellowstone gRPC,Business 档 $499/月)订阅持仓币的池子账户(Raydium CLMM/CPMM、Orca Whirlpool、Meteora DLMM、PumpSwap),本地报价器替代 Jupiter 轮询(Jupiter 自托管只做路由发现与离线校验)。
- 发送:Helius Sender(东京,SWQoS 通道)+ Jito 东京 block engine(bundle 原子性,tip 取 `tip_floor` 75–95 分位并随机化)双路发;Chorus One 实测 **SWQoS 是决定性因素**,优先费/tip 对延迟影响可忽略。
- 确认:`processed` 且 `meta.err == null` 触发对冲(≈ 400 ms);`confirmed` 复核;`lastValidBlockHeight` 判 DROPPED;`null` 状态视为 UNKNOWN。

### 5.2 法兰克福中继(触发条件:东京接入的统计显示落地延迟是 Solana 腿净边的主要损耗)
- 法兰克福裸金属 RPC 节点(24–32 核、768 GB–1 TB、双企业级 NVMe、10 Gbps,≈ $1.5–2.5k/月)+ DoubleZero Edge shred 订阅 + BAM preconf + 直连 leader TPU(Yellowstone Jet + SWQoS)+ Jito Frankfurt/Amsterdam。
- CEX 信号仍在东京采,以紧凑消息推到法兰克福;法兰克福盒子在最新状态上复核后发送,包含证据回传东京触发对冲(单程 ≈ 120 ms,可接受)。
- 跟踪:Alpenglow 主网时间(11/9 窗口)、Firedancer Votor 支持、SIMD-0306 —— 都会改变落地与终局假设。

## 6. 可靠性清单(对应事故)

| 事故 | 规则 |
|---|---|
| 9/24 交易节点 403 → 已上链交易当失败 → 裸多 | 传输错误只进 UNKNOWN;状态只由链上证据(≥ 2 个独立运营商一致)改变;UNKNOWN 期间不做任何反向操作 |
| Solana "confirmed" 但 `err != null` 幻影成交 | 成功 = `err == null` 且余额/内部指令符合预期(Solana 接入时适用) |
| 9/20 AIN 插针:单点采样 + 失败重试不复核 | ConfirmWindow 跨 ≥ 2 块;每次重试前必须在最新状态上重新预检(可选 L0+L1);不达标放弃本轮 |
| JCT 重试用旧价 | 意图携带的价格只在生成它的那个事件里有效;重试是新意图 |
| 公共 RPC 的 pending nonce 漏掉交易 | 本地 nonce 分配器(槽 → 候选集合) |
| 并行 multicall 把 IP 从所有公共节点封禁 | 端点令牌桶/冷却/降权;来源按运营商计;可用独立来源 < 2 → `SourcesLow` + P0 |

## 7. 可选扩展:纯链上 backrun(F 类)

- 触发:L0 看到某薄池一笔 swap 把价打偏(9/20 的 $200 → +5.6%),下一块回归几乎确定。
- 执行:原子 swap 合约 + bundle(`revertingTxHashes=[]`),与 CEX 无关;复用 §2 与 §10 的组件,只是策略在 chain-core 里而不是 sequencer 里。
- 前提与触发条件:builder profile(§10)+ L0 全覆盖 + 起止同币的合约变体已就绪,且 cdex(D 类)在新框架上稳定。

### 10.1 自建节点(权威状态源)

- **自建 bsc-geth 全节点 ×1(东京)**,快照同步、`--tries-verify-mode none` 快节点模式;并行试 reth-bsc(alpha),稳定后切换。硬件:16 核+、64–128 GB、2 × 4 TB NVMe;放独立主机(见 02)。
- 作用:`eth_call`/状态读取(本机 ≈ 0.9 ms,远端 ≈ 40 ms)、revm 的状态后端、回执与 nonce 的证据源之一、`eth_getFinalizedHeader` 终局判定、公共 mempool 观察(散户单)。
- 接入 BlockRazor Full Node Sync 流 + 静态 peer 以缩短块首达时间。
- 节点与 chain-core 同机时用本机 IPC socket(不走 HTTP);chain-core 订阅 `newHeads`、目标池子的 `logs`、`newPendingTransactions`。

### 10.2 块流与 pending 流(比节点更早)

- BlockRazor(东京区域)与 bloXroute BDN(新加坡区域)的块流并行接入,按 hash 对齐取先到;实测差异决定长期保留哪家。
- 用途:比自建节点早 50–150 ms 看到新块 → 更早看到自己交易的包含证据(早证据 `IncludedOk{EARLY}`,需在若干块内被回执印证)→ 更早对冲。

### 10.3 L0 池状态(闭式定价)

- 事件驱动维护 PancakeSwap V2(reserves)、V3(liquidity、sqrtPrice、tick bitmap、tick 流动性)的内存镜像;来源是 Swap/Mint/Burn/Flash 日志;每块结束用 `eth_call` 抽样校验(drift 检测),漂移即全量重建该池。数学在 [hft-amm](../crates/hft-amm/README.md)。
- 报价 = 纯数学,< 50 µs;支持多跳路由(同 §2.3 的 `bsc_route` 一跳桥接)。
- **PancakeSwap Infinity(V4)带 hook 的池子不能闭式算**(动态费用依赖 `beforeSwap`,且可能与 sender 相关):白名单制,只用 L1 模拟。
- free profile 也可单独启用 L0(条件:免费 WS 提供可靠 `logs`)。

### 10.4 L1 revm 精确模拟

- 对 `latest` 状态(本机节点后端 + 热缓存)模拟完整 calldata(`SwapGuard` 外壳 + Universal Router 或自有合约路径),得到精确 `amountOut`、`gasUsed`;热缓存下亚毫秒。
- 用途:最终 `minOut` 与 `gasLimit`(× 1.2–1.3);builder 也会模拟,失败即丢,所以本地先模拟能省掉无效投递。
- 发送前必须在**最新块**上再模一次(L0 的 ConfirmWindow 要求跨 ≥ 2 块,L1 在发送前一刻校验)。

### 10.5 bundle 构造与出价

- bundle 内允许 0 gwei 交易,竞价方式是**直接向 builder EOA 转 BNB**(48Club、Jetbldr 明确优先此种出价);出价在 `SwapGuard` 合约内转给 builder(不用独立的 N+1 转账)。
- 出价 = 预期净利 × 比例(参数),上限保证成本线;`maxBlockNumber = current + 2`,`SwapGuard.maxBlock` = bundle 的 `maxBlockNumber`;`revertingTxHashes = []`(失败不上链不付费)。
- 每家 builder 一个变体(出价收款地址不同),共享 nonce(同一槽里的候选)。

### 10.6 多 builder 并发直投

- 同一 bundle 同时投 48Club `puissant-builder`、BlockRazor、bloXroute(`mev_builders: ["all"]`)、Blocksmith AP、Jetbldr AP;`Sent` = 至少一家 builder 确认收到;记录每家的接收时间与包含结果,持续统计**每家的真实包含率与"被 builder 自营抢跑"的比例**,据此动态调整投递集合与出价。
- 回执证据源:本机节点 + 付费 RPC(NodeReal、QuickNode/Chainstack)+ builder 的 bundle 状态接口(48Club `explore.48.club/v2/bundle`)+ 块流;仍需 ≥ 2 个独立域一致(§2.7)。
- 传输:HTTP/2 长连接预热;每家独立超时;任何 HTTP 错误只进 UNKNOWN。

# 02 · 硬件与托管方案

> **实现以 [`hft/`](../README.md) 规格为准,本章是设计证据;冲突处以 hft 为准。** 线程计划、主机类与内存表归 [hft-core](../apps/hft-core/README.md#线程计划),调优即代码归 [deploy](../deploy/README.md) 与 [host-tuning](../docs/runbooks/host-tuning.md)。
>
> 依据:[research/05 硬件/托管/调优](research/05-hardware-hosting-os-tuning.md)。核心结论一句话:**网络放置(百 µs 级)≫ 软件栈(十 µs 级)≫ 单项内核参数(µs 级)**;所有目标交易所都在东京 AWS,所以基准形态的正确答案是"同 AZ、同 spine 的 AWS 实例 + 调优内核栈",而不是 colo。主机类是部署配置(同一份 `aarch64` 二进制,只换线程计划与调优):新系统先以 `dev2` 在现有 `c7g.large` 上开发测试(功能、正确性、交易所测试网/模拟盘联调与模拟账户;**不放正式实盘账户**;与 cdex 正式账户共机,受资源护栏约束;无延迟验收),大体没问题后统一升级主机:升级主机同时运行 `prod` 与 `sim` 两个 hft-core 实例,在那里做延迟验收,门槛满足后开始正式实盘([11 §6](11-实施路线图.md))。主机档位(2026-10-03 M0-d 起,M0-e 修订):**默认 `c32`**(`c8g.8xlarge`,32 vCPU/64 GiB),`c16`(`c8g.4xlarge`,首批下单 venue ≤ 4)只在 M3 末满订阅探针达标且启用 `epoll_pwait(0)` 时保留为候选,`c8`(`c8g.2xlarge`)只能承载 prod(无 sim);档位由 M3 末满订阅探针选定([11 §3.2](11-实施路线图.md)),宁可上更大档位,不砍首批 venue。`c4`(`c8g.xlarge`)只作联调档,`metal`(x86 剖面)是可选扩展。

## 2. 基准形态:AWS 东京,同 AZ

### 2.1 步骤

1. **AZ/spine 探测(< $50)**:在 apne1-az1 / az2 / az4 各开 3–5 台 Spot(`c7i.large` 或 `c8g.large`),**每台一个 Cluster Placement Group**(不同 CPG 落在不同 spine),对 Binance(fstream/ws-fapi/api)、OKX、Bybit(11-12 迁入后重测)、Bitget、Gate、KuCoin、Hyperliquid 的全部解析 IP 测 TCP 握手 `minrtt`(`ss -ti`)与 WS 首帧到达分布(HW RX − 交易所 `E`),持续 1 小时以上、覆盖一个活跃时段。保留最优 (AZ, CPG)。**在 M1.5 之前做**(M1.5 与 M3 末探针的租用实例开在胜出 AZ;R8-11);此后**每周重测**(交易所端点与我们的实例都会因扩缩容而移动)。结果同时决定机外看门狗的位置:Binance 若与 dev2 同在 az2,看门狗改到第三 AZ 的 t4g.nano([11 §6](11-实施路线图.md))。
2. **落地**(统一升级到选定的主机类或启用可选 `metal` 时):在胜出 AZ 用胜出 CPG(或在其中新建)+ 关联的 Precision Time Placement Group(若该实例支持),启动生产实例;用 On-Demand Capacity Reservation 锁容量(metal 在东京可能缺货)。M1.5、M3 末探针的按需租用实例与每个里程碑末的参考机也开在同一 AZ(以 az-probe 为准)。另预建第二 AZ 的待命清单(预建 ENI-B/ENI-C,每个正式版带它的 `host_expect`);网卡 MAC 只在运行期核对、不进发布哈希,所以换 AZ 重建不必先发版。
3. **三块 ENI(`c32` 另预留第四块)**:ENI-A 随实例启动(管理、冷进程、S3 上传;IRQ 在核 0);**ENI-B** 是 prod 的交易网卡,在驱动加载后再挂载,全部队列的 IRQ/软中断钉在一个**专用 IRQ 核**(升级主机类的核 1,不放任何线程),热线程只做非阻塞 `recvmsg`;**ENI-C** 是 sim 实例的网卡(sim 出口 IP = ENI-C 的私有 IP + EIP),队列 IRQ 钉在 sim 的一个核上,使 sim 的行情包永远不在 prod 的热核或 IRQ 核上处理。**ENI-B2**(R8-11,只在 `c32`,默认不启用):第二块交易网卡,IRQ 钉在预留的核 28;启用后延迟敏感流(BBO、下单、用户流)留在 ENI-B,批量流(深度、成交、标记价、REST)走 ENI-B2;ENI-B2 只有行情与 REST,不进任何 key 白名单。启用条件由 M3 末探针定([11 §3.2](11-实施路线图.md)),清单字段 `[eni_b2]` 归 deploy。原设计"ENI-B 按 4 元组把每条交易所连接导到它的 venue 线程所在核"已被 hft 取代(见 §4.2);ntuple 只作可选 A/B(ENA 上 `ntuple-filters` 是否可用待核实)。ENA 驱动用 GitHub 2.17.3(PHC、HW RX 时间戳、ntuple、AF_XDP ZC、Large LLQ 控制)。
4. **OS 调优**(见 §4)+ 验收(见 §6),全部以代码形式进入 `deploy/`。
5. 稳定 1 个月后转 1 年 Savings Plan / RI(约 −34%)。

基准形态的发布目标是单一 `aarch64-unknown-linux-gnu`(`target-cpu=neoverse-v1`,覆盖 `dev2` 的 c7g 与 `c16`/`c32` 的 c8g);升级只换配置,在 dev2 上的测试网联调与模拟长跑稳定后统一进行(M7),正式实盘在升级主机上开始。

**为什么默认候选从 `c16` 改成 `c32`**(2026-10-03 五路评审 V5 P1-3、§5-5,R8-10):收包改为中断驱动后,ENI-B 的 IRQ 要独占一个核;核 0 不能再同时承担 IRQ、housekeeping、persist 与段预创建;BBO 与深度要分线程。按这些原则,全部 6 个下单 venue + sim 同机约需 28 个核,`c16` 只放得下 ≤ 4 个下单 venue。延迟优先,所以宁可上更大档位,也不砍首批 venue。核号表与内存表唯一归属 [hft-core](../apps/hft-core/README.md#线程计划)。

**为什么 `c16` 只是有条件的候选、选档移到 M3 末探针**(第四轮评审 W5 N-P1-2、N-P1-6,R8-11):`c16` 原计划只有一条 feed-bbo 线程轮询全部 venue 的 12 个 BBO socket,一圈空轮询约 12–24 µs,光节拍就让 `kernel_rx` 的 p50/p99 预算不闭合。现在的 `c16` 计划改为**两条 feed-bbo + 一条 feed-md**(feed-bbo 初值按 4 + 8 个 socket 分组,M3 末探针后重分;原来的两条 feed-md 合为一条,core 行情不含全量深度;核号表归 [hft-core 线程计划](../apps/hft-core/README.md#线程计划) 的 `c16` 节),每条 feed-bbo 仍有 ≥ 3 个 socket;允许 ≥ 3 个 socket 的行情线程每圈 `epoll_pwait(0)` 只读就绪的 socket([03 §3.1](03-网络与传输层.md))后才可能闭合,而这要在完整线程计划、满订阅下实测,M1.5 的单 venue 切片看不到。所以档位由 M3 末满订阅探针按 `c16` 计划实测后选定([11 §3.2](11-实施路线图.md)),默认 `c32`。

**prod + sim 同机的资源划分**(R8-9、R8-10):sim 实例只用非隔离核,永不占 prod 的热核;独立 `hft-sim.slice`(CPU、内存上限);独立的 journal 与冷盘目录;独立网卡 ENI-C(sim 出口 IP = ENI-C 的私有 IP + EIP,不占 prod 的按 IP 限速;IRQ 钉在 sim 的核上)。同机干扰的验收:`prod` 的 p99 因 sim 运行的劣化,2 小时一块随机顺序开/关 sim、按块配对,bootstrap 95% 置信区间上界 ≤ 1.05(R8-11;判定唯一归属 testing §8.2)。主机档位必须按"prod 线程计划(每个下单 venue 的 gw 独占线程,规则 T8 无例外)+ sim 实例的核与 ENI-C IRQ 核 + 批处理与冷进程"合计选定;隔离核列表由 hft-core 线程计划生成。规格唯一归属 [hft-core](../apps/hft-core/README.md) 与 [deploy](../deploy/README.md)。

**可选 `metal` 主机类推荐 c7i.metal-24xl**(x86 剖面;触发条件:升级主机上测出主机侧是瓶颈,且 CEX-CEX 有利可图),理由:
- x86 生态零风险(`sonic-rs`/`rustls`/`revm`/`aws-lc-rs` 的 SIMD 与性能数据都以 x86 为准;ARM64 上 rustls 略慢、`cntvct` 分辩率待核实);
- 有 PHC:**没有 PHC 就测不了到交易所的单向延迟**,而"测量先于优化"是整套方法论的基础;
- C/P-state 可控 + 关 SMT 后 48 个独占物理核:hft-core 隔离核 ≈ 16(feed/gw 分线程 + seq + advisor)、warm/housekeeping 2–4、chain-core 4、冷进程与内核 8,余量留给 bake-off;bsc-geth 不上这台(无实例存储、L3 污染);若同机跑冷进程,用 Intel RDT/CAT 给热核保留 L3 份额(启用时验证);
- AWS 数据显示它"默认噪声最大、调优后与最好的一档同级",说明调优清单能被验证。

**bake-off**(启用 `metal` 时):用我们的真实栈在 `m8azn.metal-12xl` 上按小时租用跑同一回放与 mock 交易所,若 tick-to-trade p99 优于 c7i 3 µs 以上,则把 A 类策略的执行放到 m8azn(可选专用执行机;它不需要 PHC:内部分段用 TSC,单向延迟由同 CPG 的 PTP 探针机代测)。`c8g.metal-24xl` 同样进 bake-off,作为成本替代的依据。

## 3. 可选:裸金属 + Onload(colo,仅在条件触发时)

**触发条件**:(a)某主要目标所迁出 AWS 或提供 colo/交叉连接;(b)基准形态测得 AWS 网络抖动(而非我们的栈)主导 p99 且 hunting 无法改善;(c)需要自有跨区域链路(东京 ↔ 法兰克福)。

**形态**:Equinix TY2/TY6–8 或 AT TOKYO CC1 半柜(Direct Connect 站点),单路 **EPYC 9175F**(16 核 5.0 GHz,512 MB L3 = 每核 32 MB)或 9575F,试验机可用 Ryzen 9950X3D;**AMD Solarflare X4** 网卡(Onload 半程 ≈ 0.6 µs,比 X3 低 27%)或 ConnectX-7/8 + XLIO;GNSS grandmaster(Timebeat Open Timecard 系列 £225–3,138,或 Meinberg 级 $5–15k)→ PTP < 1 µs;Direct Connect 10 G 专用端口($1,564/月)公共 VIF 到 ap-northeast-1 + transit 备路。OPEX $4–6k/月 + CAPEX ≈ $30k。

**明确认知**:colo → AWS 公共端点 RTT ≈ 1–2 ms,**永远输给同 AZ EC2**(Zenlayer 自测 ≈ 2 ms;所有东京裸金属云 Vultr/Latitude/OCI/GCP 同样 ≥ 1–3 ms)。colo 的价值只在硬件级 NIC 与非 AWS 交易所。Equinix Metal 已于 2026-06-30 终止服务,不再是选项。

## 4. OS/内核调优清单(基准形态;按 c7i.metal 写成,Graviton 差异见 §4.3)

以 AWS `trading-latency-benchmark` 的 `tune_os.yaml` 为基线,按 research/05 §3 修正。**原则:先测(`hiccups`、`rtla osnoise/timerlat`、`perf stat`),一次改一项,24 h 直方图对比。**

### 4.1 GRUB(x86)
```
transparent_hugepage=never audit=0 nmi_watchdog=0 nosoftlockup mce=ignore_ce
nohz=on skew_tick=1 acpi_irq_nobalance clocksource=tsc tsc=reliable
cpuidle.off=1 intel_idle.max_cstate=0 processor.max_cstate=0 idle=poll intel_pstate=disable
isolcpus=domain,managed_irq,<hot> nohz_full=<seq> rcu_nocbs=<hot> rcu_nocb_poll irqaffinity=<irq>
hugepagesz=1G hugepages=<N> nosmt mitigations=off
```
`<hot>` = prod 实例全部 `Spin` 线程的核(由 hft-core 线程计划生成;sim 的核不在其中),`<seq>` = sequencer 核(`nohz_full` 默认只给它),`<irq>` = 核 0(housekeeping、系统服务、ENI-A)与核 1(ENI-B 的 IRQ 独占;启用 IRQ 拆分时加核 28)。IRQ 专用核也加入 `rcu_nocbs`(R8-11,W5 N-P1-1:RCU 回调不在软中断核上执行);`isolcpus=managed_irq` 只排除隔离核,所以 NVMe 等 managed IRQ 的 effective_affinity 不落在 IRQ 专用核由 hostprobe 单独检查。收包模型相关的项不在 GRUB 里,全部在 §4.2 的运行期调优。`mitigations=off` 在单租户单用途盒子上可接受;`idle=poll` 让空闲核 100% 功耗,metal 上无所谓。本节是 x86 metal 的写法;Graviton 的 GRUB **不写** `transparent_hugepage=never`(THP 用 `madvise`,且是 hostprobe 的 required 项,§4.3)。

### 4.2 运行期(systemd oneshot,随发布归档)
| 项 | 设置 | 预期 |
|---|---|---|
| irqbalance | 关;ENI-A 与其他 IRQ → 核 0;**ENI-B 全部队列 IRQ → 核 1(独占,不放任何线程)**;ENI-B2(启用时)→ 核 28;ENI-C 全部队列 IRQ → sim 的一个核;hostprobe 检查 NVMe 等 managed IRQ 不落在 IRQ 专用核,TASK_ON_HOT 检查覆盖 IRQ 核 | IRQ 不漂到隔离核;热核不处理软中断;sim 的包不进 prod 的核 |
| 队列 | ENI-B 用 ENA 默认队列数(c8g 上的队列数与 RSS 哈希在 M1.5 核实);不按连接导核;ntuple / RSS 源端口预计算只作可选 A/B;IRQ 核空闲时是否保持唤醒按 M1.5 的 A/B 定,允许的形式只有 hostprobe 规则登记的两种(`nohlt` 或列入白名单的 keepawake 线程,[tools](../tools/README.md)) | 全部收包软中断在 IRQ 核完成 |
| 合并 | `ethtool -C <eni-b> adaptive-rx off rx-usecs 0 tx-usecs 0`(ENA 默认 Tx 静态 64 µs!) | 去掉批处理等待 |
| 卸载 | `ethtool -K <eni-b> gro off lro off tso off gso off sg off` | 去掉批处理延迟 |
| 环 | `ethtool -G <eni-b> rx 4096 tx 1024` | 抗突发 |

**收包模型的取舍**(2026-10-03 五路评审 V5 P0-1,[13 §17](13-设计评审与优化.md)):本表原先的"busy poll"一行是 `net.core.busy_poll=50 busy_read=50`、每 socket `SO_BUSY_POLL`、`napi_defer_hard_irqs=2`、`gro_flush_timeout=200000`(LWN 实测:中断模式 p99 21.1 µs → 独立核轮询 14.0 → threaded NAPI busy poll 13.0),IRQ 钉到各 venue 线程所在核。它与 hft-net"IRQ 在 hk 核、热线程不做 NAPI 轮询"的规格并存,两种模型混在一起时:新 socket 默认继承 `busy_read`,热线程每次空读都替同一队列上全部 socket(包括同机 sim 的行情)做 NAPI 轮询;没人轮询的队列,包会被 `napi_defer_hard_irqs` + `gro_flush_timeout` 压最多 200 µs。忙轮询在 p99 上的 7 µs 收益不抵这两个风险与它占用的热核,所以只保留中断驱动;threaded NAPI busy poll(内核 ≥ 6.17)只作日后 A/B。数值与校验的唯一归属是 [deploy](../deploy/README.md) 与 [hft-net](../crates/hft-net/README.md)。

### 4.3 Graviton 差异(`c4`/`c16`/`c32`;`dev2` 只做最小、可回滚的调优,见 `hft/deploy`)
THP 用 `madvise`(非 `never`;GRUB 基线不写 `transparent_hugepage=never`,否则 hostprobe 的 THP required 项不过、hft-core 拒绝启动);无 C/P-state 项(IRQ 核的空闲策略按 M1.5 A/B 定);收包模型同 §4.2(`busy_poll`/`busy_read` = 0);`cntvct_el0` 作时钟(频率在 M1.5 实测);AWS 数据显示 c8g 调优前后中位几乎不变(它本来就稳),只有 max 下降。dev2 只有一块网卡,ENI 分工与 IRQ 独占核不适用(dev2 无延迟验收)。

## 5. 时间与测量

- **UTC 源**:PTPG 内 ENA PHC → chrony,误差界 < 40 µs(m7i 实测 ±25–34 µs);非 PTPG 实例只有 NTP(±1.4–1.7 ms),不能做单向延迟测量。
- **交易时钟**:TSC(`rdtscp`,invariant),启动期校准频率;运行期 housekeeping 每 1 000 ms 写一条 `ClockStatus`(Meta 记录,含 `(tsc, phc, calib_err_ns)`);journal 段头记录 (tsc0, utc0, ratio) 与误差界。含 PHC 端点的分段按样本前后两条校准对线性插值换算,逐样本给误差界,误差界 > 1 µs 的样本计入 `unsynced_cal`、不进分位数;HW 戳不可用时以 `sw_rx`(REALTIME)为锚。原来"校准对 60 s 一条、取最近一条阶梯换算"的写法,在 TSC 与 PHC 差 0.1–1 ppm 时误差可达 6–60 µs,与 `kernel_rx` 预算同量级(W5 N-P1-4,R8-11;规则归 [latency-budget](../docs/latency-budget.md))。
- **单向延迟到交易所**:HW RX 戳 − 交易所事件戳(ms 分辩率),大样本分布估均值(~0.1 ms 精度)与形态,区分"AZ 距离"(常数)与"交易所内部扇出/LB 排队"(随负载);订单 ack 往返取半作对照。
- **自身十点分解**(AWS T1–T10):D2 HW RX → 内核 RX;D3 内核 RX → 应用;D4 应用处理;D5 应用 TX → 内核 TX。仓库内的指标名用 `kernel_rx`(D2+D3)、`nic_to_kernel`(D2)、`kernel_to_user`(D3,`sw_rx` 常态记录后进生产直方图,不作门槛);目标 `kernel_rx` p50 ≤ 8 µs、p99 ≤ 20 µs(中断驱动,`c32` 的分配,待 M1.5 与 M3 末探针实测;`c16` 的预算由 M3 末探针给出;唯一归属 [latency-budget §3](../docs/latency-budget.md))。
- ENA **只有 RX 硬件戳、无 TX 硬件戳**;PHC 读取上限 125 次/s(只用于校准,不在热路径)。c8g 上 HW RX 戳与 PTP/PHC 是否可用,两份调研说法相反,在 M1.5 租用的 c8g 上第一时间核实([12 A7](12-风险与未决问题.md))。

   - GitHub 的 workflow run usage(timing)接口已宣布关闭。
   - 自 2026-10-01 起,check、workflow run 与 status 按仓库的保留期删除(默认 90 天)。
   - arm64 标准 runner 的用量计入私有仓库的免费分钟。
   - libFuzzer 的 `-timeout` 按墙钟判定;目标在回调里调用 exit 会被记为崩溃并写出 `crash-` 文件。

### P1

**N-P1-1 dev2 批处理的 SCHED_IDLE 不跨 cgroup 生效**

- **场景**:
  - `hft-batch.slice` 在 `hft.slice` 之下。`hft.slice` 的 `CPUWeight=50`,`system.slice` 是默认的 100。
  - 按任务设的 `CPUSchedulingPolicy=idle` 与 `CPUWeight=1` 只在 `hft.slice` 内部比较。在根一级,调度器比较的是 `hft.slice` 和 `system.slice` 两个组实体,唤醒抢占也按"匹配的 sched_entity"判定(cgroup SCHED_IDLE 补丁说明)。
  - 所以批处理满载时,每个被争用的核上旧系统与 hft 按 100:50 分配,批处理最多拿走 1/3;旧系统因此产生的等待计入 `system.slice` 的 cpu "some" 压力。
  - deploy:245"争用时完全让出",以及 hft-core:448、477 的同类说法都不成立。M3 标定演练(hft-core:535)可能因此失败、触发退路;反过来,也可能演练恰好通过,而旧系统在高峰时被拖慢。
- **修复**:
  - dev2 上把批处理放到根级 slice,例如 `hftbatch.slice`(名字不带 `-`,避免被 systemd 当成嵌套),设 `CPUWeight=idle`(写 `cpu.idle=1`,需 systemd ≥ 252、内核 ≥ 5.15)。内存拆成 `hft.slice` 864 + `hftbatch.slice` 512,合计 1,376 MiB 不变。
  - 演练前读 `/sys/fs/cgroup/cgroup.subtree_control` 与该 slice 的 `cpu.idle`,确认设置生效(待核实)。

**N-P1-2 升级主机上的 `hft-replay-verify` 有两处实现缺口**

- **(a) `verify = false` 时启动失败**:
  - 基础单元带 `ExecStartPre=+/usr/bin/systemctl stop hft-verify.service`(deploy:305)。
  - M8 起正式主机的清单是 `verify = false`,不安装 `hft-verify.*`(deploy:145、454;launch:84)。对未加载的单元执行 `systemctl stop` 会报 "not loaded" 并以非 0 退出,于是每日回放每天都启动失败。
  - deploy 的测试表(deploy:569)只测了 `LoadState`,测不到这一点。
- **(b) 并发规则只在 dev2 实现**:
  - hft-core:416 规定"全部主机类:回放运行时 archiver 与 pipeline 暂停"。deploy 只在 dev2 的覆盖文件里实现了它(deploy:252)。
  - c16/c32 的 `hft-batch.slice` 上限 4,992 MiB 是按"回放时 archiver/pipeline 不在"算的。实际并发时是 4,096 + 2,048 + 768 + 128 = 7,040 MiB,OOM 会先杀回放(+900)。⑦ 满规模段与 M8 的每日回放都受影响。
- **修复**:
  - 把"暂停 archiver/pipeline、结束后恢复"写进基础单元。
  - 所有 `systemctl stop` 加 `-` 前缀(忽略未加载的单元),或由生成器按 `verify` 开关生成。
  - 增加用例"`verify = false` 的主机上回放完成"。恢复时的竞态见 P2-1。

**N-P1-3 CI 额度闸门不可用,且会造成热修死锁**

- **死锁**:
  - preflight 第 3 条要求 `main` 上"实际执行了的最近一次 nightly 是绿的"(development:148)。
  - 用量 ≥ 1,500 min 后每夜任务被跳过(development:183、211)。若最近一次实际执行的每夜正好是红的(这恰恰是需要热修的情形),到月底任何正式版都过不了 preflight。

**N-P1-8 换 AZ 重建时从 S3 恢复冷副本没有工具,epoch 可能回退**

- **场景**:
  - incident-response:275 要求"不能摘卷时从 S3 取回最近已提交的小时",但 journal-archiver 只有 `run`、`check`、`backfill` 三个子命令(journal-archiver:40–41、217),没有恢复命令。AZ 故障时 EBS 卷恰好摘不下来,所以这正是换 AZ 的主路径。
  - DurableMeta 存在 `<cold_root>/<instance>/meta/`(hft-journal:161),不归档到 S3。恢复时 epoch 取 max(快照, DurableMeta) + 1(hft-core:606),DurableMeta 丢失后就只按快照算,可能不大于故障主机最后一段运行用过的 epoch。
  - ClientOrderId 由 epoch、slot、gen 组成(hft-types:326–328)。新主机按快照状态重新分配,会和故障主机最后一段运行发出的订单撞号:网页撤单能清掉挂单,但迟到的回报会被认到新主机的槽上。
  - 新主机续写的段号与故障主机已部分上传(未提交 manifest)的对象键相同,上传时会 Conflict 并进入 quarantine(journal-archiver:158–161)。
- **修复**:
  - 增加 `journal-archiver restore` 子命令。
  - DurableMeta 每次写盘后作为快照文件上传。
  - 恢复时 epoch 另加安全间隔(例如 +64)。
  - S3 键里带"恢复代",避免与故障主机的对象撞键。
  - M7 验收加一次演练:第二 AZ 的待命网卡 + 新卷从 S3 恢复 + `--recover-from-snapshot`,用测试网账户。

   - **回放结束后批处理可能不恢复**:回放的 `ExecStopPost` 用 `start --no-block` 拉起 archiver 与 pipeline(deploy:252),而 `hft-unit-idle` 把 `deactivating` 也当作"忙"(deploy:523)。存在竞态,archiver/pipeline 可能被跳过且没有定时器再拉起。
   - **开机时 sim 可能起不来**:hft-core 单元只有 `ExecStartPre` 检查护栏 is-active,没有 `After=hft-dev2-guard`(deploy:248),开机时可能连续失败 3 次后撞上启动次数限制(deploy:302)。
   - **非干净停机后 sim 不交易**:护栏停机超过 `TimeoutStopSec`、崩溃或整机重启之后,Sim 账户带 Recovery cap(hft-risk:416;hft-core:560),护栏的自动重启救不回交易;同一天第二次触发就可能停机超过 24 h,⑦ 重新计时(testing:345)。
   - **修复**:加 `After=`;恢复动作放到独立的 oneshot 单元;Sim 账户的 Recovery 处理见 §5-4。
2. **I/O 与护栏判据**
   - dev2 护栏没有 `system.slice` 的 `io.pressure` 停机信号,`hft-core.slice` 的 I/O 不限(hft-core:459),也没有 IOPS 上限。
   - c32 的 sim 写上限 30 MB/s(hft-core:458)也限制了 Drain 时写 Model 检查点(hft-core:386)。检查点较大时 Drain 超过 20 s 被 SIGKILL,会破坏 ⑩ 期间 sim 每小时的干净启停(待核实检查点大小)。
   - `system.slice` 的压力和 swap-in 也可能由旧系统自身引起,却照样停 hft,并计入退路(b)的"一周 ≥ 2 次"(hft-core:524)。
   - 整机 PSI 的告警级别两处不同:hft-core:509 写 P2,watchtower:129、276 写 P1。批处理永远处于可运行状态,整机 cpu "some" 会长期偏高,P1 天天出现,触发"P1 一周 ≥ 3 次写 postmortem"(incident-response:26)。
3. **hft-verify 的进程与限额细节**
   - **停止信号**:没有设 `KillMode`(deploy:452),systemd 停单元时会把 SIGTERM 发给全部子进程。libFuzzer 以 72 退出;`hft-dst` 死于 SIGTERM——这两种情况都不在分类表里(tools:437–442)。
   - **harness 超时的判别**:testing:64 与 tools:438 互相指向对方定义存法,实际都没定义。libFuzzer 把回调里的 exit 记为崩溃并写 `crash-` 文件,超时会被误判为失败而清零;`-timeout` 按墙钟判定,在 idle 调度下被饿时会误触发。
   - **内存**:`-rss_limit_mb` 按单元 MemoryMax 设定,但 dev2 上真正的约束是 512 MiB 的 slice(成员上限合计 832 MiB),会先被 cgroup OOM 以 SIGKILL 杀掉;语料目录无限增长。
   - **修复**:`KillMode=mixed`;退出码 72、SIGTERM、SIGINT 一律记"中止";harness 把超时输入写进单独目录后正常返回;`-timeout` ≥ 600 s;限额按 slice 的剩余内存计算;定期 `-merge` 收缩语料并设上限。
4. **验证账本的键与口径**
   - files source 的不可变键 = 前缀 + 相对路径(journal-archiver:148)。其中 `crashes/dst/inflight.json` 每个种子都会改写(tools:460);各主机最小化出的 `.min` 内容不同;同一 crash 的 resolutions 可能在两台主机上分别写出——都会 Conflict。
   - `path_digest` 不含 `Cargo.lock`、nightly 日期、剖面设置(development:168),依赖升级后旧的累计量仍被计入新版本。
   - **修复**:排除 `inflight.json`;crash 与 resolution 的键带主机段;`path_digest` 加入这三项。
5. **CI 缓存、复现与证据**
   - **缓存共用无效**:`nightly-arm` 构建的是 `ci` 剖面,发布构建是 `release`/`release-hot`,两者共用键 `arm64-release`(development:152、185)。rust-cache 在键已存在时不会再保存,谁先存就决定缓存内容,另一方拿到的缓存没用。上一轮是我建议共用这个键,这里纠正。
   - **复现作业太短**:`fuzz-repro` 20 min 内冷构建 ASan 目标基本不可能(development:175)。建议直接下载对应 Release 的验证包,用包里已编译好的 fuzz 二进制、按默认限额运行,不再编译。
   - **热修被验证包绑住**:每个正式版发布都要求验证包作业成功(development:160)。热修不需要 ③④,应允许 Admin 选择跳过,事后再补出包(development:166 已支持)。
   - **证据会被删除**:2026-10-01 起 check 与 workflow run 按仓库保留期删除。preflight 依赖这些运行记录(development:146–148),解耦豁免的证据只在作业摘要里(development:137)。保留期要设到上限,并把证据写进 `RELEASE.json`。
   - **生成物无处生成**:金样与各类生成物必须与生成器同一提交提交(development:71、138),但本地不要求能编译(development:12)。需要一个 CI 作业重新生成并把补丁上传为 artifact。
6. **⑩ 测量窗口与 `verify` 开关**
   - 测量窗口不防主机重启:只 `stop` 了 verify 定时器,重启后 `OnBootSec` 又会拉起;`systemd-run` 建的交替定时器是临时的,重启后丢失(host-upgrade:36–37)。修复:用持久标志文件 + 发布内的正式定时器。
   - 切 `verify = false` 要发一个补丁版(launch:84),这个新版本还要做候选版本补跑。建议同一发布里放两份清单(`tokyo-cex-1` 用于 M7、`tokyo-cex-1-live` 用于 M8),M8 时只改 `host-local.toml` 后重新激活。
   - 生成器只检查待命清单的 `host`/`class` 与主清单一致(deploy:147),应同时检查 `verify`、`formal_live`、`instances`。
7. **D-23 的维护静默时长**
   - 维护静默最长 30 min,watchtower 在第 3 步停掉、第 8 步才恢复(launch:79–86),期间看门狗读不到延长的维护时间;看门狗的缓存在它自己重启后也会丢失。
   - launch:82 的游标路径与 journal-archiver:204 不一致。
8. **IAM 与 IMDS 细节**
   - 正式主机的角色缺 SSM 托管权限(deploy:411),而 SSM 是破窗通道。
   - 各消费者角色缺 KMS 授权。
   - root 执行 `journal-archiver check`(launch:80)时实例角色没有 S3 权限,需要写明使用哪份凭证。
   - 凭证代理自己的告警 token 不在秘密表里(deploy:399–407)。
   - dev2 不锁 IMDS:hft 的非 root 进程能拿到与旧系统共用的角色,旧系统进程也能读 hft 的秘密(建议见 §5-7)。
9. **其他小项**
   - 按组激活后,清理旧版本时必须保留所有组的 current 与 previous 链接所指的版本(release-and-deploy:70),否则可能删掉 cold 组正在用的 venv。
   - `hft` 用户打开 `/dev/cpu_dma_latency` 的权限没有写明(hft-core:555;deploy:302、71)。
   - `hft-shm-release` 删除热段文件后,kill-switch 等读者的映射仍会占住整段 tmpfs 页(kill-switch:67);`hft-window stop` 应核对 tmpfs 已用量,而不是文件列表。
   - ⑥ 的"连续 3 天"在护栏停掉 prod 时算暂停还是重新计时,没有定义。
   - 退路(a)的新主机没有 archiver,回放报告与验证运行记录传不回 dev2 的 watchtower。
   - 以 root 执行 `hft-dev2-guard clear` 可能新建 root 属主的事件或状态文件,护栏用户之后写不进去。
10. **口径残留**

    - deploy:264 的二级动作没列 reconciler,与 hft-core:516 不一致。

## §4 应保留的设计

- **dev2 护栏**:
  - 只按旧系统 cgroup 的信号停 hft,整机 PSI 只告警。
  - 持久的 tripped 标志 + `ExecCondition=` 统一挡住所有启动路径;窗口标志放在 `/run`;不用 `Conflicts=` 与 `mask`。
  - 只自动重启 sim、每天至多一次,"无人启停"用 `InactiveEnterTimestampMonotonic` 判定;polkit 按"用户 + 单元 + 动词"授权。
  - `hft-shm-release` 只在 `state = Stopped` 时释放。
- **部署**:
  - `verify` 开关决定装不装,preflight 查 `LoadState`。
  - 按组的 `current-<group>` 与按版本的 venv。
  - S3 键带主机段与 `hft-testnet` 前缀,并在加载时交叉校验 `is_prod` 与前缀。
  - MAC 不进哈希;待命清单随每个正式版发布;看门狗目标是主机本地文件。
- **维护静默**:只降级电话通道、最长 30 min、经 `/healthz` 转告。
- **IMDS**:只放行 uid 0,冷进程用按前缀发放的短期凭证,DuckDB/polars 按凭证文件的 mtime 重建。
- **停机标记**:先写标记再停机、fsync、改名为 `.consumed`、不同范围合并为 `*`、无法解析时按 Global 处理。
- **SmokeOrder**:建在 OMS 槽里;不经模式门但走风控链,#5 不查 `max_px_dev`;`Drain{cancel_resting = false}` 时保留,用来验证交易所死手。
- **验证账本**:按 CPU 时间计量;疑似由 CI 复现;只有失败清零;按 `path_digest` 跨版本累计;开正式实盘的版本补跑。
- **CI**:
  - 额度规则的方向(只停每夜与开发构建)。
  - `conformance-x86` 在被发布的同一 SHA 上与金样比对。
  - 交叉编译作为备用路径。
- **⑩ 与选档**:同机干扰按 2 小时一块、种子随机、bootstrap 判定;M3 末探针定档,M1.5 不定档。

## §5 需要负责人决定的问题(附推荐)

1. **dev2 批处理的 CPU 放置**(N-P1-1)。推荐用根级 `hftbatch.slice` 加 `CPUWeight=idle`。备选是对整个 `hft.slice` 设 idle:sim 也会让给旧系统,符合"旧系统优先",但旧系统满载时 sim 可能被饿到触发看门狗。
2. **CI 额度的读法与破窗**(N-P1-3)。推荐 quota-gate 按作业时长自估用量,并允许 Admin 覆盖。额度耗尽时的应急路径有两个选择:
   - (a) 把仓库镜像到个人账户的私有仓库出包。仍然免费,但用的是 Trading 的额度。
   - (b) 接受"到月初之前不能热修"。
   - 推荐 (a),并每季度演练一次。
3. **测试网 UID 读不到时怎么办**(N-P1-7)。推荐 `uid_policy = Unverifiable`:只允许用于 `is_prod = false` 的账户,需 Admin 签字。
4. **Sim 账户非干净重启后能否自动解除 Recovery**(P2-1)。推荐只含 Sim 账户的实例在没有 `RecoverMismatch`、没有毒丸时自动解除;否则至少报一条 P1"sim 处于 Recovery"。
5. **切 `verify = false` 的方式**(P2-6)。推荐用两份清单切换,不另发补丁版。
6. **护栏的因果判定**(P2-2)。推荐只在 hft 自身用量明显(`hft.slice` 的 CPU 或内存超过阈值)时才停机,否则只告警;退路(b)的触发次数只计这种情况。
7. **dev2 的 IMDS 保护**(P2-8)。推荐只对 hft 的各个 uid 加 nft 丢弃规则,并在 dev2 也跑凭证代理。这不影响旧系统。

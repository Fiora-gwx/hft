## §3 新发现

### P1

**P1-1 Trim 与 L2 逐轮减仓在默认参数下第一步后停滞**
- **场景**:持仓 h = 10 000 USDT,第一步目标 T = 7 500。
  1. 执行层的完成判定是 `|T − pos| ≤ band × |T|` = 1 125(E:335)。MarginStress/Hard 的非零目标同样按带判定(E:348、350)。
  2. 每片 ≤ 500(pc:499)从上往下切:9 500 → 9 000 → 8 500,到 8 500 时判 Done。
  3. 下一轮目标 = 8 500 × 0.75 = 6 375。按"目标的设与留"(pc:207)与生效目标 7 500 比:1 125 / 7 500 = 0.15,不大于 band → 不调用 `ctx.target`。
  4. 结果:只减了 15%,之后永不再动。执行层的停点落在 (8 125, 8 625],其中 ≥ 8 500 的情形都会停。
- **其他受影响的路径**:
  - L2 的"每 `stress_step_ms` 再减一轮"(pc:292)同样只剩一步,之后要等 L2 截止由引擎处理。
  - `Trim{Overweight}`:目标 = cap,执行层在 ≤ 1.15 cap 处 Done;结束条件却要求 ≤ 1.10 cap(pc:278);下一步目标仍等于 cap,与生效目标相同 → 不重发。该 group 永久停在 Trim,期间不做常规调仓。
  - 常规超配减仓同样落在 1.15 cap,与 `overweight_tol` 0.10 不一致(pc:216、226)。
  - `stress_reduce_frac` 取合法下限 0.05–0.13 时(f ≤ b/(1+b)),第一步就落在带内,一步都不减。
- **引用**:pc:187、207、216、226、277–283、292、473、499、514;E:335、348、350。
- **修法**:
  1. Stress、Trim、超配减仓目标的 `band` 设为 0(或 ≤ f/4)。
  2. 每轮以上一步的目标为基准(T_{k+1} = T_k × (1 − f)),步进目标不受"设与留"带宽规则约束,靠 `tag_seq` 区分。
  3. `check()` 加交叉校验:`stress_reduce_frac > band/(1+band)`,`overweight_tol ≥ 执行带`。
  4. 重算 pc:283 的步数与时长。

**P1-2 `open_allowed = false` 持续 30 s 后就不计成本清仓,与 pipeline 的"只平不开"语义冲突**
- **场景**:
  - PCP 的币池规则:有仓位的 group 只要某一轮不满足过滤条件(24 h 成交额、OI、正费率占比 ≥ 0.6、上架天数、交易状态),就置 `open_allowed = false`。滞回只用于"移除"(`drop_after_rounds`)。
  - pc 的处理:`close_only_rounds`(3)× `stress_step_ms`(10 s)= 30 s 后进入 Trim,约 2 min 内减到 5%,不经成本门。
  - 后果:一次 OI 抖动或一期负费率,就让整个仓位以 taker 成本平掉(按例子每次平仓 17 bp);下一轮条件恢复后,又要重新过入场分位与开仓成本门(32 bp)。上一轮 §5-2 推荐的"持续若干轮",应指 pipeline 的轮次,而不是 10 s 的步长。
- **引用**:pc:68、273–283、516;PCP:89–96、104–107;round8e 简报 E14(a)。
- **修法**:见 §5-1。

**P1-3 Model 的下架状态不在检查点的任何一节,也收不到撤回**
- **场景**:
  1. CarryModel 的活跃集要排除"有下架通知"的 group(pc:571),这个状态只能来自 `Notice` 事件。但 Model 状态清单(pc:553)和检查点两节(pc:606–614)都不含它;SDK 也没有生效公告的视图(SDK:486–513)。
  2. 收到下架通知之后的每一天:实盘 Model 一直连续运行,持有这个状态;当天 00:00 的检查点不含它。recompute 从检查点续算时,该 group 回到活跃集,同池分配随之改变,Advice 不一致。门槛 ⑦ 要求"recompute 每日通过"(T:329、350),于是每天失败,直到该 group 被移除,⑦ 重新计时。
  3. 普通重启后,Model 同样会把份额分给下架币。
  4. 撤回走 `Resume{Delisting}` → `Risk{CapCleared}`,而 Model 不收 `Risk`(SDK:225、810),所以状态永不清除。
  5. hft-risk 内部对 Delisting cap 自相矛盾:risk:359 说它不进 cell 计算,risk:532 说它把 cell 降为 CloseOnly(另见 392)。pc:333 依赖的撤回事件能否投递到,待核实(方法:按 hft-risk mode 的 `risk_events` 生成规则走一遍 `Resume{Delisting}`)。
- **引用**:pc:333、553、571、606–614;SDK:225、486–513、810;S:648(公告表,节 24);risk:359、392、532;T:329、350。
- **修法**:
  - SDK 只追加一个视图 `Views::inst_status(i) -> InstStatusView{delist_at_ns, delisting_cap, maint_from_ns, maint_to_ns}`,从 sequencer 公告表与 hft-risk 投影,ModelViews 同样可读;pc Model 改为读视图。
  - SDK 写一条通用规则:Model 的每项状态要么在两节之一,要么能由 ModelViews 当场推出。

**P1-4 门槛 ⑦ 的重新计时路径表漏了决定模拟结果的 crate**
- **场景**:T:346 只列策略包、strat-lib、SDK、exec、risk、oms;T:348 又写"既不属于第 4 条也不属于本条的版本变化同样不重新计时"。于是下列改动既不重新计时,也不需要 7 天回放一致来证明:

  - hft-sequencer:模式门、Ctx 排空顺序、Advice 路由与 `spec_seq`、`quote_live` 聚合;
  - hft-ledger:`PortfolioView` 与换算率;
  - hft-types:`cap_cross_px`、`pair_lot`、`funding_settle_norm_ns`;
  - hft-book;
  - `[sim]` 配置表(SimTuning、延迟与保证金模型)。
- **引用**:T:343–348;sim:225、287;S:134、354、420。
- **修法**:见 §5-2。

**P1-5 quote 模式的撤单不产生 `LatencySample`,⑩ 的 `rep_to_order` 在主网负载下没有样本**
- **场景**:
  - LP、T:358 与 LB:61 都把"Ack 后同一事件撤单"当作 `rep_to_order` 的主样本源,每个探测点每天约 86 400 条。
  - 但 OMS 只在"每订单首个交易所响应时"合成样本(OMS:226、745);`SlotStamps` 只在下单、SendReport 和首个响应时写入(OMS:317)。撤单发生在 Ack 之后,首个响应已经用掉,撤单的 `sent_tsc` 不被记录,也不产生样本。
  - `LatencySample` 也没有区分新单与撤单的字段(event:462–483),撤单若混进来会污染 `order_rtt`。
  - 结果:⑩ 的硬线分段只剩 pair/target 模式在测试网行情时段的少量第二腿样本。
- **引用**:LP:13、110、139、185、224、243;T:358、364–365;LB:61;OMS:226、317、745;event:462–483、503–506。
- **修法**:见 §5-4。

### P2

1. **strat-lib 构件的快照缺"最近一次观测",确定性夹具会失败。**
   - `PercentileStats` 当前采样区间里未提交的那次观测,以及补齐规则要用的上一次观测时刻与值,都不在快照里(SL:248、375、381、428)。
   - `LeadLag` 每腿的上一次 mid 也不在快照里(SL:272–274;XT:52 却写"无路径状态")。
   - 所以 SL:285"构件本身没有路径依赖的状态"不成立。
   - 修法:把它们写进原始样本节,同步 `LAYOUT_ELEMS` 与 `snapshot_bytes`。注意:改 strat-lib 会让 pc 的 ⑦ 重新计时,宜在 ⑦ 开始前改。
2. **`path_settle_ms` 公式在参数角点偏小。** 目标平滑窗要等分位带与基差平滑都一致之后才开始一致,正确上界是 `max(band_update_ms, basis_smooth_ms) + target_smooth_ms + …`。例:`band_update_ms` = 60 000、两个平滑窗都是 600 000 时,公式给 671 s,实际需要 1 211 s,recompute 会误报(pc:715、721;范围见 pc:439、448、462)。
3. **advice outbox 会合并,而 recompute 的配对规则没写。** S:429 的 outbox 对同一 (strategy, account, group, local_kind) 只留最新一条,被覆盖的 Advice 不进 journal(重启追赶期间很常见);R:60 与 T:82 只说"逐字节比较"。应规定按 (strategy, group, local_kind, basis_seq) 配对;重算多出、journal 里没有的,计为 `coalesced`,不算分歧。
4. **换版当天的 verify/recompute(待核实)。** 每日任务用已安装的发布制品(T:271)。Model 代码有变的发布当天,换版前的 Advice 是旧二进制产生的,用新二进制必然不同。R:220 承认跨版本不成立,但每日任务对"当日含版本切换"怎么处理没写(按段换二进制,或标 `skipped_reason = release_change`)。
5. **检查点文件格式缺路径节。** core:381–389 自称"检查点文件格式的唯一归属",但键与写法里没有路径节的版本与长度;SDK:244 又把布局交给 core。应补 `path_version`/`path_len`(合并备忘里交给 J8 的待办未落地)。
6. **`ResetPreview.no_open_ms` 的口径不对。** WARMUP = true 时取 min(cold_start, path_settle)(SDK:275)。对 pc 来说,路径收敛并不挡开仓——分位带在就绪后第一个 tick 就算出来;真正挡开仓的是预热取数与注入(PCP:169 写 < 10 min,外加 `warmup_rate_per_s`)。建议预览分两项列出,或 SDK 加 `Model::warmup_ready_ms`。
7. **模型 tick 超过 1 ms。** pc:694 的 `band_tick` p99 是 2 ms,而 SDK:1298、1305 要求 ≤ 1 ms,超出的"按 gix 分片";SDK 却没有分片/续算接口(S:430 的"一个模型分片"没有对应 API)。要么明确允许边界 tick 到 2 ms,要么 pc 把分位带重算按 gix 分摊到边界后的几个 tick(仍然确定)。
8. **无限记忆的路径状态没有收敛上界。** EWMA 一类状态没有有限的 `path_settle_ms`(SDK:132–133、252),第三类策略(只用 Model 的统计策略)会碰到。建议规定 `u64::MAX` = 当日剩余部分不比较。
9. **Model 收哪些事件,两处写法不一。** SDK:225、810 写 Model 不收 External/Risk/Mode;S:426 写"账户级事件"进 Model。需统一。
10. **GroupId 有两个分配者,彼此不读。**
    - pipeline 维护 `next_ctr`(P:141–146);hft-cfg 是人在 TOML 里手写 n,只用 `--against` 比上一版本(tools:342、351)。
    - 后果:人工 blob 新增的 id 以后可能被 pipeline 分给别的指纹,TY:154 的"一个 id 永久对应一个指纹"只剩兜底。
    - 修法:pipeline 每轮从生效 blob 读出最大 n、更新 `next_ctr` 并登记外来 id 的指纹;hft-cfg 从版本库取下一个 n。
11. **⑦ 计时没有执行者。** 规则在 T:343–347,但只有 hft-cfg 的 `diff` 能判小改(tools:406);pipeline 与 ops_bot 改参数时,没有组件跑 `minor_change_check`、记录计时起点。建议 journal-archiver 的日报按 ConfigBlob 自动给出 ⑦ 状态。顺带两处残留措辞:launch:54"小改白名单"、P:266"首个 core 策略"。
12. **"目标的设与留"漏了 urgency。** pc:207 的三种重发情况(无目标、原因/场景码不同、数量出带)不含 urgency 变化。所以 L2 升 Urgent(pc:258)与下架临近升 Urgent(pc:334、341)按字面都不会重发,升级不生效。应加第四种情况。
13. **Broken 的 group 上 `exit`/`exit_all` 不记待完成退出。**
    - pc:252 对 Broken 的 group 只设封锁;`pend_exit` 只在进入 Exit 时才记(pc:257)。
    - 后果:Broken 解除后(自动平仓只平多出的那一腿),对冲部分仍在,而 `pend_exit` 为空,退出不会继续;封锁到期后还可能重开。
    - 修法:命令对 Broken 的 group 也记 `pend_exit`。
14. **Fix 阶段遇到 MinOrder 永不结束。**
    - pc:322 只把"0/0 Exit 遇 Stuck(MinOrder)"视为完成。
    - `Fix{Liquidation}`(`exit_group` 时是 0/0 Hard)与 `Fix{Other}` 的对齐目标遇到 MinOrder 只写 Note,而 Fix 只在 `Exec{Done}` 时回 Idle(pc:320)。
    - SWEEP 里的"Fix 截止"(pc:341)没有定义动作。该 group 会永久停在 Fix。
    - 修法:把完成规则推广到任何 0/0 目标与对齐目标,并写出 Fix 截止时的动作。
15. **门控期间退出目标每 3 s 重发并写 P1。** pc:322 对 Gated(非 LINK_STALE)也重发并写 `Note{ExitRetry}`(P1)。HARD 或长时间限速退避下,64 个 group 的 `exit_all` 约每秒 20 条 P1。执行层在门控原因消失后会自动回 Working(E:327、337),重发没有用。只对 SliceFails 重发即可。
16. **缺参数交叉校验。** `advice_refresh_ms`(≤ 300 s,pc:465)可以大于 `advice_max_age_ms`(pc:476),不变的 group 会在两次心跳之间过期、无法调仓;`check()`(pc:663)不查。应加 `advice_refresh_ms + alloc_period_ms < advice_max_age_ms`。
17. **心跳突发。** 每个 10 s 的 UTC 边界一次发 64 条 Advice(pc:146),每条触发该 group 的完整评估(pc:205),sequencer 上约 100 µs 的周期性突发,与"延迟优先"相冲。建议按 gix 错开心跳,仍然确定。
18. **L3 → L2 回落后可能不再进 Stress。** 同一 Input 里 `Risk{L2}` 与 `Exec{Done{engine}}` 的入队顺序,决定 pc 在 Overridden 阶段会不会错过 L2(pc:293、325、331;S:362)。修法:回 Idle 时按已保存的 `stress[venue]` 复查。
19. **Note 容量不够。** L2 首轮 64 个 group 在同一事件发完(pc:746),每个目标一条 `StressReduce`,而 Note 容量是 16(SDK:858),会丢 48 条,报表 `stress_steps` 少计。SWEEP 一次已经用满 16 条(pc:341),同一事件里的 ExitRetry/TrimStep 会被丢。
20. **`FundingView.upd_tsc` 与 `prev_interval_s` 没有数据来源。** SDK:590–596 定义了这两项;S:136 说 funding 取自 `MarketLast`,而 `MarketLastRow`(S:540–548)没有这两个字段;关键帧之后的取值规则也没写(合并裁决 R12 只管 `rx_tsc`)。pc 闸门 3 的资金费新鲜度门依赖它(pc:214)。
21. **pc:502 与 E:378 不一致。** pc:502 写切片越价"按 `rr_max_cross` 截取";E:378 规定增仓切片取 `ioc_max_cross`,减仓取 `rr_max_cross`。
22. **LP target 模式 `band = 0`(LP:127)。** 现货腿以基础币扣手续费时,完成判定 `|T − pos| ≤ 0` 永远达不到(E:335),开仓目标从不 Done,每轮写一条 TargetStuck。band 应给 lot 级的值。
23. **`model_tick(every_ms)` 的分辨率没写。** 实际分辨率是 AdvisorTick 的 1 s(S:310),SDK:210–213 没写,也不拒非整数倍(pc 是在自己的 `check()` 里拒的)。
24. **永续×永续的门槛压力用例方向。** `one-sided-30` 与 `l3-path` 固定 +30%、作用于全部 inst(sim:231、287),只压空头那一所;多头那一所的 −30% 只能用 Custom 非门槛用例(sim:296)。T:227 的"不利方向"在账户永续净仓 ≈ 0 时没有定义。见 §5-5。
25. **大币池受 64 group 上限约束。** `max_groups_per_instance` 固定 64(core:369),Ctx 目标容量也是 64。横截面统计类策略要么改 hft-core 容量表,要么拆账户。core:67 承认预算表可能要改,与 CB:3 和 strategies/AGENTS"app 零改动"的措辞不一致。应在 cookbook 写明"先单独提 hft-core 容量 PR"。
26. **小一致性问题。**

### 写第二、第三个策略的检验

- **跨所永续×永续资金费**:SDK 够用——两条永续腿、`Views::leverage`、按 venue 的 MarginStress、执行层两永续的 PerpFirst 规则(E:403)、pipeline 的 venue 角色都是通用的。缺口:门槛压力用例的方向(P2-24),要作为门槛就得改 hft-sim 与 testing;Model 要用下架信息时缺视图(P1-3)。
- **跨所吃单 cross-taker**:引擎与 app 零改动(registry 已有 feature 行)。但 `LeadLag` 快照的缺口(P2-1)要改 hft-strat-lib,而改 strat-lib 又会让 pc 的 ⑦ 重新计时——两个策略经构件库耦合在一起。
- **只用 Model 的统计策略**:
  - 缺公告视图(P1-3);
  - EWMA 类状态没有 `path_settle_ms` 语义(P2-8);

  - tick 分辨率只有 1 s(P2-23);
  - Model 看不到 Risk/External/Mode 事件,只能读视图;
  - 超过 64 个 group 要改 hft-core 容量表(P2-25)。
- **SDK 建议只追加的部分**:`inst_status` 视图;模型 tick 续算接口,或明确时间片例外;`path_settle_ms = u64::MAX` 的语义;`model_tick` 的分辨率与校验;可选的 `OwnEvMask::RISK | EXTERNAL`。

## §4 应保留的设计

- registry 是唯一的策略清单;依赖方向机检;`decoupling-gate` 与带 Model 和 pipeline 插件的 `scaffold-gate`。
- 检查点的键不含参数、refdata、发版;原始样本节 + 路径状态节,`PATH_VERSION` 不符只丢路径节,配路径金样;`recompute_from_seq` 由 Note 的 v[1]、v[2] 确定;分位带与心跳按 UTC 边界对齐。
- 重发必须改字段(tag 低位序号);"有仓位"的统一定义加 `MINORDER_RESIDUAL`;`pend_exit` 的"回 Idle 前先查";L2 期间待完成退出保持 0/0 并升 Urgent。
- GroupId = `(StrategyId << 24) | 计数器`,由构造保证;`spec_seq` 丢弃旧规格的 Advice;LotMismatch 只检查新增与指纹变化的 group。
- `minor_change` 作为 schema 属性,由工具通用判定;累计差相对于基准比较,分步改绕不过去;结构字段只能是 None。
- `ResetPreview` 只依赖 SDK 声明;Live 实例上的结构参数热更属于升级类;pipeline 插件不得拥有结构字段。
- `InstRiskView` 按 inst 的价格带类别取值;`dust_notional` 与执行层同源;`venue_ready`。
- 成本门只对场景 1–3 生效且没有绕过开关;与杠杆无关的永续硬上限计入承诺额;负资金费的开关与期数拆成两个字段。

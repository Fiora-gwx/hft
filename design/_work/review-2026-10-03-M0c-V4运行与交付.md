# M0-c 后独立评审 V4:运行、交付与资源(2026-10-03)

> 无上下文子代理只读评审原文(主控未改动内容,只换了标题)。路径相对 `E:\trading\hft\`。

## §1 结论

1. **交付路径在逻辑上是通的。** dev2 不放正式账户，靠三道关卡保证（启动时 `ProdAccountOnDev2` 拒绝、dev2 的 IAM 读不到 `hft/live` 下的秘密、发布预检）。M7 在升级主机上 prod 与 sim 同机做延迟验收，M8 直接正式实盘。
2. **执行不了的地方在免费 CI。** 我用 GitHub API 只读统计了 Trading 仓库的实际用量，据此推算：hft 每月大约只够 8–20 个合并 PR、2–4 次开发构建；门槛 ③④ 需要 4–8 个月；额度用尽会把 Trading 的发布一起停掉（P0）。
3. **不设小额实盘后，门槛只补偿了"软件正确性"。** 交易所的真实撮合、费用、保证金字段和正式端点行为，以及校准过的模拟结果，都要到满额正式实盘的第一天才暴露。⑥⑦⑩⑪ 都补不上这块。
4. **dev2 的内存预算只在纸面上闭合**（余量 135 MiB），实际有两个漏洞：tmpfs 热段停机后不释放；swap 增长只告警不停机。所以护栏保证不了"旧系统（cdex）优先"。
5. **c16 规格基本合理，但有三个缺口：**
   - sim 与 prod 共用 ENI-B 的收包队列，busy-poll 会让 prod 的热核去处理 sim 的包；
   - 没有任何机外监控，也没有"整机失联"的处置手册；
   - 实例角色让本机任何进程都能取到正式交易 key。
6. **门槛 ⑥ 和 ⑩ 在当前配置下大概率测不出来**：拿主网行情给测试网下单会产生价格错配；组合携带下单太少，样本 n < 1000，按规则不报 p99。

## §2 发现

### P0

**P0-1 免费 CI 额度下，交付吞吐不可行，还会拖停 Trading 的发布**

- **场景**：CI 是唯一的构建与测试环境（development.md:8）。在 dev2 上每联调一次，都要走一遍：合入 main → main CI → 打 `-dev.N` 标签 → arm 发布构建 → 服务器拉取（development.md:65,168；deploy/README.md:85）。
- **核实（只读 API 实测 Fiora-gwx/Trading，私有仓库、个人账户）**：
  - 8 月作业分钟 530，9 月 411；
  - ARM64 Release 每次 15–17 分钟，每月 150–177 分钟；
  - CI 每次计费中位 9 分钟（14 个 crate、1.8 万行、无 LTO；rust 作业中位 6.9 分钟）。
- **预算推算**：按 development.md:148-160 的分配，hft 每月实际可用的分钟数如下。

  | 项 | 分钟/月 |
  |---|---|
  | 账户总额度 | 2,000 |
  | 减 hft 每夜任务 | −750 |
  | 减 Trading 实际用量（8–9 月实测） | −410～−530 |
  | **hft 剩余（PR + 发布 + 开发构建合用）** | **约 720–840** |

- **为什么单次运行比规格估得贵**：
  - `ci` 剖面继承 `release` 的 `lto="fat"`、`codegen-units=1`（development.md:45-46），每个测试二进制都要做 fat LTO；
  - 另外还有 aarch64 `cargo check`、decoupling-gate 的二次编译、loom、按路径触发的 fuzz 冒烟（nightly 工具链 + ASan，要单独编一遍）、maturin wheel；
  - 并行作业各自向上取整到整分钟。
  - 结果：PR 每次现实约 15–30 计费分钟（规格目标 ≤10，testing.md:251）；发布/开发构建约 35–60 分钟（规格目标 ≤30，testing.md:254）。
- **后果**：
  - 每月约 2–4 次开发构建（M3/M6 联调唯一的迭代手段），15–40 次 PR 运行；
  - 每夜 20 分钟里扣掉构建只剩 5–12 分钟给 DST/fuzz：fuzz 6 个解码器 × 2 h 需 60–144 夜；DST 20 万种子按 0.1–0.7 s/种子需 28–465 夜（testing.md:263 自己估 28–200 夜）。任一失败清零，现实看 4–8 个月；
  - 额度一用尽，两个仓库的 Actions 全停（development.md:157）。
- **附带的配额坑**（github/docs 原文核实）：
  - Free 计划的 artifact 存储只有 500 MB/月，按 GB·时累计，没有付款方式时超额即阻断；
  - 而发布归档作为 artifact 保留 7 天（development.md:132），每夜账本与 fuzz 语料 artifact 保留 90 天（development.md:139）；hft 归档含 polars/duckdb/pyarrow 的 wheelhouse，估 100–200 MB/次（Trading 只有 23 MB）；
  - cache 每仓库 10 GB，要装 4 套 target 缓存加每夜新增的语料，会被逐出 → 冷构建 → 每夜超时。
- **修复（全部免费）**：
  1. 在一个免费 GitHub Organization 下建 hft 仓库：独立的 2,000 分钟和 artifact/cache 配额，同时解决 P1-9 的"老板只读"问题。
  2. `ci` 剖面改为 `opt-level=3, lto=false, codegen-units=16, incremental=false`（保留 debug-assertions/overflow-checks）。fat LTO 只用于正式版的 hft-core 与 kill-switch；开发构建用 thin LTO、只构建 dev2 需要的二进制、跳过 aarch64 一致性集。
  3. 去掉 `pull_request_review`/`labeled` 触发的整套重跑（development.md:101,117），只重跑解耦作业；python 与 operations 改为按路径的步骤，并入一个作业，减少取整损耗。
  4. 允许在"CI 全绿的 PR 头"上用 `workflow_dispatch` 出开发构建，不必先合入 main。
  5. 发布 artifact 设 `retention-days: 1`（Release 资产本身不占 artifact 配额）；账本写成 Release 资产，语料只放 cache 或 S3。
  6. M1 第一周用实测分钟数重算日历。
- **另一项待测量可以销账**：待测量 H2 的"`ubuntu-24.04-arm` 在私有仓库是否可用"已有答案——Trading 8–9 月 20 次成功运行。计费倍率仍需看计费页；超额单价 Linux x64 $0.006/min、arm64 $0.005/min。

**P1-2 dev2 护栏保证不了 cdex 优先**

- **算术核实**：
  - 预算闭合式是 2,575 − 600 = 1,975 ≥ 1,840，余量只有 135 MiB（hft-core/README.md:338）；
  - hft 用满时 MemAvailable ≈ 735 MiB，低于 watchtower `HostPressure` 的 800 MiB（watchtower/README.md:96）→ 联调窗口内会持续报 P1，与 testing §7"7 天无未解释 P1"冲突。
- **(a) tmpfs 热段停机后不释放**：
  - 热段跨进程保留是设计前提（hft-core/README.md:360；deploy/README.md:235）。在 cgroup v2 下，这些页在单元停止后转记到父 slice；又因为 `MemorySwapMax=0`，换不出去。
  - 联调窗口结束、批处理恢复后：`hft.slice` = 1,200 + 192（prod 残留热段）+ 512 = 1,904 MiB，超过上限 1,776 MiB → slice 内 OOM。
  - 护栏二级停机之后，sim 288 MiB + prod 192 MiB 的热段仍占着内存，停机并没有达到释放目的。
- **(b) swap 只告警**：旧系统已经在用约 0.8 GB swap（现状测量与升级分析-2026-10-01.md:35）；hft 的 `mlockall` 会把 cdex 的页挤进 swap，而护栏对 swap 增长只告警不停机（hft-core/README.md:384）。cdex 引擎可能在 PSI 触发停机之前就已经出现缺页延迟尖峰。
- **修复**：
  - 干净 Drain（`Stopped`、persist 已刷完）之后卸载该实例的 tmpfs 挂载；崩溃路径则保留；
  - 把 swap-in 速率（`/proc/vmstat pswpin`）和 system.slice 的 memory.pressure 纳入停机信号；
  - `HostPressure` 阈值与预算对齐；
  - dev2 的 sim 订阅降到使满额时 MemAvailable ≥ 1 GiB。

**P1-3 `Conflicts=` 是双向的：每天 01:30 UTC 会停掉测试网实例**

- **依据**：
  - dev2 上 `hft-core@prod` 的覆盖文件写了 `Conflicts=hft-replay-verify …`（deploy/README.md:211）；
  - replay-verify 定时器 UTC 01:30 触发（deploy/README.md:252）；
  - launch.md:43 还特意写"定时器照常触发"。
- **问题**：systemd 的 Conflicts= 是双向生效的（"starting the former will stop the latter and vice versa"）。定时器或任何人启动批处理单元，都会让测试网实例 SIGTERM→Drain。门槛 ⑥ 要求"连续 3 天"（testing.md:294），每天都会被打断。
- **修复**：窗口开始时 `systemctl mask --runtime` 批处理的单元和定时器（或在批处理单元里用 `ExecCondition=` 检查 prod 未运行），不要依赖 Conflicts=。

**P1-4 ⑥ 和 ⑩ 在现有配置下很可能测不出来**

- **依据**：
  - `feed_env` 默认是 `prod`（hft-core/README.md:518）；
  - M7 明确写"主网行情 + 测试网下单"（hft-core/README.md:92；host-upgrade.md:23）；
  - launch A4 只设了 `order_env`（launch.md:39）；
  - 样本数 n < 1,000 时不报 p99（latency-budget.md:177）。
- **问题**：
  - 下单价格、lot/tick 来自主网，而测试网盘口稀薄、价格带不同 → IOC 不成交、被价格带拒单、第二腿成交价与主网盘口无关 → 产生 Broken 等"伪异常"，⑥ 很难做到"连续 3 天无未解释异常"；
  - 组合携带下单稀少，7 天里 `tick_to_trade`/`leg_gap` 的样本远低于 1,000，⑩ 无法判定。
- **修复**：
  - ⑥ 改用 `feed_env=testnet` 与测试网 refdata（测试网的符号映射是否不同，属 A21 待核实）；
  - ⑩ 注册一个只能绑定 `is_prod=false` 账户的"延迟探针"策略：按 BBO 事件以固定速率挂不会成交的 post-only 单再撤单，每天产生 ≥1 万个样本。

**P1-5 sim 与 prod 共用 ENI-B 收包队列**

- **依据**：ENI-B 全部队列的中断都钉在 hk 核（deploy/README.md:107,116）；启用了 busy_poll/busy_read（deploy/README.md:146）；sim 出口就是 ENI-B 的第二个私有 IP（deploy/README.md:165）；已知限制里也只写了"队列共享"（deploy/README.md:408；hft-core/README.md:679）。
- **机理**：busy-poll 是按 NAPI 队列轮询的，会处理该队列上所有 socket 的包。sim 订阅全宇宙（容量表 4096 个 inst），它的行情包会在 prod 的 feed/gw 热线程里完成协议栈处理；不走 busy-poll 的部分则全部落到核 0（hk + persist + 全部 IRQ）。这是"sim 不占热核"之外的一条直接干扰通道。
- **修复**：sim 用独立的 ENI-C，其队列 IRQ 钉到 sim 核 13–15；hostprobe 核对 sim 连接的 `SO_INCOMING_NAPI_ID` 不属于 ENI-B。需在 M7 用 sim 开/关对比 softnet 计数实证。

**P1-6 本机任何进程都能读取正式交易 key**

- **依据**：
  - 升级主机的实例角色授权读 `hft/live/*`（deploy/README.md:272）；
  - ops_bot 读 S3 Parquet（ops_bot/README.md:108），pipeline、treasury 也读 S3（python/AGENTS.md"谁持有什么 key"），它们都要用实例角色凭证。
- **问题**：IMDS 对本机所有 uid 都可达，所以"ops_bot 不持 key"只在进程层面成立。面向 Telegram 的 Python 进程、或其 PyPI 依赖一旦被利用，就能取走全部正式交易 key 和 kill-switch key（这把 key 实际上能下单，kill-switch/README.md:247）。
- **修复**：
  - 用 iptables owner 规则只放行 root 和归档进程的 uid 访问 169.254.169.254；
  - Python 冷进程改用 root 辅助进程发放的、只覆盖相应 S3 前缀的 STS 短期凭证；
  - preflight 增加"非 root uid 访问 IMDS 被拒"的检查。

**P1-7 门槛 ⑦ 没有计时规则，也没绑定参数**

- **依据**：launch.md:49 和 incident-response.md:214 都写"是否重新计时按 testing §8"，但 testing.md:295 只写了"连续 ≥ 14 天"，没有任何重置或暂停规则。研究期间参数会持续变化。
- **后果**：护栏停机、采集窗口（hft-core/README.md:342 要求先停两个实例）、发版、改参数算不算重新计时，全凭解释；正式实盘用的参数可能只在 sim 上跑过很短时间。
- **修复**：
  - 证据绑定（发布版本，StrategyParams 的 SHA，RiskParams 的 SHA）；
  - 停机累计 ≤ 24 h 视为暂停，超过则重新计时；
  - 策略/执行层/风控代码变化，或参数超出"小改白名单"，则重新计时；
  - 压力用例必须用最终参数重跑。

**P1-8 没有机外监控，也没有整机失联手册**

- **依据**：
  - watchtower 的 `/metrics` 只绑 127.0.0.1（watchtower/README.md:62），而它说的兜底"研究主机上的 Prometheus up==0"（watchtower/README.md:248）既抓不到回环地址，研究主机也不在预算里（11-实施路线图.md:105-111）；
  - 电话告警通道未选型（watchtower/README.md:130,247）；
  - kill-switch 与 hft-core 同机（kill-switch/README.md:246）。
- **场景**：c16 宕机或 AZ 故障时，watchtower、ops_bot、kill-switch 同时消失：没有任何告警，老板的 `/stop` 无响应，普涨中永续空头无人减仓。
- **修复**：
  - dev2（不同 AZ）上跑一个只用标准库的外部看门狗，心跳缺失 60 s 就用独立 token 发 Telegram + Bark；
  - incident-response 新增"交易主机失联"一节：谁有网页权限、各所手工撤单/减仓步骤、从 AMI + EBS/S3 重建主机并用 `--recover-from-snapshot` 恢复的顺序；
  - 电话告警通道列入 ⑪。

**P1-9 "老板只读"在个人账户的私有仓库上无法实现**

- **依据**：R8-6（round8-decisions.md:56）；development.md:7、117。
- **核实**（github/docs 原文）：
  - "In a private repository, repository owners can only grant write access to collaborators. Collaborators can't have read-only access to repositories owned by a personal account."
  - "Protected branches are available in public repositories with GitHub Free …"，私有仓库需要 Pro/Team。
- **后果**：老板只能是有写权限的协作者；CI 红也能合并；"解耦豁免需 Admin 批准"阻止不了合并。
- **修复**：仓库放进免费 Organization，老板给 Read 角色；生产安全以"发布工作流 preflight 证实该 SHA 全绿"为准（这条已具备），并把解耦检查也放进 preflight。

### P2

1. **同机干扰判据不一致，且统计上判不出来。**
   - testing.md:298 写 <10%；hft-core/README.md:622,639、deploy/README.md:373、host-upgrade.md:36 写 ≤5%；

2. **压力用例偏弱，描述也自相矛盾。**
   - 按默认 perp_margin_frac 0.5（杠杆 2，launch.md:67）、MMR 0.5% 计算：强平价在 +49.3%，+30% 结束时 liq_dist ≈ 14.8%，只到 L2，永远到不了 L3；
   - 但 launch.md:50 与 testing.md:220 都要求"依次到 L1/L2/L3"；

3. **M7→M8 切换步骤缺项**（launch.md:73）。

6. **IAM 与预算口径不一。**
   - deploy/README.md:142 写"由实例角色挂 ENI-B"，同文件 :170 写"实例角色没有 EC2 写权限"；
   - dev2 的实例角色与 cdex 共用（现状测量:38，只有 S3 写），扩权限属于改生产主机 IAM 的 `[需授权]` 步骤，launch A 没列；
   - 参考机（每次发布约 7 次 × 1 h）、research 主机、S3 增长、多出的公网 IPv4 都不在 11 §8 的预算里。
7. **c16 冷盘不够。** EBS 估 500 GB（现状测量:182），但按保留期 seq 7 天 + raw 3 天（journal-archiver/README.md:139）、raw ≈160 GB/天（现状测量:131），约需 0.69 TB。另外 hugetlb 不计入 memory.max，所以 prod 的 `MemoryMax` 8,320 MiB 实际起不到约束作用。
8. **AMI 禁用了 SSM agent**（deploy/README.md:154；host-tuning.md:48）。而到 EC2 的 SSH 时断时续，incident-response 的 D/G/R6 都要上机。建议保留 SSM 作破窗通道（限制在非隔离核）。
9. **`/stop` 走兜底时不持久。** 经 kill-switch 撤单的停止不进 journal（ops_bot/README.md:196），hft-core 重启后交易员 `/resume recovery` 就会恢复开仓（incident-response.md:235）。建议 ops_bot 记一条"待补 Kill"，心跳恢复后自动补发。另外，ctl 不可达但 sequencer 还活着时，kill-switch 挡不住新单（kill-switch/README.md:244），可以给它一个经 polkit、只允许 `systemctl stop hft-core@prod` 的兜底权限。
10. **账户名跨实例唯一性未校验。** ops_bot 按账户名路由（ops_bot/README.md:65,74），`/kill`、`/stop` 不带实例名，而两个实例各自编号（hft-core/README.md:94）。建议启动时校验两实例账户名不相交。
11. **CI 拉 S3 fixtures 的凭证没定义。** fixtures/README.md:114-131 用 S3 指针，但 development.md:97 只给了 `contents: read`。建议仅对需要的作业开 GitHub OIDC（`id-token: write`），扮演只读 fixture 桶的角色。
12. **模拟系统的适用范围没写清。** sim 线程全部是 `Park{1000}`（hft-core/README.md:224-229），用自己的行情连接，延迟模型固定 2 ms。它评估不了 10–20 ms 窗口的跨所吃单类策略；对组合携带基本够用，但研究吞吐受实时限制（每组参数要跑数周，dev2 每个策略只有 2 个模拟实例）。建议在 hft-sim 概要里写明适用范围。
13. **dev2 上采集窗口与门槛 ⑦ 互斥**（hft-core/README.md:342）。可交易性分析需要补录现货数据，排期上要么先采集后长跑，要么接受 ⑦ 重新计时。
14. **发版后改了交易所适配代码，会不经测试网直接上实盘。** release-and-deploy.md:32-38 只要求回放 + 模拟；testing.md:257 的"发布前 dev2 演练"没写进 runbook。建议：改动 `venue-*`、`hft-venue`、`hft-net`、`hft-oms` 时，先在 dev2 测试网窗口装同一个 `vX.Y.Z` 冒烟。

## §3 应保留

- prod/sim 实例角色的启动校验：Sim 账户、key、gw、`SimOnHotCore`、`EgressIpOverlap`、`DevBuildWithProdAccount` 都会退出 2。
- dev2 不放正式账户的三道关卡；护栏只按资源信号停机、cdex 重启只告警；守护脚本只用标准库，polkit 白名单只允许停 hft 单元。
- 服务器自己拉取、不可变归档、冷激活、按组激活（sim 先于 prod 升版本）、恰好保留一个回滚版本、`--recover-from-snapshot` 与两层毒丸防护。
- kill-switch 极简且独立：只依赖 hft-rt、每把 key 核 UID、`SO_PEERCRED` 只认 ops_bot；watchtower 的告警不经 ops_bot。
- `/stop` 的语义：非 HARD、确认绑定 `cmd_hash` + TTL、不比对状态版本、失败或兜底时 ops_bot 自己发 P0。
- CI 累计账本规则：只有失败清零、漏跑不清零、可按 artifact 重建。
- reconciler 严格放行闸门、资金费差异只告警并由账本自动校正；archiver 的上传与删除纪律、测试网数据单独前缀。

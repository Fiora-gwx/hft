# M0-b 修订后的第二次独立评审(2026-10-03)

> 无上下文子代理的只读评审,只给了用户要求(`round8-decisions.md`)。主控已核对 P0-1、P0-2、P0-3 的出处属实,并复算了 P0-3 的推导(e = 0.30、m = 0.5% 时 L1 在 +28.93%、L3 在 +29.19%、强平在 +29.35%)。

## 1. 结论

基础层(hft-types、hft-event、hft-refdata、hft-journal、hft-rt、SDK 的 params/registry)可以开工。交易路径(oms/exec/risk/venue)与模拟/小额实盘要等 3 个 P0 修完;P1 中会造成返工的几项应在对应 crate 动手前定稿。

## 2. 发现

### P0

- **P0-1 安静行情下对冲腿与自动平仓被"报价过期"卡死**:新鲜度按"该 inst 最后一次变化"判定(`hft-oms` 对冲定价第 1 步、`hft-risk` #5、`hft-exec` `quote_max_age_ms` 1000);第二腿盘口 0.5 s 不变 → `StaleQuote` → 3 s 后 Broken → 自动平仓每片也要求报价 ≤ 1 s → Failed;`max_mid_age_ms` 无默认值;与 hft-strat-lib "安静的 inst 几秒无推送不应判为过期"矛盾。修法:新鲜度 = BBO 连接健康 + 最近任一消息/心跳 + 未在重同步;`BboView` 加连接确认时刻;风险递减单在连接健康时用最近报价 + `rr_max_cross` 定价;DST 加"第二腿盘口 10 s 不变"。
- **P0-2 模拟实例上的参数试验会不经确认下发到实盘**:pipeline 校准对共享 policy 与覆盖项(`python/pipeline` "两个实例共享同一 policy 文件与覆盖项");pipeline 主体的 `SetParams` 恒为中性,含 `open_allowed` 0→1 与新增 group。修法:覆盖项按实例分键;人工经 pipeline 转发、作用于 Live 账户的放宽带 `origin_issuer`,按人工规则要求确认。
- **P0-3 MarginStress 用"维持/保证金余额"比率分档,默认值下几乎不给减仓时间**:r = m(1+X)/(e−X),L1(0.6)到强平(1.0)之间只有约 0.67·m 的价格空间(e = 0.30、m = 0.5% 时为 0.42%)。修法:改用到强平价的距离 `(liq_px − mark)/mark`(或权益/维持倍数)分档,默认留数个百分点;比率作交叉校验;hft-sim 加"单边 +30%"压力用例并作为上线门槛 ⑦ 的必过项。

### P1

1. `Kill{Account, flatten}` 可被策略的新目标覆盖(engine_flatten 不置 `force_active`)→ 设账户级清仓锁,只接受更接近 0 的目标。
2. 两腿 lot/最小量不对齐,每片留下不可对冲的残余(如现货 0.004 BTC vs OKX 永续一张 0.01 BTC);小额实盘"按最小名义设上限"放大它 → 切片按两腿 lot 的较粗者取整;小额上限取两腿 `max(min_notional, min_qty × px) × (1 + fee + slip)`。
3. 策略、ledger、risk 状态里存的 TSC(`ConfirmWindow.since`、`Throttle`、`reentry_block_until`、`round_start_tsc`、`MarginRow.deadline_tsc`)不随重启/换机平移 → `Now` 增加跨重启连续、停机不计的引擎时间,状态只存它;或 `restore` 传 `(stop_tsc, now)`,ledger/risk 并入同一 `recovery_end`。
4. IDENTITY 只核一把 key;kill-switch 与 reconciler 的 key 从不核 UID → 每把 key(Ed25519、HMAC、kill-switch、只读)都核 UID = `venue_uid`。
5. KillWord 位宽三处不一致(hft-types u32;hft-rt 与 hot-path-rules `AtomicU8`;hft-venue `kill_mask: u8` 且漏判账户 HARD 位)→ 统一 AtomicU32,gw 判定照 hft-risk;自检走真实 store/load。
6. dev2 上小额实盘的可用性:replay-verify 与 hft-core 同在 `hft.slice`(OOM 可能先杀 hft-core,不走 Drain);崩溃后 /dev/shm 空间检查可能让它起不来;slice `CPUQuota 100%` 含 advisor 镜像;护栏二级停 hft-core 后不自动拉起,Broken 自动平仓随之停止 → hft-core 与批处理分子 slice;replay-verify 独立上限;空间检查扣除已存在的段;dev2 实盘名义上限写进 launch。
7. 资金费差额经"余额"条目仍会进 Recon cap 与启动闸门;`NoHistory` 永久卡住 → 分级前用同组报告的 Funding 条目修正结算资产余额差;`NoHistory` 给入账路径。
8. 老板紧急停止的可达性:确认比对 `ctl_state_version`,事故中 cap 频繁变化会反复 `ConfirmInvalid`;失败不通知 → Viewer Kill 的确认绑定预览 `cmd_hash` + TTL,不比对状态版本;`/stop` 失败/超时 P0 推送。
9. 上线门槛时序互锁(阶段 B 模拟就要求 ④ DST 累计 20 万种子;⑥ 无测试网的所由 ⑨ 小额实单覆盖,⑨ 在阶段 C),且受免费 CI 额度限制(GitHub Free 私有仓库 2,000 分钟/月,与 Trading 仓库共享;额度用尽连发布构建也会停) → ③④ 移到阶段 C 之前;加"最小名义实单核验";按账户做每月 CI 预算并为发布预留;漏跑一夜不清零。
10. portfolio-carry 没有单 group 强制退出的通道(`open_allowed = false` 仍走成本门;正资金费且无更优币时永不平) → per-group `force_exit` 参数或 reduce_only `StrategyCmd`,映射为 `reason = Exit`。
11. c8 线程计划把 OKX、Bitget 的 feed 与 gw 合并在同一线程,违反 T8;deploy 的隔离核 "2-7" 与 hft-core "2-6" 不符。
12. venue 层:OKX 数量换算两套口径(`sz = qty / ctVal` 与 refdata `qty_unit_shift` 并存,会差 ctVal 倍);去重键只用成交 id(Binance/OKX 成交 id 按交易对编号,跨品种可能撞号)→ 键改为 (inst, trade_id),强平/ADL 的 0/负 id 不入环。

### P2(14 项)

Advice 跨启动过期由谁判定不清(sequencer 说"标为过期"但 `EventRef::Advice` 无该字段);固定容量溢出未定义(`ModeOutcome.cells` 64、`cancel_open` 32);容量数字三处打架(hft-core / hft-sequencer / hft-exec);`TargetOrigin::Engine(AutoFix)` 无线上编码;`RISK_REDUCING` 位值不一致(hft-event vs hft-oms);incident-response 说 `/hedgefix` 可"补齐缺的一腿"(实际只平多出的一腿);两套毒丸机制;`AdvisorLag` 两种定义;成本门公式量纲错;replayer sim 读录下的 Advice 与重演状态不一致;reconciler 依赖未定义(hft-oms、"hft-risk reconcile 模块");解耦边界细节(pipeline 插件放在框架包、decoupling-gate 对 `engine-change` 标签豁免、hft-testkit 经 registry 间接依赖策略);可疑交易所事实(Binance RecvWindow NotFound 定终态、心跳口径只适用 USDⓈ-M、countdown 超时 ≥ 2×刷新、Bitget 强平标记只列双向持仓、现货账户未禁借币);默认参数冲突(`perp_leverage` 1 vs `perp_margin_frac` 0.30)。

# 设计评审:以 portfolio-arb 为主策略时的适配性与执行正确性(2026-10-02)

> 只读评审,未改动 `hft/`、`architecture-v2/` 正文与 `Trading/portfolio-arb/`。触发原因:用户确认**后续主要交易是老板的 CEX-CEX 打分套利(`Trading/portfolio-arb`)**,而现有设计的"现金流策略"前提是 cdex(C/D/E)+ A 类延迟套利。这是新的需求证据,所以重新审视范围。

## 0. 结论

1. **设计前提与主策略不符(范围级问题)。** hft 的 C 类 Carry 照 cdex `spread_engine` 写成"单币阈值触发"(`hft/crates/hft-strategies/README.md` C 节只有 11 行;Sizer 是 cdex 口径:单币 $150、chunk $40)。portfolio-arb 是"全币打分 → 幂律分配 → max_share 迭代封顶 → 目标 − 实际 → 双向切片调仓 + 滞回门"的**截面组合策略**。规格里没有承载它的策略族、数据来源(7 天分位、24 h 资金费统计、OI/成交额)、资金口径(BN 保证金余额 + Gate 现金 + Gate 代币按 bid)、账户级保证金风控、回测器与迁移方案。`AV2/01-总体架构.md:171` 只把它的"原则"放进 Python 流水线。**[已复核]**
2. **执行正确性有 7 个 P0 级规格漏洞**,都能在写代码前改规格修掉(§3)。其中两个会直接让 carry 留裸腿:开仓链接的对冲重试被分类成 reduceOnly(Binance 必拒),以及自身被强平/ADL 的成交被当成外来单、不更新仓位。
3. **工期与范围**:core 规格估计 Rust 12.5–18 万行 + 测试 8.5–12 万行(子审查按规格细节估算,量级判断),14–18 周对两人不现实;迁移门槛(DST 7 夜、测试网 3 天、Shadow ≥ 14 天、小额实盘)还在其后串行叠加。carry 用不到微秒级机制(忙等核、大页 journal、帧模板、N+1 热备连接、conn-builder、L2 双路),这些应移到 optional。
4. **主策略的盈亏主要由手续费/滑点、两腿一致性、跨所保证金、资金费核算决定,不由主机内微秒决定。** 现设计的投入重心应相应调整。

## 2. 策略执行层面的问题(carry 专属)

1. **平仓腿顺序**:规格规定平仓"现货 IOC 卖 → OnFill 永续 reduce-only 买"(hft-strategies C 节)。保证金压力下要先减的是永续空头(释放保证金、流动性更好);现货先卖时若卖不掉(见 P0-4),永续空头平不掉。建议按原因分:保证金/硬动作类退出 → 永续先;常规退出可按流动性选。PA 自己的原则也是"优先关 BN 空"(`PA/docs/dryrun_plan.md:155`)。
2. **账户级保证金与跨所资金**:按 PA 默认 deployable 0.6、BN 占总资金 40% 估算,BN 空头名义 ≈ BN 权益 × 1.5;持仓币**普涨 50%** 时 BN 权益只剩总资金约 10%(名义 0.9× 总资金,约 9 倍杠杆),**普涨 60%** 时约 4%,接近维持保证金。现货浮盈在 Gate,补不过来。PA 只有告警;hft 的强平距离硬动作是按单个 group 写的(cdex 小仓口径),输入来源也没定义(`hft/crates/hft-risk/README.md`:"保证金/强平距离不在热路径风控里")。需要:账户保证金率分档 cap(先禁开、再按比例跨 group 减仓)、watchtower P0 规则、treasury 从 optional 升为 core(至少监控 + 划转流程)。
3. **ADL / 强平 / 下架 / 结算周期变化**:见 P0-3;下架只能等每日 refdata 或 Drain 重启,没有"下架公告 → CloseOnly + 退出计划"的路径;Binance 会把高波动币的结算周期改成 1 h,interval 必须跟随事件。
4. **资金费按币归属 [需核实]**:按我对币安文档的记忆,全仓(联合保证金模式必为全仓)下 `ACCOUNT_UPDATE m=FUNDING_FEE` 只带余额 B、不带持仓 P,也就没有 symbol;而 `FundingSettle` 需要 `inst`(`hft/crates/hft-event/README.md` FundingSettle),venue 层又禁止合成。建议 Binance 按"只推费率"由 sequencer 合成每币资金费,WS 余额事件只做校验,reconciler 用 `/fapi/v1/income`(带 symbol)校正。
5. **C 与 D 共用 Binance 账户**:规格要求一个 (account, inst) 至多被一个非 Shadow cell 引用(`InstOwned`,hft-strategies SetParams 校验)**[已复核]**。PA 币池与 cdex 名单有重叠(如 AIN、TRADOOR、LIGHT),单向持仓下同币只能有一个 BN 净仓,资金费与盈亏也无法按策略拆分;两者还共享 BN 保证金,而分配器的"总资金"不知道 D 占了多少。建议 C 与 D 用不同的 Binance 子账户,或明确由一个分配器统一管理该账户。
6. **成本才是主要杠杆**:配置费率 BN taker 5 bp + Gate 1.6 bp,双腿往返 13.2 bp,另加两边点差。PA 的成本-机会门实际上几乎不起作用(C-4:新开仓与清零全部绕过),目标跟踪会频繁换手。两条值得量化的方向:(a) 修好滞回门、控制换手;(b) 一条腿挂单(Gate 现货 post-only,成交后 BN IOC 对冲),OMS 已支持 PostOnly + OnFill,但有逆向选择,需用数据评估。费率档(VIP/BNB 抵扣)在 `待测量` D6,应提前。
7. **数据缺口**:现有 collector 只有 Binance/OKX/Bitget,没有 Gate;7 天分位、成本标定、回测都缺 Gate 现货 BBO/深度历史。建议现在就为 31 个币录 BN 永续 + Gate 现货 BBO 与浅层深度。

## 4. P1(正确性或运维风险)

1. **NotFound 宽限后定 Rejected,迟到成交会双重对冲**;槽回收后的成交只写 Note 不入账。对冲腿的 NotFound 应等成交历史确认;保留上一代墓碑,迟到成交照常入账并报 P0。(`hft-oms` 终态表、`not_found_grace`;Binance `-1007` 后订单能否迟到执行 [需核实])
2. **恢复时输出不一致只告警,状态按重算推进**:重算决策与实际已发单不一致时,真实回报落成 StaleGen。不一致时该 (venue, account) 全部置 Unknown 并严格化闸门。(`hft-sequencer` RecoverDriver)
3. **对账告警规则不会触发**:watchtower `ReconcileMismatch` 条件是"严重级别 ≥ CloseOnly",reconciler 从不发 CloseOnly;`NakedExposure` 用同一份 ledger,看不见漏记成交。(`hft/apps/watchtower/README.md`、`reconciler`)
4. **自动 HedgeFix 无次数与冷却上限**,门控拒绝下可自激成循环(灌满 journal → JournalFull abort,或耗尽订单额度连锁 Broken)。复用 HedgeRetry 的计次/截止;HARD 下抑制。
5. **ClockBad 与 Halted 会挡平仓**:检查链 #2 只看 `origin == Strategy`,会拒策略的 Flatten/硬动作;`Throttle::can_fire` 遇 halted 开平同拒。两者只拦 Open,硬动作绕过 cooldown。
6. **Binance 账户模式启动不核验** **[已复核:venue-binance/refdata/hft-core 全文无 positionSide/双向持仓]**:单向/双向、多资产、全仓/逐仓、杠杆。reduceOnly 语义依赖单向持仓;若账户是双向持仓,下单全部被拒。加闸门位,配置变化设 cap。
7. **reconciler 缺 Gate 现货挂单与成交** **[已复核]**:Gate 只列了 futures 端点,而 carry 的多头腿在现货。
8. **Gate 实现顺序把期货定为"主用"** **[已复核]**(`venue-gate` 开发备忘),carry 需要的是现货 JSON 下单与 `spot.login`;`待测量` C2 测的也是合约登录。
9. **Shadow 期与旧引擎共用账户的规则空白** **[已复核 kill-switch 部分]**:kill-switch 在 hft-core 心跳停止时撤**该账户全部挂单**、`also_dms_venues` 默认 true,而迁移前旧引擎仍在同一账户交易。需要规定 Shadow 期是否持交易 key、是否刷新死手、kill-switch 是否武装、reconciler 是否把旧引擎仓位当差异。
10. **单进程爆炸半径**:HARD 只能与 Global 组合,测试账户失控只能连正式账户对冲一起封;确定性毒丸输入让恢复反复崩溃;新版本崩溃后 `VersionNeedsDrain` 使回滚走不通。允许按账户 HARD;同 seq 连续崩溃时隔离该输入。
11. **API key ↔ AccountId 无交易所身份核验**:test/prod key 配反就会串单。启动时按 key 查交易所 UID 与 `AccountMeta` 比对。
12. **磁盘/persist 退化没有自动降级**,runbook 却写"watchtower 已全局 CloseOnly"(watchtower 只告警)。冷盘满 → JournalFull → abort → 重启同样起不来。
13. **Drain 可能留裸腿**:`cancel_resting=true` 只等 Pending* 收敛,HedgeRetry 等待间隙与已 Ack 的 IOC 不在等待范围。
14. **Binance 用户流未知事件类型**(`TRADE_LITE`、`MARGIN_CALL`、`ACCOUNT_CONFIG_UPDATE`)若当解码失败,会触发查询风暴并断用户流;显式列可忽略类型。

## 5. 范围、工期与部署

- **规模(估计)**:地基 14–20k、运行时 22–32k、两所 6–8.5k、决策核心 27–37k、链上 11–16k、apps 18–27k、testkit/xtask/tools/deploy 28–42k(Rust,不含测试);Python 11–16k。按 AI 辅助下"经评审 + 有测试"300–600 行/人日,2 人 14–18 周只能完成 3–9 万行。只做 carry 最小版(无链上、无 A)约 6.5–9 万行,与 14–18 周相当。

- **一次性迁移把 C 的上线绑在 D/E 链上全栈与 ops_bot 完整对齐上**。可选做法:C 用独立的交易所子账户先上线——不违反"一个账户只归一个系统",但违反第七轮"一次性迁移"。需要用户/老板裁决。

## 7. 建议(按优先级)

1. **先定需求**:确认 portfolio-arb 是主策略后,写 `PortfolioCarry` 策略族规格(分配 advisor、目标跟踪调仓、按 venue 权益视图、168 h 分位与资金费统计、滞回门修正版、切片 Sizer、按原因的腿顺序、账户保证金分档 cap),再动代码。
2. **规格里修掉 §3 的 7 个 P0**,并补 P1-6/7/8(账户模式核验、Gate 现货对账、Gate 现货优先)。
3. **现在就开始录数据**:31 个币的 BN 永续 + Gate 现货 BBO 与浅层深度;并做 carry 经济性测量(资金费 × 基差 × 两所实际费率 × $500 切片滑点)。这是参数标定、回测与缩短 Shadow 的前提。
4. **重划 core**:第一交付 = Binance USDT-M + Gate 现货 + PortfolioCarry;链上(D/E)与 A 为第二交付;§5 列的微秒机制移到 optional。
5. **C/D 账户隔离**:不同 Binance 子账户,或由一个分配器统一管理该账户。
6. **treasury 与保证金管理升为 core**(至少监控、分档 cap、划转流程)。
7. **组合级回放器升为 core**(不是 hftbacktest 队列模型);冻结夜间自动换参,换参走样本外验证 + 人工接受。
8. **Shadow 放独立小实例**,并写清 Shadow 期 key、死手与 kill-switch 规则。
9. **portfolio-arb 专用迁移手册**:带入场价的 Adopt、Gate 余额基线、两腿同时采纳。

1. 解耦骨架已经基本能用。Model 的内存/检查点声明、按 GroupId 指纹重置、结构参数热更、分块检查点、布局金样、`non_prod_only`、`Views::leverage`、按成员聚合的 `BboView` 都写进了 SDK,engine/app 的 README 里没有策略族名。

3. 本轮新发现 6 个 P1,没有 P0。最要紧的三个:
   - 重发 Exit 目标会被执行层当作"相同目标"忽略,卡住的退出永远解不开。
   - "检查点只存原始样本"与"恢复后与连续运行逐字节相同"互相矛盾,每日 `--advice recompute` 必然失败,门槛 ⑦ 过不了。

## §3 新发现

### P1

**P1-1 被保留的 Exit/Hard/MarginStress 目标"原样重发"解不开 SliceFails**
- 场景:退出目标进入 `Stuck(SliceFails)`。策略按 pc:296 在 `fail_cooldown_ms` 后"以保存的字段重发同一目标"。但执行层规定,逐字段相同的目标视为已接受、不替换,而 SliceFails 只在目标被替换或清除时解除。
- 后果:退出永远卡住;每 3 s 发一条 P1 `ExitRetry`;对 `Hard`(强平后对齐腿)来说,裸露的腿一直留着。
- 引用:pc:248、296、669;E:305、539、555。
- 修法:重发时改动 `tag`(低位放重发次数),或在同一个 Ctx 里先 `clear_target` 再 `target`。hft-exec 写明"重置失败计数必须改字段"。

**P1-2 低于最小下单量的残余引起死循环**
- 场景:0/0 退出只剩一腿低于交易所最小下单量,执行层报 `Stuck{MinOrder}` 和 P1 `ExecStuck`,策略视为完成并 `clear_target`。
- 下一次评估又被"有仓位"条件拉回来:
  - `force_exit` 的 group:pc:291 "仓位非 0 且无生效目标 → 重设 0/0";
  - 负资金费:pc:202、255 "条件成立且有仓位 → 再进 Exit"。
- 后果:每个 BBO 都写 TargetSet/Stuck/Cleared 记录并发一条 P1,journal 与告警被刷爆。
- 引用:pc:202、255、291、296;E:496。
- 修法:把"有仓位"定义为至少一腿超过尘埃线且不低于最小下单量;对 MinOrder 残余置标志,仓位变化前不再触发。

**P1-3 退出被打断后丢失(状态机没闭合)**
- (a) L2 的 Stress 处理对 Exit 阶段的 group 没有例外(pc:266、305)。0/0 退出目标会被替换成"当前量 × 0.75",回落后回到 Idle,`exit_all`、下架、负资金费退出都被吃掉。
- (b) 退出中出现 `External{Manual}` → 冻结并清目标;两腿对齐后自动解冻回到 Idle 重新评估(pc:302)。Exit{Cmd} 没到 Done,所以没设再开仓封锁:人工在网页上平掉的仓位会被策略立刻重开。
- (c) `Exit{Delist}` 只在 Notice 事件里进入(pc:308),SWEEP 只对 Exit 阶段做升级,被 (a)/(b) 打断后不会恢复。
- 修法:在 GroupState 里持久记录"待完成退出"(来源、是否 urgent、封锁时长),任何阶段回到 Idle 前先检查它。L2 期间,有待完成退出的 group 保持 0/0,只升级为 Urgent。人工冻结的自动解冻:若之前在退出中或仓位已减少,同时设上封锁。

**P1-4 "检查点只存原始样本"与"续算逐字节相同"冲突,门槛 ⑦ 过不了**
- 场景:分位带只在每 `band_update_ms`(30 min)更新,恢复后在第一个模型 tick 重算(pc:524)。平滑窗从空开始,恢复后发出全部 group 的 Advice(pc:568)。这些都是路径依赖的状态,不能由原始样本重算。
- 后果:
  - SDK 的确定性夹具"检查点 → 恢复 → 继续 = 连续运行"(SDK:214、981、1182)过不了;
  - pc:680 "分位带与连续运行一致"不成立;
  - 每日 recompute 比较 `last_seq` 之后的全部 Advice(R:59;T:81),每天都会不一致,⑦ 要求的"每日通过"(T:316)达不到。
- 修法见 §5-1。

**P1-5 GroupId 的分配器每实例一个,规格却要求全局唯一**
- 冲突:P:139 写"分配器每个策略实例一个";TY:152、S:603、CP:130 要求全局唯一,重复报 `GroupIdDup`。
- 场景:dev2 的 `sim` 实例里,每个研究中的策略有 2 个模拟实例(core:344;`crates/hft-sim/README.md:218`)。两个分配器各自从同一个值开始,第二个实例的 SetParams 被拒。hft-cfg 有自己的分配路径(TY:152),同样会撞。
- 修法:GroupId = (StrategyId << 24) | 实例内计数器;或分配器按 hft-core 实例共享。

**P1-6 资金费环容量:pc 写 64,strat-lib 是 256**
- 引用:pc:120、394、521、656 写 64;SL:185、425、440 是 `FUNDING_RING = 256`(约 6 KiB/group)。
- 后果:
  - pc 的快照上界每 group 只留 2,048 B 给"节头 + PctConfig + 资金费环 64 × 24 B"。环一旦超过约 78 条(1 h 周期一做预热就有 168 条),节体超过声明,按 SDK:211、S:415 整份检查点作废,而且一直作废。
  - `FUNDING_TRUNC` 的判据与 strat-lib 的 `TRUNCATED` 不一致;`funding_window_ms` 上限 48 h 的理由也过时了。
- 修法:公式改用 `FundingStats::snapshot_bytes`;标志直接取 summary 的 `TRUNCATED`;重新说明窗口上限的理由。

### P2(场景 + 引用 + 建议)

1. **dev2 sim 的预算没有余量。** core:323 给 advisor 128 MiB;pc 64 group 精确为 64.07 MiB/实例,2 个池实例合计 128.13 MiB,超出即装配退出 2。研究 `pct_*` 时任何加大内存的改动都会被拒。`max_cells_total` 128、`max_instances` 8(core:337-338)只够 2 个研究策略。PCP:95 默认 32 group 暂时缓解。建议:表里写明余量,或约定 sim 实例 ≤ 32 group。
2. **SetParams 不校验检查点盘上限,而启动时校验。** core:300 启动时检查 2×Σ`snapshot_bytes`,S:608 与 CP:129 只查内存。热改通过后,下次启动退出 2,而且 core:56 写明退出 2 不重启。另外 core:67 说"零改动,只需运维调大预算",core:300 却说"调大预算 = 改本表"。
3. **门槛 ⑧ 实际覆盖不到 SDK 说的内容。** T:317 与 testkit:127-131 的 scaffold-gate 不装配 hft-core、不绑定账户、不生成 pipeline 插件;SDK:1184 声称的">1 MiB/group 的 Model + 按 `mem_bytes` 装配"只在 core:727 由 hft-core 自己的测试覆盖。testkit:131 与 tools:91 检查 diff 的路径范围也不一致。建议用 `--with-model --with-pipeline` 生成探针,并做一次装配检查。
4. **结构参数热更在 Live 实例上是中性的(CP:63、P:167),不需确认。** 后果是全部 group 重置,数小时只能 HOLD,并注入约 62 MiB 预热数据(pc:500、PCP:138)。PCP:99-101 的 policy 字段又重复了 `pct_window_ms`、`pct_min_coverage` 等策略参数,热更后预热回看窗口不会跟着变。
5. **分块检查点的描述有两处不一致。** pc:570 写"块间 Model 照常处理事件",与 SDK:211、S:415、core:359(整个 advisor 暂停)相反。SDK:211 说 `max_bytes` 按 1 ms 时间片给出,core:359 是固定 `checkpoint_chunk_kib`。
6. **SetParams 的 LotMismatch 检查对存量 group 也整条拒绝(S:607;E:398)。** 价格上涨使某个持仓 group 的 lcm 名义超标,或拿不到参考价时,该实例的一切 SetParams(包括收紧、`force_exit` 参数、`open_allowed = false`)都被拒;这个 group 又因有仓位不能移除。建议只检查新增或指纹变化的 group。
7. **永续硬上限(pc:88)没计入其他 group 的已承诺增量(pc:85 只用于保证金约束)。** 多个 group 同时开仓时会短时超过上限。另外 LotMismatch 的标志每个参数版本复位一次(pc:300、603),pipeline 每轮都改 `liq_score` 时,每轮会重复一条 P1。
8. **本池资金费最高的币,超配或被置为"只平不开"后几乎减不下来。** 原因:`close_gain_daily` = 0(pc:217、546;PCP:108),只能等一次性收益覆盖平仓成本。这已写成已知限制(pc:708),但"只平不开"的意图(例如流动性枯竭)达不到。见 §5-2。
9. **`relax` 字段的语义有冲突。** pc:502 说 `relax` 决定人工修改的确认,CP:63 说 body 字段不参与放宽判定。`neg_funding_exit_periods` 标 `Up`,但"0 = 关闭"是最宽,不单调:3 → 0 会被判为收紧。
10. **预热会重复触发,而且 pipeline 有一处与 SDK 冲突。** 新 group 同时满足"新增 GroupId"和 `ModelGroupReset` 两个触发条件(P:180;SDK:236)。重启追赶时重放 SetParams,又会重写 Meta `ModelGroupReset`(S:402)。P:277 "格式变化换 `local_kind`"与 SDK:988、PCP:202 冲突。
11. **门槛 ⑦ 的重新计时范围和白名单。**
    - 重新计时不含 hft-oms、hft-sequencer、SDK 的代码改动(T:332)。
    - 小改白名单只写在 README 文字里(pc:504-510),无法机检。
    - 分位类字段 ±20% 太宽(`p_entry` 0.80 → 0.64)。
    - "首个 core 策略"的写法(T:316、222)意味着每加一个策略都要改 testing.md。
12. **小一致性问题。**
    - pc:665、677 的"100 group 分两批"在每实例 64 group 上限下(core:339)不可能出现。
    - `MAX_BBO_CONN_SLOTS` 的归属:TY:154 说归 SDK,S:312 说在 hft-types;hft-venue 不依赖 SDK,应归 hft-types。
    - cdex:63、cross-taker:42、maker-taker:42 的 `StrategyDesc` 字面量缺 `non_prod_only`,按 Rust 写法编译不过。
    - pc:645 "约 5 次分位查询"实际约 7 次,64 group 的 p99 接近 1 ms。
13. **`BboView.resync` 对成员取"或"(S:332;SDK:514)。** 一条赛马成员在 resync 时,即使另一条健康成员正在送数据,该 inst 也判为不可用,削弱了 L-P1-2 的冗余效果。建议改为"没有任何非 resync 的 up 成员"才算 resync。
14. **latency-probe 只走 OrderIntent 路径。** pc 实际走的是 TargetIntent → hft-exec 推进 → 切片,这条路径在门槛 ⑩ 中没有样本(待核实 latency-budget 是否另有覆盖)。建议加一个 `target` 模式。

### 写第二、第三个策略的检验

- **跨所永续×永续资金费**:SDK 够用。两腿都是永续时的腿顺序已定义(E:378),treasury 两个方向都算(treasury:59),hft-sim 支持多空(sim:428),可以读实际杠杆。缺口是压力用例:`StressScope` 只有全部资产同向一种(sim:242),`PricePath` 只有单边与现货/永续基差扩大(sim:240),没有"某一所单独暴涨"的变换,需要改 hft-sim。MS-2 写的"对永续腿不利的方向"在两条永续腿时有歧义(T:222)。
- **跨所吃单 cross-taker**:SDK 够用(LegLink Simultaneous、`rx_tsc`/`hw_rx_ns`、`utc_of`、参考行情订阅、LeadLag)。只需修 DESC 字面量,并在发布构建里打开对应 feature(registry:103 归 deploy)。
- **只用 Model 的统计策略**:Model 收不到 `Exec`/`Order`/`Manual`(SDK:718-724),看不到成交、命令与封锁。每实例 64 group(core:339)加"一个账户一个实例",大币池要么改 hft-core 容量表,要么拆成多个账户。dev2 的 sim 容量和预算(P2-1)意味着第二个研究策略上来就得改 hft-core 的表,与 cookbook:3 "容量表也不改"矛盾。

## §4 应保留的设计

- 依赖方向与 registry 唯一清单;testkit 只带测试策略;`decoupling-gate`。
- 参数编解码只有一份实现,`schema_digest` 不含字段属性与描述符。
- Advice 不透明;按 `basis_seq`/`boot_seq` 判过期;`spec_seq` 丢弃旧规格产生的 Advice。
- 检查点键不含参数、refdata 与发版;布局用 `ModelLayoutDesc` 金样而不是字节金样;分块写出时整个 advisor 暂停。
- `mem_bytes`/`snapshot_bytes` 声明由装配求和、SetParams 复核。
- 结构参数通过 `layout_eq` 按 group 重置,不重新分箱。
- `non_prod_only` 在 refdata、hft-core 装配、gateway、sequencer 四层都校验。
- `BboView` 按值返回,报价健康只看连接成员;`Views::leverage` 与风控杠杆上限读同一来源。
- portfolio-carry 侧:
  - `close_cost` 与"只对开仓用倍数条件";
  - 默认生效的负资金费退出;
  - 已承诺额从目标视图推导;
  - CloseOnly 下持有 + `exit_all`;
  - 与杠杆无关的硬上限;
  - Stuck 按目标原因区分处理;
  - LotMismatch 只拒增仓;
  - "目标的设与留"规则;
  - 人工外来成交冻结、引擎不自动平。

## §5 需要负责人决定的问题(附推荐)

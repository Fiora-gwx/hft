# Wire 轮询与交接审查

本报告是共享 Windows x86_64 主机的诊断，不代表 aarch64 参考机验收。基线为 `408b496c`。无 c8g 主机访问。实际 Linux syscall trace、绑核 profile 与网卡到 sequencer 的 p50/p99 待独立参考运行。

## 实现与测量边界

`wire_poll` 用相同 Conn/TLS/WS 入口比较 eager `poll_rx` 与 `poll_rx_if_needed`，在一次脚本收包里预装持续 backlog，每轮取一个消息。TLS 加密和脚本装载在计时外；计时包含接收缓冲压缩、脚本 recv、TLS 解密及 WS 解帧。HistBench 预热 5,000 次、采样 50,000 次；有序 TSC，nominal 频率或一次校准；系统分配器、不绑核；开发构建 opt-level=3/debug=0。脚本 API 调用计数不是实机 Linux 系统调用观测。

SPSC 比较同线程写入并取出 16 个 64 B 元素的现有 try_pop/read_batch API，包含写端批量发布；不含跨核 cache-line 迁移、sequencer 调度或业务处理，不能用它替代跨核 hop 验收。

## 路径审查

| 项目 | 当前实现与决定 |
|---|---|
| 专用核与共享主机 | IdlePolicy 的 Spin、SpinThenPark、Park 已可配置。Spin 不 park，任务内不等待；dev2 保留共享核 park 配置。未改变默认线程计划。 |
| epoll | feed 的 ReadyPoll 使用 epoll_pwait(timeout=0)，ready_poll 生效时一次探测多个 fd；gw 不调用零超时 epoll。park 才等待事件/期限。 |
| 接收批量 | 每次 poll_rx 至多一个 recvmsg，短读不补 EAGAIN。BBO 路由用新入口优先消费完整缓冲记录/帧，部分记录补读，帧数公平性限额保持。 |
| read-until-EAGAIN / recvmmsg | TCP 没有 datagram 消息边界；无证据支持额外读取循环。保留一次读满空闲缓冲的有界处理。 |
| 缓冲尺寸 | Md 256 KiB、Order 64 KiB 的配置契约不变。先减少不必要的压缩，不通过放大缓冲掩盖排队。 |
| TLS | rustls unbuffered 握手后原地 record layer，next_frame 按需逐记录解密，凑够一帧即停。继续保留，未批量预解密整个 backlog。 |
| 定时器 | wire 任务计算 next_deadline，TaskLoop 等待 min(park 上限, 下一期限)，无粗粒度 timer wheel 需要改动。 |
| SPSC | producer/consumer 分离 cache line、缓存对端游标已有。gateway 将逐项 tail Release 改为一次批量 Release；sequencer 优先级不变。 |
| wakeups | Spin 热生产者不调用 futex/eventfd 唤醒；共享核模式保留丢唤醒防护。 |
| 内核 busy-poll | SO_BUSY_POLL=0，IRQ 隔离规则不变；需要 owner 改变架构决定并有参考机证据后才能启用。 |

## BBO stage 边界

现有 [BBO stage 数据](2026-10-15-bbo-stages.json) 明确排除 exchange decode 和 NIC；wire 改动不能据此宣称 seq-decide 改善。此任务的 BBO 路径测量使用 hft-venue 原有 `venue_feed_bbo_path`，覆盖生产 feed poll 到输出环，协议为已有 StubProto，不代表真实交易所 decode。seq-decide 分段未修改，未重编译未触及的 sequencer crate。

## 验证范围

NET-080/081 检查明文/密文已有数据、部分记录、跨记录帧、读取戳与 recv 调用数；已有 net/venue 测试覆盖错误帧、控制帧、TLS、环满、订单重排、账户配额、每帧 drain 和预热零分配。不得把脚本正确性测试等同于 Linux 性能验收。

## 逐消息直方图结果

| 输入/操作 | before p50/p99 ns | after p50/p99 ns | scripted recv/message before → after |
|---|---:|---:|---:|
| 274 B payload（300 B TLS record） | 948 / 1,131 | 151 / 988 | 1.0 → 0.0046 |
| 2,048 B payload | 1,205 / 2,237 | 323 / 3,459 | 1.0 → 0.03227 |
| 16 × 64 B SPSC 写入 + 取出 | 45 / 63 | 33 / 39 | 0 → 0 |

2 KiB 的 p99 回退，因此仅 BBO feed 启用缓冲优先；其余行情与 gateway 保留直接 poll_rx。BBO 的 p99.9 也由 1,508 ns 上升到 6,103 ns，完整原始值在 [JSON](2026-10-15-wire-io.json)。此策略在持续 backlog 下合并读取、减少重复搬移，但偶尔整块补读的尾部成本仍需 aarch64 验证；不能把中位数收益解释为所有尾部改善。

## 既有 feed harness

Criterion 20 样本、300 ms 热身、2 s 测量；仅计生产 poll_once，脚本加密与输出环排空在计时外。before 使用原 feed/gw 源码，after 为 BBO 缓冲优先入口；两者 net 核心相同，原入口不变。估计值不是逐消息 p50/p99。

| 基准 | before | after |
|---|---:|---:|
| `venue_feed_bbo_path` | 5.4235 µs | 4.8465 µs |
| `venue_feed_dup_drop` | 11.937 µs | 4.8857 µs |
| `venue_bbo_live_tick` | 13.186 µs | 4.3413 µs |
| `venue_idle_loop_bbo` | 14.73 µs | 3.7705 µs |
| `venue_idle_loop_bbo_ready` | 19.452 µs | 4.0613 µs |

空闲 ready 路径也有数倍变化，说明共享机调度/负载的干扰很大。表中所有值保留，但不据此宣称 feed 整体加速，也不替代原 BBO stage 的参考运行。
